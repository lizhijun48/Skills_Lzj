# meta-risk-basics · 风险管理基础通用框架

> **核心定位**：产品经理和项目经理共享的风险管理入门工具——"不确定的事件如果发生了会影响目标"就是风险，管好它就管好了不确定性。
> **被调用方**：pd-go-nogo（产品机会评估的风险维度）+ pd-product-strategy（战略风险）+ pd-portfolio-management（组合风险）+ pm-risk-management（项目风险管理完整版）

---

## 为什么PD和PM都需要风险管理？

| 视角 | 产品经理的风险 | 项目经理的风险 |
|------|-------------|-------------|
| 核心关注 | "产品方向对不对" | "项目能不能按时交付" |
| 风险来源 | 市场变化、用户需求偏移、竞品冲击 | 范围蔓延、资源不足、技术难题 |
| 失败代价 | 做了一个没人要的产品 | 项目延期/超支/质量不达标 |
| 管理方式 | 假设验证+快速试错 | 风险登记册+应对计划+储备 |

**核心逻辑**：PdM管"做对的产品"（方向风险），PgM管"把产品做对"（执行风险）。两者都需要系统化的风险管理方法。

## 一、风险的定义与分类

### 定义

**风险**= 不确定的事件或条件，一旦发生，会对目标产生正面或负面影响。

- **威胁（Threat）**：负面的不确定事件→需要应对
- **机会（Opportunity）**：正面的不确定事件→需要利用
- 本框架主要关注威胁管理（机会管理见pd-portfolio-management）

### 风险分类

| 分类维度 | 类型 | 示例 |
|---------|------|------|
| **已知-未知** | 已识别但不确定是否发生 | 甲方可能改需求 |
| **未知-未知** | 完全没预料到 | 疫情封控 |
| **技术风险** | 技术方案不确定 | AI模型精度不达标 |
| **市场风险** | 市场环境不确定 | 竞品提前发布 |
| **组织风险** | 内部资源/管理不确定 | 核心成员离职 |
| **外部风险** | 政策/法律/不可抗力 | 等保标准升级 |

## 二、概率-影响矩阵（PIM）

### 矩阵结构

|  | 影响1(微小) | 影响2(轻度) | 影响3(中度) | 影响4(重大) | 影响5(灾难) |
|---|---|---|---|---|---|
| **概率5(极高)** | 🟡中 | 🟠高 | 🔴极高 | 🔴极高 | 🔴极高 |
| **概率4(高)** | 🟢低 | 🟡中 | 🟠高 | 🔴极高 | 🔴极高 |
| **概率3(中)** | 🟢低 | 🟡中 | 🟡中 | 🟠高 | 🔴极高 |
| **概率2(低)** | 🟢低 | 🟢低 | 🟡中 | 🟡中 | 🟠高 |
| **概率1(极低)** | 🟢低 | 🟢低 | 🟢低 | 🟡中 | 🟡中 |

### 概率量化参考

| 等级 | 概率 | 判断依据 |
|------|------|---------|
| 5-极高 | >80% | 历史项目中频繁发生 |
| 4-高 | 60-80% | 本类项目中常见 |
| 3-中 | 30-60% | 有可能发生 |
| 2-低 | 10-30% | 偶尔发生 |
| 1-极低 | <10% | 几乎不会发生 |

### 影响量化参考

| 等级 | 影响 | 判断依据（成本/进度/质量/范围） |
|------|------|--------------------------|
| 5-灾难 | 不可接受 | 项目失败/产品下线 |
| 4-重大 | 严重影响 | 进度延期>30%/成本超支>30% |
| 3-中度 | 可感知 | 进度延期10-30%/成本超支10-30% |
| 2-轻度 | 轻微 | 进度延期<10%/成本超支<10% |
| 1-微小 | 可忽略 | 几乎无影响 |

### 应对优先级

| 风险等级 | 处理策略 | 资源投入 |
|---------|---------|---------|
| 🔴 极高 | 必须制定应对计划+分配应急储备 | 优先级最高 |
| 🟠 高 | 必须制定应对计划 | 优先关注 |
| 🟡 中 | 可接受但需监控 | 定期检查 |
| 🟢 低 | 可接受，列入观察清单 | 周期性回顾 |

## 三、4种风险应对策略

### 威胁应对

| 策略 | 含义 | 适用条件 | 示例 |
|------|------|---------|------|
| **规避** | 改变计划消除风险 | 风险太高不值得冒 | 放弃新技术方案改用成熟方案 |
| **转移** | 将风险后果转移给第三方 | 有合适的转移对象 | 购买保险/外包高风险模块 |
| **减轻** | 降低概率或影响 | 风险不能完全消除 | 增加测试/设计冗余/原型验证 |
| **接受** | 不采取行动 | 风险在可接受范围 | 小概率低影响风险→观察 |

### 机会应对

| 策略 | 含义 | 适用条件 | 示例 |
|------|------|---------|------|
| **开拓** | 确保机会发生 | 机会价值高 | 分配最优秀团队攻坚 |
| **分享** | 引入第三方共享受益 | 需要外部能力 | 与合作伙伴联合开发 |
| **提高** | 增加概率或影响 | 机会可能发生 | 增加市场推广投入 |
| **接受** | 不主动追求但准备利用 | 机会不确定 | 准备好方案，等机会出现 |

### 决策树——选哪种策略？

```
风险能消除吗？
├─ 能 → 规避
└─ 不能
    ├─ 有第三方能承担吗？
    │   ├─ 能 → 转移
    │   └─ 不能
    │       ├─ 能降低概率/影响吗？
    │       │   ├─ 能 → 减轻
    │       │   └─ 不能 → 接受
    │       └─ 影响在可接受范围内吗？
    │           ├─ 是 → 接受（主动）
    │           └─ 否 → 必须规避或转移
```

## 四、风险登记册模板

### 即用模板

| # | 风险描述 | 类别 | 概率 | 影响 | 风险等级 | 应对策略 | 应对行动 | 责任人 | 状态 | 截止日期 |
|---|---------|------|------|------|---------|---------|---------|--------|------|---------|
| R001 | AI模型精度不达95% | 技术 | 4 | 4 | 🔴极高 | 减轻 | 增加训练数据+备选模型 | 张工 | 开放中 | 6/30 |
| R002 | 核心后端离职 | 组织 | 3 | 4 | 🟠高 | 减轻 | 代码评审+知识文档+AB角 | 李总 | 监控中 | 持续 |
| R003 | 等保三级不通过 | 合规 | 2 | 5 | 🟠高 | 转移 | 聘请等保咨询机构 | 王工 | 准备中 | 7/15 |

### 使用规则

1. **编号规则**：R+3位数字，按发现顺序编号
2. **描述格式**："[风险源]可能导致[后果]"，如"甲方频繁变更需求导致范围蔓延"
3. **责任人不许空**：每个风险必须有人负责跟踪
4. **定期更新**：产品/项目周会过一遍风险登记册
5. **关闭条件**：风险不再可能发生 或 已发生并处理完毕

## 六、风险管理的5个层次

### 从"救火"到"预防"

| 层次 | 名称 | 描述 | 典型表现 |
|------|------|------|---------|
| L1 | 救火式 | 出了问题再解决 | "线上挂了！快修！" |
| L2 | 缓解式 | 知道有问题但不够系统 | "这个可能会出事，盯着点" |
| L3 | 预防式 | 系统识别+评估+应对 | 有风险登记册+定期评审 |
| L4 | 预测式 | 基于数据分析预测风险 | 趋势分析+预警指标 |
| L5 | 文化式 | 风险意识融入组织文化 | 人人主动报告风险 |

### 进阶路径

```
L1救火 → L2缓解：建风险登记册，开始记录
L2缓解 → L3预防：用PIM评估+制定应对计划
L3预防 → L4预测：引入数据分析+预警指标
L4预测 → L5文化：风险透明化+无责报告文化
```

## 核心原则

1. **风险不等于问题**：风险是"可能发生"，问题是"已经发生"——风险可以预防，问题只能解决
2. **主动优于被动**：花1小时识别风险，省100小时救火
3. **量化优于定性**：概率-影响矩阵让风险可比较、可排序
4. **登记册是活文档**：不更新的风险登记册=没有风险管理
5. **风险与机会并存**：管理威胁的同时别忘了利用机会
6. **文化是终极防线**：最好的风险管理是团队每个人都在想"什么可能出错"
