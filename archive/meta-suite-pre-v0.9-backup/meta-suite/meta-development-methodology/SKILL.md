# meta-development-methodology · 开发方法与生命周期选择通用框架

> **核心定位**：产品经理和项目经理共享的开发方法决策工具——"用什么方法做"是产品和项目的共同起点，选错方法比选错技术栈后果更严重。
> **被调用方**：pd-integration（产品整合管理-开发方法选择）+ pm-integration（项目整合管理-开发方法选择）+ pd-innovation-process（新产品开发流程选择）

---

## 为什么开发方法选择这么重要？

| 选对方法 | 选错方法 |
|---------|---------|
| 需求变化时从容应对 | 需求一改就崩盘 |
| 交付节奏可预期 | 永远在"快完了" |
| 团队协作高效 | 开发和产品天天吵架 |
| 甲方满意 | 甲方追着改需求 |

**核心逻辑**：开发方法不是"我们团队习惯用什么"，而是"这个产品/项目的特点适合用什么"。

## 一、5种开发方法对比

### 全景对比表

| 维度 | 预测型(瀑布) | 迭代型 | 增量型 | 敏捷型 | 混合型 |
|------|------------|--------|--------|--------|--------|
| **需求确定性** | 高 | 中低 | 中 | 低 | 混合 |
| **技术确定性** | 高 | 中低 | 中高 | 低 | 混合 |
| **交付方式** | 一次交付 | 循环改善 | 逐块叠加 | 小步快跑 | 分阶段混合 |
| **变更成本** | 高 | 中 | 中 | 低 | 阶段相关 |
| **适用规模** | 中大型 | 中型 | 大型 | 小中型 | 大型 |
| **甲方参与** | 里程碑 | 定期评审 | 增量验收 | 持续参与 | 阶段相关 |
| **文档要求** | 重 | 中 | 中 | 轻 | 分阶段 |
| **风险暴露** | 晚 | 早 | 中 | 早 | 分阶段 |

### 各方法详解

#### 1. 预测型（瀑布/Waterfall）

**核心逻辑**：需求明确→设计→开发→测试→交付，一气呵成。

```
需求 → 设计 → 开发 → 测试 → 部署 → 交付
  ↓      ↓      ↓      ↓      ↓      ↓
 完成   完成   完成   完成   完成   完成
```

**适用条件（全部满足）**：
- ✅ 需求在项目启动时就能完全定义
- ✅ 技术方案成熟，无技术风险
- ✅ 变更极少或变更成本可接受
- ✅ 甲方要求一次性交付
- ✅ 合同约定固定范围+固定交付

**典型场景**：
- 政府信息化项目初设阶段（需求已审批）
- 建筑工程（图纸定稿后施工）
- 硬件产品量产

**踩坑预警**：
- ❌ 需求"应该不会变"→大概率会变，瀑布变更是灾难
- ❌ 甲方说"我要的东西很清楚"→他清楚的不是需求，是期望

#### 2. 迭代型（Iterative）

**核心逻辑**：先做原型→评审→修改→再评审→……→最终版本。

```
原型V1 → 评审 → 修改 → 原型V2 → 评审 → 修改 → ... → 最终版
```

**适用条件**：
- ✅ 需求方向明确但细节模糊
- ✅ 甲方需要看到原型才能确认
- ✅ 技术方案需要验证

**典型场景**：
- UI/UX设计（需多次评审）
- 新技术验证（PoC阶段）
- 复杂算法调优

#### 3. 增量型（Incremental）

**核心逻辑**：把大系统拆成小块，每块做完就交付一块，最终拼成完整系统。

```
模块A(完整) → 交付A
模块B(完整) → 交付A+B
模块C(完整) → 交付A+B+C=全部
```

**适用条件**：
- ✅ 系统可拆分为独立模块
- ✅ 每个模块可以独立交付价值
- ✅ 甲方可以分阶段验收

**典型场景**：
- 大型ERP系统（财务模块→HR模块→供应链模块）
- 智慧城市项目（视频监控→门禁→停车场）

#### 4. 敏捷型（Agile/Scrum）

**核心逻辑**：小团队、短周期、快反馈、持续调整。

```
Sprint 1(2-4周) → 可用增量1 → 评审 → 调整Backlog
Sprint 2(2-4周) → 可用增量2 → 评审 → 调整Backlog
...
```

**适用条件（全部满足）**：
- ✅ 需求变化频繁
- ✅ 团队5-9人，跨职能
- ✅ 甲方/用户可频繁参与评审
- ✅ 产品可拆分为小的可用增量
- ✅ 不需要大量前置文档

**典型场景**：
- 互联网产品
- SaaS产品
- 创业项目MVP

**踩坑预警**：
- ❌ 甲方不在→Scrum Master变传话筒
- ❌ 没有Product Owner→需求没人拍板
- ❌ Sprint中途改范围→这不是敏捷，这是混乱
- ❌ 跳过回顾会→问题永远重复

#### 5. 混合型（Hybrid）

**核心逻辑**：不同阶段用不同方法，取各方法之长。

```
需求阶段(预测型) → 架构设计(预测型) → 开发(敏捷) → 集成测试(预测型) → 交付
```

**适用条件**：
- ✅ 需求有确定部分也有不确定部分
- ✅ 甲方要求部分里程碑式管理
- ✅ 合同约束要求阶段性交付
- ✅ 大型项目必须分阶段管控

**典型场景**：
- 政府信息化项目（初设+详设走瀑布，开发走敏捷）
- 大型AIoT项目（硬件走瀑布，软件走敏捷）
- 企业数字化转型（整体规划走预测，试点走敏捷）

## 二、决策矩阵——选哪种方法？

### 2×2快速判断

```
                    需求确定
                      高
                      |
         预测型        |       增量型
         (瀑布)        |       (分块交付)
                      |
  技术确定 ——————————+—————————— 技术不确定
         高           |           低
                      |
         混合型        |       敏捷型
         (前稳后快)     |       (小步快跑)
                      |
                      低
```

### 7因素加权评分（精确选择）

| 因素 | 权重建议 | 偏预测 | 偏敏捷 |
|------|---------|--------|--------|
| 需求变化频率 | 20% | 低频(1-2次/月) | 高频(每日) |
| 技术成熟度 | 15% | 成熟技术 | 新技术/探索 |
| 团队敏捷成熟度 | 15% | 无敏捷经验 | 有Scrum经验 |
| 甲方参与度 | 15% | 里程碑参与 | 每日/每周参与 |
| 合同/合规约束 | 15% | 固定范围+审计 | 灵活范围 |
| 项目规模 | 10% | 大型(50+人) | 小型(<15人) |
| 产品创新度 | 10% | 改进型 | 颠覆型 |

**评分规则**：每个因素1-5分（1=偏预测，5=偏敏捷），加权求和：
- **1.0-2.5** → 预测型
- **2.5-3.5** → 混合型
- **3.5-5.0** → 敏捷型

### 即用决策卡

| 判断条件 | 结论 |
|---------|------|
| 需求变化>3次/月 且 甲方能每周参与 | 敏捷型 |
| 需求基本确定 且 技术成熟 | 预测型 |
| 需求部分确定+部分不确定 | 混合型 |
| 大系统可拆独立模块 | 增量型 |
| 需要看到原型才能确认 | 迭代型 |

## 三、政企项目混合法推荐

### 为什么政企项目大多走混合型？

| 政企特点 | 与纯敏捷的冲突 | 混合法解决方式 |
|---------|--------------|--------------|
| 财政审批固定预算 | 敏捷范围不固定→预算无法审批 | 前期预测型锁定预算范围 |
| 初设/概算需批复 | 敏捷不做大量前期设计 | 初设走预测型 |
| 审计要求文档完整 | 敏捷文档轻量化 | 前期文档完整，开发期文档适度 |
| 验收需对照合同 | 敏捷交付物难以对照 | 里程碑式验收+增量交付 |
| 等保测评要求 | 安全要求必须前置 | 安全架构预测型设计 |

### 推荐混合模式

```
阶段1：立项与初设 → 预测型（瀑布）
  ├─ 项目建议书 → 可研 → 初设概算 → 评审
  └─ 输出：范围基线+技术架构+安全方案

阶段2：详细设计与开发 → 敏捷型（Scrum）
  ├─ 2周Sprint → 可用增量 → 评审
  ├─ 6-8个Sprint完成核心功能
  └─ 输出：产品增量+迭代记录

阶段3：集成测试与验收 → 预测型（瀑布）
  ├─ 系统集成测试 → 等保测评 → 试运行 → 终验
  └─ 输出：验收报告+测试报告+运维手册
```

### 关键衔接规则

| 衔接点 | 从预测→敏捷 | 从敏捷→预测 |
|--------|-----------|-----------|
| 范围 | 预测阶段锁定核心范围 | 敏捷阶段所有增量需回归到范围基线 |
| 文档 | 预测阶段产出的文档是敏捷阶段的输入 | 敏捷阶段产出需补齐文档用于验收 |
| 评审 | 初设评审通过→解锁开发 | 每个Sprint产出需符合初设要求 |
| 变更 | 初设内→敏捷调整；超初设→走变更 | 测试阶段变更→走正式变更流程 |

## 四、生命周期阶段映射

### 产品生命周期 vs 项目生命周期

| 阶段 | 产品经理关注 | 项目经理关注 | 开发方法 |
|------|------------|------------|---------|
| 发现 | 市场机会+用户需求 | — | 设计思维/精益创业 |
| 定义 | 产品定义+PRD | 项目立项 | 预测型(立项) |
| 开发 | 产品增量+用户反馈 | 项目执行 | 敏捷型(开发) |
| 上市 | GTM+种子用户 | 项目收尾+验收 | 预测型(验收) |
| 增长 | 运营数据+迭代 | — | 敏捷型(迭代) |
| 衰退 | 退市决策 | — | — |

### 开发生命周期阶段对照

| 阶段 | 预测型 | 敏捷型 | 混合型 |
|------|--------|--------|--------|
| 启动 | 项目章程→范围定义 | 产品愿景→Backlog梳理 | 项目章程→范围基线 |
| 规划 | WBS→进度→预算 | Sprint规划→Definition of Done | 初设→Sprint规划 |
| 执行 | 按计划开发 | Sprint执行→每日站会 | 开发Sprint执行 |
| 监控 | EVM→偏差分析 | 燃尽图→回顾会 | 双轨并行监控 |
| 收尾 | 验收→归档 | 发布→回顾 | 验收→回顾→归档 |

## 五、常见错误与修正

| 错误 | 后果 | 修正 |
|------|------|------|
| "我们用敏捷"但没有Product Owner | 需求没人拍板，团队等指令 | 任命PO或转为迭代型 |
| 瀑布项目需求频繁变更 | 变更成本爆炸 | 评估转为混合型 |
| 敏捷团队50人 | Scrum仪式效率极低 | 拆为多个Scrum团队+SoS |
| 政府项目全走敏捷 | 审计不通过 | 改为混合型 |
| 跳过初设直接开发 | 概算无法批复 | 补初设阶段 |
| 敏捷但不做回顾会 | 问题永远重复 | 强制每Sprint回顾 |

## 核心原则

1. **方法适配项目**：不是"我们习惯什么方法"，而是"这个项目适合什么方法"
2. **政企默认混合**：纯敏捷在政企项目里行不通，默认推荐混合型
3. **阶段可切换**：项目不同阶段可以用不同方法，不必一刀切
4. **敏捷不是乱来**：敏捷有严格框架（Scrum/看板），不是"想到哪做到哪"
5. **预测不是死板**：预测型也有变更管理，不是"定了就不改"
6. **决策要留据**：选什么方法、为什么选，必须写进项目章程/产品规划
