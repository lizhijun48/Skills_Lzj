# 中央法规库三层架构建设 SOP（law-repository-sop）

> 来源：legal-suite/law-repository 实战建设经验（2026-08-31~09-01）沉淀。对齐 GOV_SkillGovernance v3.6。

## 一、适用场景

- 用户要求建"单独的法规库 / 知识库 / 权威数据源"，且要明确含**原文、司法解释、领域解读、案例引用 + 更新/版本迭代机制**
- 各行业技能已内嵌蒸馏数据，需与权威源**解耦**（不删、不迁、不阻塞）
- 需要"蒸馏引用源 + 新要求反向推动源更新"的**双向闭环**

## 二、核心原则（对齐 GOV v3.6）

1. **原则八 修改前置治理判定**：任何改动先判定「严格符合 / 特殊情况偏离」
2. **原则九 模块融合去重**：跨模块重叠话术互指，不重复实现
3. **原则十 外部技能通用化**：第三方技能去显著标识、留结构、原版溯源
4. **QG4 数据溯源 / QG6 变更管理**：库一切变更先登 manifest，再改具体文件

## 三、三层架构模型

| 层 | 目录 | 内容 | 硬边界 |
|---|---|---|---|
| **L1 原文层** | `laws/` | 法律/法规/司法解释原文/部门规章原文（有法律效力的权威文本） | 只存原文，不含解读/案例 |
| **L2 领域解读层** | `L2-interpretation/` | 官方释义、权威实务解读、学理解释 | 须 `关联原文:` 指向 L1 |
| **L3 案例引用层** | `L3-case/` | 指导案例/公报案例/典型案例要旨与案号 | 须登记所援引的 L1 法条 |

> 用户需求 #1 明确"原文、司法解释、领域解读、案例引用"同库 → L1 含司法解释原文，L2 放解读，L3 放案例，**三层同库**（反模式：库只存原文、把解读案例甩给技能层）。

## 四、最易错的关键边界

> **技能蒸馏数据 ≠ 法规库内容。**

- 技能层（如 `law-skills` 的 A3/A9、`pm-bid` 的法规依据、各 `references/*.md`）里的是**场景化蒸馏初始数据**——独立资产，**不删、不迁、不阻塞**。
- 法规库是"权威原文/解读/案例"的**溯源层**；库未补全时蒸馏照常使用，库补全后建立"引用+溯源"正向闭环，**而非把蒸馏搬进库**。
- **不杜撰**：版本/文号/施行日期缺失一律标「待核实」；联网不可用时用"知识起草稿·待核"先行入库（frontmatter 状态=待核），官方恢复后逐条转正。

## 五、建设步骤（8 步）

1. **建目录骨架**：`README.md` / `law-manifest.md` / `laws/` / `L2-interpretation/` / `L3-case/` / `registry/reverse-registry.md` / `sources/`（不占技能编号，作 data 基础设施挂在套件下）
2. **写 README**：定位 + 文件头规范 + 更新规程六条 + 数据流图
3. **写 law-manifest.md**：已入库 / 待补 / 待核 三区，唯一盘点入口
4. **写架构与逻辑说明.md**（独立说明文件，讲"是什么/为什么"，与 README 操作手册互补）
5. **写 registry/reverse-registry.md**：蒸馏数据 → 库原文 反向登记
6. **种子入库 + 待补登记**（按 P0~P3 优先级）
7. **独立说明文档**：把结构及其逻辑单独成文放库内
8. **联网恢复后**：逐部核验转正（状态改「新鲜」、补「来源文件」）、填 reverse-registry、级联通知下游技能

## 六、文件头规范（laws/ 每个文件必带）

```yaml
---
法律名称: 中华人民共和国XX法
层级: 法律            # 法律/行政法规/司法解释/部门规章
现行版本: 2017修订
版本说明: <通过/修订会议信息，缺失标"待核实">
施行日期: 2017-12-28   # 缺失标"待核实"
快照日期: 2026-09-01   # 入库/核对日期
来源: <发布机构 + 文档形态>
来源文件: ../sources/<原件>   # 无原件标"无原件（在线来源）"
状态: 新鲜            # 新鲜/待核(180天)/待核(版本待核实)/待补
规模: 6章68条
---
```

## 七、更新规程六条

1. **仅人工触发**：不自动抓取；用户下令或 AI 检出失效时提请
2. **三粒度**：单法 / 分片（某领域）/ 全量审计（每季度）
3. **180 天阈值**：快照超 180 天 → 状态改「待核(180天)」
4. **git 一更新一 commit**：commit message 含法规名 + 版本变化，可回滚
5. **级联标记**：原文变更 → manifest 登记下游 → 技能引用处加「⚠️ 上游已更新」；反向同理
6. **优先级链**：人大网/中国政府网原文 > 官方汇编 PDF > 权威转载（frontmatter「来源」如实记级别）

## 八、双向闭环逻辑

- **正向（蒸馏引用库）**：技能引用库内 L1/L2/L3 → 标注 `来源：law-repository/<层>/<文件>(快照日期)`
- **反向（缺口登记）**：技能缺某法 → manifest「待补」登记 → 人工补库 → registry 登记引用关系 → 库更新时级联通知下游

## 九、反模式（勿犯）

- ✗ 把技能蒸馏数据搬进库（破坏初始数据独立）
- ✗ 编造文号/年份（不杜撰）
- ✗ 库只存原文、解读案例甩给技能层（与用户需求 #1 冲突）
- ✗ 联网失效就停摆——改用"知识起草稿·待核"先行入库，保框架可用

## 十、复用提示

本 SOP 可平移到其他套件建"权威数据源"：经济-suite 可比公司/估值参数库、pm-suite 招投标法规库、gridman 财税准则库等，均适用 L1/L2/L3 + 反向登记 + 蒸馏解耦模式。
