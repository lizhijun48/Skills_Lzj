# 不同文档类型的写作风格指南

不同类型的技术文档有截然不同的写作惯例。在动笔前先对号入座，选对风格。

---

## 一、招投标 / 应标技术方案

### 语气
专业稳重 + 适度的商务亮点表达。避免过度吹嘘，但可以突出技术优势和价值点。

### 典型结构（根据招标文件模板调整）
1. 项目理解与需求分析（对招标要求的理解）
2. 总体技术方案
3. 系统架构设计
4. 关键技术与创新点
5. 功能模块设计（对应招标文件的功能要求）
6. 非功能性设计（性能、安全、可用性、可扩展性）
7. 实施方案（进度、里程碑、人员）
8. 项目管理与质量保障
9. 售后服务与运维方案
10. 公司实力与成功案例（可选，有时在商务部分）

### 各类章节的要点

**需求理解**：把招标要求翻译成技术目标，**复述 + 深化**，体现对客户业务的理解深度。不要照抄招标文件。

**架构方案**：整体架构图 + 分层/分子系统说明。架构图必备，最好有两张（逻辑架构 + 部署架构）。

**关键技术**：选 3-5 个真正的技术亮点深入讲，比空泛地罗列 20 个"特性"更有说服力。

**部署方案**：环境要求、部署拓扑、实施步骤、数据迁移方案（如涉及）。

**安全方案**：等保合规（等保 2.0 三级是常见要求）、数据加密（传输+存储）、身份认证、权限控制、审计日志、数据脱敏。

**运维方案**：监控告警、日志管理、备份恢复、升级方案、容量规划。

**质量保障**：测试方案（功能/性能/安全测试）、验收标准、质保期服务、SLA 承诺。

### 语言特点
- 第一人称可用："我方"、"本方案"、"我司"、"项目组"
- 可用修饰语："领先的"、"成熟的"、"经过生产验证的"、"业界主流的" — 但要有依据
- **关键承诺要具体**：
  - 好："99.9% 年可用性"、"单节点支持 10000 TPS"、"RTO ≤ 30 分钟，RPO ≤ 5 分钟"
  - 差："高性能"、"高可用"、"稳定可靠"
- 避免"宇宙第一"、"全球唯一"这种无法证实的口号

## 二、产品设计文档 / 开发设计文档

### 语气
严谨、客观、具体。完全站在工程实现角度，给开发/测试/运维看。

### 典型结构
1. 概述（背景、目标、范围、术语表、相关文档链接）
2. 总体架构（逻辑视图、进程视图、部署视图）
3. 子系统 / 模块设计
4. 数据流设计
5. 关键业务流程
6. 数据模型（ER 图、表结构、索引策略）
7. 接口设计（内部接口 + 外部接口）
8. 非功能性设计（性能、安全、可用性、可观测性）
9. 部署架构
10. 依赖与风险

### 语言特点
- 中立第三人称，不用"我方"
- **每个设计决策写明理由**：不是"使用 Kafka"，而是"选型 Kafka 的理由：① 高吞吐 ② 已有基础设施支持 ③ 与下游消费者解耦"
- 精确：接口、参数、返回值、错误码都要具体化
- 可追溯：能关联到需求编号或使用场景
- 有争议的选择要写**权衡（Trade-off）**：比如"选 MySQL 而非 PostgreSQL，因为团队更熟悉；代价是 JSON 查询能力较弱，通过 ES 弥补"

## 三、接口文档

### 语气
极简、精确、无废话。读者是调用方开发者，只关心怎么调、返回什么。

### 每个接口的必备要素
1. 接口名称
2. URI + HTTP 方法（或 RPC 方法名）
3. 功能描述（1-2 句）
4. 鉴权方式（Token / Basic / OAuth / 免鉴权）
5. **请求参数表**（字段名 / 类型 / 必选 / 说明 / 示例）
6. **返回字段表**（字段名 / 类型 / 说明 / 示例）
7. **错误码表**（错误码 / HTTP 状态 / 含义）
8. 请求示例（curl 或 JSON）
9. 响应示例（成功 + 典型失败各一个）
10. 调用注意事项（限流、幂等性、超时、重试策略）

### 语言特点
- 字段说明短而准，一行搞定
- 枚举值必须列全
- 时间字段必须说明格式（`yyyy-MM-dd HH:mm:ss` / ISO8601 / Unix 时间戳毫秒）
- 金额必须说明单位和精度（元 / 分，保留几位小数）
- 可选参数要说明**缺省值和缺省行为**

## 四、系统架构文档

### 语气
高层、抽象、强调决策和权衡。读者是架构师、技术决策者。

### 典型结构
1. 业务背景与驱动力
2. 架构目标和非功能性要求（要量化）
3. 总体架构（分层视图 / 数据视图 / 部署视图）
4. 核心技术选型（每项带选型理由）
5. **关键架构决策记录（ADR）** — 有争议的选择单独列
6. 容量规划与性能设计
7. 可靠性与容灾设计
8. 安全架构
9. 演进路线（现状 → 目标态的分阶段路径）
10. 风险与依赖

### 语言特点
- 不陷入具体实现细节，留给设计文档
- 重视"为什么"胜过"是什么"
- 对比类表格很常用（方案 A / 方案 B / 方案 C 的优劣）

---

## 通用写作建议

### 开头段
每章/每节的开头用 1-2 句话点题，告诉读者这节要解决什么问题、讲什么。不要上来就堆细节。

### 承接
使用恰当的连接词让段落流畅："基于上述架构，……"、"为满足 XX 要求，……"、"需要注意的是，……"。

### 图文配合
- **先文字说总体，再用图细化**
- 每张图前面用一句话说明"下图展示了 XXX"
- 每张图后面用 2-3 句话解读关键点
- 图不能替代文字，也不能和文字完全重复

### 段落长度
- 招投标文档：段落可长（5-8 行）
- 设计/接口文档：段落短（2-4 行）+ 列表 + 表格，方便快速扫读

### 列表使用
- 并列项 3-7 个用有序/无序列表
- 每项尽量等长、同一层级
- 每项前面有一个小标题（加粗）+ 冒号 + 说明，读起来更清晰
