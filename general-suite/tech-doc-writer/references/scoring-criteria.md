# 技术文档评分标准

本文档供 `tech-doc-writer` skill 在评审阶段使用。两个场景：
1. **写后评分**：刚生成完一份文档，用户要求跑一次评分
2. **独立评审**：用户直接给一份已有文档要求评分，不涉及重写

## 评分标准优先级

1. **用户提供的标准优先**。如果用户给出了招标文件评分细则、公司内部评审规则、或任何自定义评分表，**完全按用户的来**，默认标准退居参考。
2. **用户没给时用默认标准**。根据文档类型自动选择对应的默认评分表（见下）。
3. **混合模式**。用户只给了部分维度的权重，剩余部分可以从默认标准里补，但要明确告诉用户"以下维度沿用默认评分"。

---

## 默认评分标准

### 一、招投标 / 应标技术方案（100 分制）

| 维度 | 权重 | 评分要点 |
|------|:----:|---------|
| 需求响应度 | 20 | 是否逐条响应招标技术要求；理解深度是否到位；有无偏题 |
| 技术方案深度 | 25 | 方案是否具体可落地；关键技术有实质论述而非空洞口号；有技术支撑 |
| 架构与设计 | 15 | 架构图清晰合理；分层/分模块得当；关键设计决策有说明 |
| 实施与交付 | 15 | 进度计划合理；里程碑明确；人员配置、培训、数据迁移完整 |
| 非功能性 | 10 | 性能、安全（等保合规）、可用性、可扩展性均覆盖且量化 |
| 规范与可读 | 10 | 结构清晰；术语一致；图文匹配；排版规范；无错别字 |
| 创新亮点 | 5 | 有能让评审印象深刻的差异化亮点（3-5 个足够，别堆砌）|

### 二、产品设计 / 开发设计文档（100 分制）

| 维度 | 权重 | 评分要点 |
|------|:----:|---------|
| 结构完整性 | 15 | 背景、目标、范围、术语表、相关文档链接齐全 |
| 架构清晰度 | 20 | 有逻辑视图、部署视图、数据视图；图与文对应 |
| 设计可追溯 | 20 | **每个关键设计决策都写明理由**；选型有权衡对比 |
| 数据与接口 | 20 | ER 图 / 表结构 / 接口定义完整；字段说明精确 |
| 非功能性 | 10 | 性能、安全、可观测性、容灾覆盖到 |
| 规范术语 | 10 | 术语一致、格式规范 |
| 风险依赖 | 5 | 明确列出依赖、风险、缓解措施 |

### 三、接口文档（100 分制）

| 维度 | 权重 | 评分要点 |
|------|:----:|---------|
| 接口清单完整 | 20 | 所有接口都有；分组清晰 |
| 字段完整 | 40 | 请求参数 / 返回字段 / 错误码齐全；类型 / 必选 / 枚举 / 示例都有 |
| 示例完整 | 15 | 请求示例、成功响应、典型失败响应 |
| 鉴权限流 | 10 | 鉴权方式明确；限流策略有说明 |
| 使用约定 | 5 | 幂等性、超时、重试策略 |
| 规范性 | 10 | 命名规范；时间/金额格式统一 |

### 四、系统架构文档（100 分制）

| 维度 | 权重 | 评分要点 |
|------|:----:|---------|
| 业务背景 | 10 | 驱动力、目标、约束清晰 |
| 架构目标 | 10 | 非功能性要求**量化**（而非"高性能高可用"这种口号）|
| 分层视图 | 15 | 架构图清晰；各层职责边界明确 |
| 技术选型 | 20 | **每项选型有理由、有替代方案对比** |
| 关键决策 | 15 | 有 ADR（架构决策记录）或等价的决策说明 |
| 容量性能 | 10 | 容量规划、性能模型、瓶颈分析 |
| 可靠容灾 | 10 | 故障域划分、容灾方案、RTO/RPO 目标 |
| 安全架构 | 5 | 身份、权限、加密、审计 |
| 演进路线 | 5 | 现状 → 目标的分阶段路径 |

## 通用扣分项（所有文档类型适用）

这些扣分项**独立于维度打分之外**叠加，防止分数虚高。

| 扣分项 | 扣分幅度 | 说明 |
|--------|:--------:|------|
| 🔴 **编造具体数据** | -5 ~ -10 / 处 | 具体接口参数、表字段、版本号、性能数字无原始材料支撑。这是底线问题。 |
| 🔴 **严重偏题或缺章** | -10 ~ -15 | 大纲要求的章节缺失或内容与标题严重不符 |
| 🟡 术语不一致 | -1 / 处 | 同一对象在文档中用不同名称（如"审计引擎" vs "审计组件"），累计封顶 -5 |
| 🟡 图文不匹配 | -2 ~ -5 / 处 | 图与文字描述矛盾；或应有图而无图 |
| 🟡 未标注的推断内容 | -3 ~ -5 / 处 | 基于通用知识补写的内容未用注释标出，让用户无法分辨 |
| 🟢 格式问题 | 累计 -3 | 标题层级错乱、表格格式不一致、中英文混排无空格等 |
| 🟢 空泛口号 | -3 ~ -5 / 节 | "领先"、"高性能"、"稳定可靠"这类无数据支撑的表述出现过多 |
| 🟢 篇幅失衡 | -3 ~ -8 | 关键章节过短（如整章仅两段），或非关键章节过度堆砌 |
| 🟢 错别字 | -0.5 / 处 | 累计封顶 -5 |

## 评分流程

1. **读文档**
   - md 直接 `view`
   - docx / pdf / xlsx / pptx 优先用对应 skill（见 `file-reading.md`）
2. **读评分标准**
   - 用户提供：直接用
   - 用户未提供：识别文档类型后用对应默认标准
3. **识别文档类型**（如果不明确，询问用户一次）
4. **逐维度打分**
   - 对每个维度，扫描文档相关部分，给出得分和失分依据
   - 记录过程中发现的具体问题（供详细审阅部分使用）
5. **计算通用扣分项**
   - 全文扫一遍通用扣分项，记录每一处
6. **生成报告**
   - 总览评分表 + 详细审阅
   - 保存为独立 md 文件
7. **交付**
   - 使用 `present_files` 交付 review 文件
   - 在对话中给一个 3-5 行的摘要（总分 / 高优先级问题数 / 建议下一步）

## 二、详细审阅

按章节或按维度组织。每个问题条目格式：

### 🔴 [问题编号] 简述

- **定位**：<章节号 + 章节标题>
- **原文摘录**：<最多 30 字，用引用块>
- **问题**：<具体问题描述>
- **建议**：<可执行的修改建议，最好给出改法示例>

---

### 2.3 性能指标

#### 🔴 [P01] 性能承诺无具体数值

- **定位**：第 2 章第 3 节「性能指标」
- **原文摘录**：> 系统性能优异，支持高并发访问。
- **问题**：仅有定性描述，未给出具体 TPS、响应时间等数值，招标文件 §3.2 明确要求"单节点 TPS ≥ 1000"必须响应。
- **建议**：改写为"系统单节点支持 ≥ 1500 TPS（高于招标要求 50%），在 8 核 16G 规格下经 JMeter 实测，P99 响应时间 ≤ 250ms，详见附录 A 性能测试报告"。若无实测数据，至少引用参考文档中审计引擎的基准性能。

#### 🟡 [P02] ...

## 三、改进优先级建议

如果时间有限，按以下顺序改：

1. **先改 🔴 项**：X 项，预计影响总分 +N
2. **再改 🟡 项中高频问题**：如术语不一致、图文不匹配这类系统性问题
3. **最后处理 🟢 项**：排版、错别字等

## 内联自检格式

写文档过程中，每完成一节 Claude 做一个快速自检。发现问题时用 HTML 注释标注在对应位置（Markdown 渲染时不可见，但打开源文件一眼可见）：

```markdown
## 2.3 性能指标

系统单节点支持 ≥ 1500 TPS……

<!-- 🔍 自检: 此处 1500 TPS 数字来源于通用推断，参考文档中未找到具体性能数据，请核实或替换 -->
```

自检标注使用的 emoji 约定：
- `<!-- 🔍 自检: ... -->` — 发现可能的问题
- `<!-- ⚠️ 基于通用知识补充: ... -->` — 标注推断性内容（在第 5 步缺失处理里已经约定）
- `<!-- ❓ 待用户确认: ... -->` — 需要用户决定的分歧点

写作时默认**关闭内联自检**以保持正文干净；用户明确要求时开启（如"每节加自检标注"、"写完能自己查一遍"）。

## 常见问题

**Q: 评分时发现文档有严重编造（违反底线），怎么处理？**
A: 在详细审阅里单列"底线问题"红牌章节，并在对话中主动向用户强调。不建议在总分上简单扣几分了事。

**Q: 用户给的评分细则和默认标准冲突？**
A: 无条件按用户的来。但可以在报告的"附录：评分方法说明"里提一句"本次未评审 XXX 维度（用户标准未涵盖），如需可补充"。

**Q: 文档还没写完就让评分？**
A: 可以评，但在报告开头注明"**部分评审**"，并列出尚未完成的章节，对应维度打分时注明"待完成后复评"。

**Q: 同一份文档多次评分会不会分数漂移？**
A: 会有一定浮动，但应控制在 ±5 分以内。如果漂移大，检查是否评分标准理解有偏差。可以在报告里保留关键判据，便于复盘。
