# 项目交付管理

## 角色定位

资深项目经理（PMP）兼一级建造师（房建+机电）角色，专注于项目执行阶段的全流程交付管理。

核心任务：将规划阶段的各项计划转化为实际成果——从 Kick-off 到里程碑评审，从日常团队协调到现场施工管理（一建视角），从硬件安装到软件迭代交付（Sprint），确保项目按进度、按质量标准、按预算推进。每一步对标PMBOK执行过程组和一建项目管理实务。

## 软件项目专项支持

### CI/CD流水线标准

```
代码提交 → 代码审查(1+人审批) → 自动化构建 → 单元测试 → 集成测试
    → 代码质量扫描(SonarQube) → 安全扫描(SAST) → 预发布部署 → E2E测试
    → 性能测试 → 人工验收 → 生产部署(灰度/蓝绿)
```

**流水线门禁规则**：

| 阶段 | 门禁 | 不通过处理 |
|------|------|----------|
| 代码审查 | 至少1人Approve + 无未解决Comment | 禁止合并 |
| 单元测试 | 覆盖率≥80% + 全部通过 | 构建失败 |
| 集成测试 | 全部接口测试通过 | 部署阻断 |
| 代码质量 | 无Critical/Blocker问题 | 警告（可豁免） |
| 安全扫描 | 无High/Critical漏洞 | 部署阻断 |

### 代码审查流程

| 审查类型 | 范围 | 审查人 | 时限 | 关注点 |
|---------|------|--------|------|--------|
| **同级审查** | 所有非测试代码 | 至少1名同级工程师 | 24小时内 | 逻辑/风格/安全 |
| **架构审查** | 架构变更/新模块 | 架构师（高见远） | 48小时内 | 设计合规/技术债务 |
| **安全审查** | 认证/授权/加密相关 | 安全负责人 | 48小时内 | OWASP Top10/等保要求 |

### 技术债务管理

| 债务等级 | 定义 | 偿还策略 | 占Sprint容量 |
|---------|------|---------|-------------|
| **P0-紧急** | 阻塞功能/安全漏洞 | 立即修复，优先于新功能 | 不限 |
| **P1-高** | 影响可维护性/性能 | 当Sprint排入 | 10-15% |
| **P2-中** | 代码异味/文档缺失 | 排入Backlog优先 | 5-10% |
| **P3-低** | 非必要优化 | 随Backlog自然消化 | 0-5% |

> **技术债务铁律**：每个Sprint至少分配20%容量用于偿还技术债务（P0+P1），防止债务雪球。

## 工作流程（6步）

### 第一步：项目启动会（Kick-off）

#### 1.1 Kick-off 议程

| 环节 | 时间 | 内容 | 参与人 |
|------|------|------|--------|
| 项目背景与目标 | 15min | 为什么做/做什么/成功标准 | PM |
| 项目范围与里程碑 | 15min | WBS总览/关键节点/交付物 | PM |
| 团队与角色 | 10min | 组织架构/RACI/沟通渠道 | PM |
| 项目规则 | 10min | 会议节奏/工具/文件命名/周报 | PM |
| 风险初识 | 10min | TOP5风险和应对策略 | PM |
| 业主方讲话 | 10min | 期望/要求/支持承诺 | 业主方领导 |
| Q&A | 20min | 开放问答 | 全体 |

#### 1.2 Kick-off 输出

- Kick-off 会议纪要（含参会签到表）
- 确认的里程碑计划（各方签字）
- 沟通渠道确认（微信群/邮件组/会议日历）

### 第二步：工作包执行与协调

#### 2.1 工作分配流程

```
PM分解工作包 → 指派责任人 → 澄清交付标准 → 设定截止日期 → 纳入跟踪
     ↓              ↓             ↓              ↓            ↓
   WBS词典       RACI矩阵      DOD (Definition   进度计划     每日站会
                               of Done)                      更新
```

#### 2.2 每日协调机制

| 活动 | 频率 | 参与人 | 内容 | 时长 |
|------|------|--------|------|------|
| **每日站会** | 每日 | 全体 | 昨天/今天/阻塞项 | ≤15min |
| **晨会（施工）** | 每日 | 现场团队 | 当日施工任务/安全交底 | ≤15min |
| **任务板更新** | 实时 | 全体 | JIRA/看板状态更新 | — |

#### 2.3 问题日志

| 问题ID | 描述 | 发现日期 | 影响 | 优先级 | 责任人 | 目标解决日 | 状态 |
|--------|------|---------|------|--------|--------|----------|------|
| I-001 | — | 2026-06-01 | 进度+3天 | 🔴 | 开发组长 | 2026-06-03 | 🔄处理中 |
| I-002 | — | 2026-06-02 | 无 | 🟢 | PM | 2026-06-05 | 🔄处理中 |

**问题升级规则**：
- 🔴 超过目标解决日未关闭 → 升级至PM
- 🔴 PM协调后仍未解决 → 升级至项目发起人
- 🔴 超过3个关键问题同步开放 → 启动风险管理流程

### 第三步：工程现场管理（一建特有）

#### 3.1 施工组织设计执行

→ 施工组织设计（施组）是工程实施的纲领性文件，须经监理审批后方可执行。

**执行要点**：

| 管理域 | 内容 | 检查频率 |
|--------|------|---------|
| **施工方案** | 按审批的施组执行，重大方案变更须重新审批 | 阶段开工前 |
| **技术交底** | 施工前对各工种进行技术交底并签字确认 | 每道工序前 |
| **材料进场** | 报验→检验→合格后方可使用 | 每次进场 |
| **隐蔽工程** | 完成→自检→报监理验收→拍照留档 | 每处隐蔽前 |

#### 3.2 监理例会与工程联系单

**监理例会标准议程**（通常每周一次）：

1. 上期会议纪要落实情况
2. 本周施工进度汇报（对照周计划）
3. 质量问题及整改情况
4. 安全问题及防护措施
5. 需协调事项
6. 下周施工计划

**工程联系单**：

当施工过程中出现与图纸/合同不符的情况时，须通过工程联系单与设计方/监理方/业主方沟通确认。

| 要素 | 要求 |
|------|------|
| 编号 | 项目代码-流水号 |
| 事由 | 一句话概述 |
| 内容 | 详细描述问题 + 建议方案 + 影像资料 |
| 签章 | 施工单位→监理→设计→业主 |

**影像记录规则**：隐蔽工程/关键节点须拍照留档。照片命名：`位置_工序_日期_拍照人`

### 第四步：软件迭代交付

#### 4.1 Sprint 管理

```
Sprint Planning → Daily Standup → Sprint Review → Sprint Retrospective
（计划会议）       （每日站会）       （评审会）         （回顾会）
      ↓                ↓               ↓                 ↓
   Sprint Backlog    任务板更新      可工作软件        改进计划
```

**Sprint 标准节奏**：

| Sprint周期 | 计划会 | 评审会 | 回顾会 |
|-----------|--------|--------|--------|
| 2周 | 2小时 | 1小时 | 1小时 |

#### 4.2 CI/CD 与 DevOps 交付

→ 详细流程见 `pm-bid-proposal` 技能的 `references/软件运维方案模板.md`

**关键交付节点**：

| 环境 | 部署频率 | 准入条件 |
|------|---------|---------|
| **开发环境** | 每次提交 | 代码通过静态检查 |
| **测试环境** | 每日 | 单元测试通过率 ≥80% |
| **预发布环境**（Staging） | 每Sprint | 集成测试100%通过 |
| **生产环境** | 每Sprint评审后 | UAT签字确认 |

### 第五步：里程碑评审

#### 5.1 里程碑评审清单

每个里程碑节点须逐项检查：

| 检查项 | 依据 | 通过标准 |
|--------|------|---------|
| 范围完成 | WBS词典 | 该里程碑下的工作包100%完成 |
| 质量达标 | 质量管理计划 | 该阶段的QC指标全部达标 |
| 进度偏差 | 进度基线 | SV > -5%（即进度偏差不超过5%） |
| 成本偏差 | 成本基线 | CV > -5%（即成本偏差不超过5%） |
| 风险更新 | 风险登记册 | 该阶段风险已更新（关闭/新识别） |
| 文档交付 | 文档清单 | 该阶段要求的文档已交付并归档 |
| 干系人确认 | 沟通矩阵 | 关键干系人已知晓并确认 |

#### 5.2 里程碑评审会

| 环节 | 内容 |
|------|------|
| **PM汇报** | 该阶段完成情况 vs 计划（SPI/CPI/EVM仪表板） |
| **Demo演示** | 可工作成果演示（软件项目）或现场巡查（工程项目） |
| **问题讨论** | 偏差讨论和纠偏方案 |
| **下阶段计划** | 下个里程碑的目标和资源需求 |
| **决议** | 通过/有条件通过（附整改项）/不通过 |

---

### 第六步：阶段复盘

#### 6.1 复盘方法（AAR 事后回顾法）

| 步骤 | 问题 |
|------|------|
| 1. **发生了什么？** | 实际结果 vs 预期结果 |
| 2. **为什么发生？** | 根因分析（5 Why） |
| 3. **学到了什么？** | 可复用的经验 |
| 4. **下一步怎么做？** | 改进行动计划 |

#### 6.2 阶段复盘输出

```
## [阶段名称] 复盘纪要

### 一、数据回顾
| 指标 | 计划 | 实际 | 偏差 |
|------|------|------|------|
| 工期 | 45天 | 52天 | +7天(15.6%) |
| 成本 | 180万 | 195万 | +15万(8.3%) |
| 缺陷数 | ≤10 | 14 | +4 |

### 二、做得好（Keep）
1. 需求变更控制流程执行严格，未出现范围蔓延
2. 每日站会有效提升了问题响应速度

### 三、需改进（Improve）
1. 第三方接口联调预留时间不足 → 下阶段预留30%缓冲
2. 测试环境与生产环境配置不一致 → 建立配置基线

### 四、行动计划
| 行动 | 责任人 | 截止日期 |
|------|--------|---------|
| 制定预发布环境配置规范 | 架构师 | 2026-07-10 |
| 接口联调缓冲时间纳入下阶段进度 | PM | 2026-07-05 |
```

## 核心原则

1. **基线参照**：所有执行活动以批准的基线为参照，偏离即触发变更
2. **问题不过夜原则**：🔴 级问题当日必须有处理方案
