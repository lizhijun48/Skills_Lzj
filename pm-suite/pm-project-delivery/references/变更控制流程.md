# 变更控制流程

> 本文件为 `pm-project-delivery` 的参考资源，详细说明项目执行中的变更控制流程、表单模板和实操要点，帮助项目经理建立规范的变更管理机制。

---

## 一、变更控制的核心原则

| 原则 | 说明 |
|------|------|
| **书面化** | 所有变更必须书面提出，拒绝口头变更 |
| **先评估后决策** | 不评估影响不审批变更 |
| **基线锁定** | 变更批准后才更新基线，未批准前按原基线执行 |
| **可追溯** | 每个变更编号归档，关联工作包和影响分析 |
| **分级审批** | 按影响范围分级，避免小事大审、大事漏审 |

---

## 二、变更控制流程详解

### 2.1 流程总览

```
变更请求 ──→ 变更登记 ──→ 影响分析 ──→ 变更评审 ──→ 实施/拒绝
              │            │            │
              │            │            ├── 批准 → 更新基线 → 实施 → 验证
              │            │            ├── 有条件批准 → 修改后重新评审
              │            │            └── 拒绝 → 通知干系人 → 归档
              │            │
              │            └── 紧急变更（跳过评审）
              │                 → 事后补评审 → 更新基线
              │
              └── 重复/无效变更 → 直接关闭并归档
```

### 2.2 各步骤详解

#### 步骤1：变更请求提出

```
变更请求须包含：
1. 变更描述：要变什么？为什么变？
2. 变更来源：客户/内部/外部/法规
3. 紧急程度：紧急/一般
4. 期望完成时间：____
5. 提出人：____
```

**变更请求表模板**：

| 字段 | 内容 |
|------|------|
| 变更编号 | CR-YYYY-NNN |
| 提出日期 | ____年__月__日 |
| 提出人 | ____ |
| 变更来源 | □客户需求 □技术调整 □法规变化 □范围蔓延 □纠偏 |
| 变更描述 | ____ |
| 变更理由 | ____ |
| 紧急程度 | □紧急 □一般 |
| 期望完成时间 | ____ |

#### 步骤2：变更登记

```
1. 分配变更编号（CR-2026-001格式）
2. 录入变更登记册
3. 指定变更评估负责人
4. 设定评估完成时限
```

#### 步骤3：影响分析（关键步骤）

**必须评估5个维度**：

| 维度 | 分析内容 | 输出 |
|------|---------|------|
| 范围影响 | 新增/修改/删除哪些工作包？ | 范围变更清单 |
| 成本影响 | 增加多少成本？（人力+材料+管理） | 成本影响估算 |
| 进度影响 | 延长多少工期？影响哪些里程碑？ | 进度影响估算 |
| 质量影响 | 是否影响已有交付物的质量？ | 质量影响评估 |
| 风险影响 | 引入新风险？改变已有风险概率/影响？ | 风险影响评估 |

**影响分析表模板**：

| 维度 | 变更前 | 变更后 | 偏差 | 应对措施 |
|------|--------|--------|------|---------|
| 范围 | | | ±__% | |
| 成本 | | | ±__万元 | |
| 工期 | | | ±__天 | |
| 质量 | | | 影响/不影响 | |
| 风险 | | | 新增/无变化 | |

#### 步骤4：变更评审（CCB）

```
CCB（Change Control Board）组成：
- 我方：项目经理 + 技术负责人 + 商务负责人
- 客户：项目负责人（重大变更须参与评审）
- 其他：监理/第三方（如适用）

评审内容：
1. 变更必要性：不变会怎样？变了有什么收益？
2. 影响可接受性：5维度影响是否在可接受范围？
3. 替代方案：有没有更轻量的方案达到同样目的？
4. 实施可行性：资源是否到位？时间是否允许？

评审结论：
□ 批准 → 更新基线 → 实施
□ 有条件批准 → 修改变更方案后重新评审
□ 搁置 → 补充信息后重新评审
□ 拒绝 → 通知干系人 → 归档
```

#### 步骤5：变更实施与验证

```
1. 更新项目基线（范围/成本/进度）
2. 更新风险登记册
3. 通知所有受影响的干系人
4. 实施变更
5. 验证变更效果（是否达到预期？是否引入新问题？）
6. 更新变更登记册（标记完成）
```

## 三、变更分级标准

### 3.1 分级矩阵

| 级别 | 范围偏差 | 成本偏差 | 工期偏差 | 审批权限 |
|------|---------|---------|---------|---------|
| **重大变更** | >15% | >10% | >15% | 客户+公司管理层双批 |
| **一般变更** | 5%-15% | 5%-10% | 5%-15% | 客户PM+我方PM双批 |
| **微小变更** | <5% | <5% | <5% | 我方PM单批 |

### 3.2 一票升级项

以下情况，无论偏差大小，均升级为**重大变更**：
- 涉及合同核心条款变更
- 涉及安全/合规风险
- 涉及知识产权/数据归属
- 客户组织架构变化导致需求变化

## 四、特殊变更处理

### 4.1 紧急变更

```
适用场景：
- 系统故障影响业务运行
- 安全漏洞需紧急修复
- 法规要求立即调整

流程：
1. 项目经理可先行实施
2. 24小时内补提变更请求
3. 48小时内补办评审
4. 更新基线和文档

注意：
- 紧急变更≠随意变更
- 事后补评审时若被否决，须回退变更
- 紧急变更次数纳入项目考核
```

### 4.2 范围蔓延防范

```
范围蔓延的典型信号：
1. 客户说"顺便帮我们做一个XXX"（"顺便"=免费）
2. 客户说"这个很简单，加一下就行"（"很简单"=不加钱）
3. 客户说"上次开会不是说了吗"（口头约定≠书面变更）
4. 需求文档以外的功能出现在测试用例中

应对话术：
1. "这个需求我们可以支持，我来做影响分析，评估一下成本和工期影响"
2. "口头约定我记下来了，我出个变更请求，正式走个流程"
3. "我们先把合同范围内的工作做好，额外需求我们单独评估"
4. "这个功能不在当前SOW范围内，建议作为二期需求"

关键原则：永远不说"不行"，只说"走流程"
```

### 4.3 客户驱动的变更 vs 内部变更

| 对比项 | 客户驱动变更 | 内部变更 |
|--------|------------|---------|
| 提出方 | 客户 | 我方团队 |
| 成本承担 | 客户承担（或协商） | 我方承担 |
| 工期影响 | 可申请延期 | 不可申请延期 |
| 审批流程 | 须客户审批 | 内部CCB审批即可 |
| 合同影响 | 可能需签补充协议 | 不影响合同 |

## 六、变更管理常见误区

| 误区 | 正确做法 |
|------|---------|
| "变更太多，走流程太慢" | 简化流程≠跳过流程，微小变更3天内处理 |
| "客户是甲方，说什么就是什么" | 专业地引导客户走流程，保护双方利益 |
| "小变更不影响大局" | 小变更积累=范围蔓延，每个变更都须登记 |
| "变更审批太严，客户不满意" | 规范流程≠拖延，快速响应+专业评估=客户满意 |
| "项目经理可以自行决定所有变更" | 重大变更须升级审批，项目经理无权单独决定 |
| "紧急变更可以不走流程" | 紧急变更先实施后补流程，但必须补 |
