# 项目收尾与知识沉淀

## 角色定位

资深项目经理（PMP）角色，专注于政府/国企项目的收尾管理。

核心任务：在获得验收批文后，系统化完成项目收尾——关闭合同、释放资源、归档文档、转移资产、沉淀经验教训、组织团队解散与表彰、完成运维交接。每一步对标PMBOK收尾过程组和软考高项收尾管理，同时兼顾政府项目特有的质保期管理、尾款支付和审计配合。

|---------|------|------------|
| 验收批文 | `pm-gov-acceptance` | 收尾的合法前提（无批文不收尾） |

## 软件项目专项支持

### 代码仓库归档标准

| 归档项 | 要求 | 验证方式 |
|--------|------|---------|
| **源代码** | 含完整提交历史，所有分支已合并或标注 | 可独立构建 |
| **构建脚本** | `build from source` 可在全新环境下成功构建 | 空环境构建测试 |
| **依赖清单** | lockfile/poetry.lock/yarn.lock 已锁定 | 依赖安装无报错 |
| **环境配置** | 环境变量模板+配置文件示例 | 文档可操作 |
| **数据库脚本** | DDL+初始数据+迁移脚本 | 空库可初始化 |
| **CI/CD配置** | 流水线定义文件（.gitlab-ci.yml/Jenkinsfile等） | 可触发构建 |
| **标签/版本** | 每个正式发布版本有Git Tag | Tag与发布记录对应 |

### API文档标准

| 文档类型 | 格式 | 覆盖范围 | 维护要求 |
|---------|------|---------|---------|
| **接口文档** | OpenAPI 3.0 / Swagger | 100%接口 | 与代码同步更新 |
| **数据模型** | ER图 + JSON Schema | 全部数据实体 | 含字段说明+枚举值 |
| **认证授权** | 独立章节 | 全部认证方式 | 含Token刷新/过期处理 |
| **错误码** | 错误码表 | 全部业务错误码 | 含错误描述+处理建议 |
| **变更日志** | Changelog | 每版本变更 | 含Breaking Change标注 |

### 运维手册标准结构

```
1. 系统概述（架构图+部署拓扑+技术栈）
2. 日常运维
   ├── 健康检查项（每日/每周/每月）
   ├── 日志查看与归档
   ├── 数据备份与恢复
   └── 证书/密钥轮换
3. 故障排查
   ├── 常见故障与处理（按模块/按症状）
   ├── 监控告警响应（告警等级+处理流程）
   └── 升级路径（运维→二线→三线→厂商）
4. 性能调优
   ├── 性能基线（响应时间/并发数/资源占用）
   ├── 调优参数与建议值
   └── 容量规划参考
5. 安全运维
   ├── 等保合规检查项
   ├── 漏洞修复流程
   └── 安全审计配合
6. 应急预案
   ├── 核心服务不可用
   ├── 数据泄露/误删
   └── 灾难恢复（RTO/RPO目标）
```

## 工作流程（7步）

### 第一步：合同关闭

#### 1.1 合同关闭检查清单

| 检查项 | 完成标准 | 状态 |
|--------|---------|------|
| 全部交付物已验收 | 有验收签字记录 | ☐ |
| 全部付款已完成 | 最后一笔尾款已支付 | ☐ |
| 质保期条款已生效 | 质保起止日期明确，质保金已预留 | ☐ |
| 变更/索赔已处理完毕 | 所有CR已关闭，索赔已和解 | ☐ |
| 合同文档已完整 | 合同+变更+往来函件+索赔记录 | ☐ |
| 供应商绩效评价已完成 | 评价表已归档 | ☐ |

**政府项目尾款管理**：
- 质保金比例通常为合同额的 3-5%
- 质保期通常为 1-3 年（大型信息化项目：软件1年/硬件3年）
- 质保期满后凭业主方出具的质量合格证明方可支取质保金

---

### 第二步：资源释放

#### 2.1 人力资源释放

| 步骤 | 操作 |
|------|------|
| 1. 绩效评估 | 完成团队成员的项目绩效评估 |
| 2. 表彰推荐 | 优秀成员推荐表彰（书面材料） |
| 3. 离职面谈（项目） | PM与每位成员10分钟一对一 |
| 4. 释放通知 | 正式通知职能部门：该成员可从本项目释放 |
| 5. 感谢信 | 向每位成员及其部门领导发送感谢信 |

#### 2.2 物力资源处理

| 资源类型 | 处理方式 |
|---------|---------|
| **自有设备** | 归还公司资产管理部门 |
| **租赁设备** | 按租赁合同归还 |
| **剩余材料** | 移交业主方（政府项目惯例） |
| **开发/测试环境** | 不立即释放，保留至运维过渡期满 |

---

### 第三步：文档归档

#### 3.1 归档清单

| 类别 | 包含文件 | 保管期限 |
|------|---------|---------|
| **立项文件** | 建议书/可研/初设批复 | 永久 |
| **合同文件** | 合同+补充协议+变更 | 合同期满后15年 |
| **管理文件** | 周报/月报/会议纪要/变更记录 | 项目结束后10年 |
| **技术文件** | 设计文档/技术方案/测试报告/竣工图 | 项目结束后15年 |
| **验收文件** | 验收申请/验收报告/验收批文 | 永久 |
| **财务文件** | 决算报告/付款凭证/审计报告 | 项目结束后15年 |
| **人事文件** | 团队绩效/表彰记录 | 项目结束后5年 |

#### 3.2 移交内容

| 移交对象 | 移交内容 |
|---------|---------|
| **业主方** | 全套竣工图/操作手册/维护手册/培训资料/账号密码清单 |
| **运维团队** | 系统架构/部署文档/应急预案/监控配置/供应商联系方式 |
| **公司档案室** | 全套纸质档案 + 电子档案（移动硬盘） |

**移交确认**：每个移交接收方须签署《文档移交确认单》

### 第四步：经验教训沉淀

#### 4.1 Lessons Learned 结构

```
## XX项目 经验教训登记册

### 一、项目关键数据
| 指标 | 计划 | 实际 | 偏差 |
|------|------|------|------|
| 总工期 | 14个月 | 15.3个月 | +1.3月(9.3%) |
| 总投资 | 2100万 | 2156万 | +56万(2.7%) |
| 团队规模 | 12人 | 14人（高峰期） | — |
| 变更数量 | — | 23个 | — |

### 二、做得好的（可复制）
1. [经验1]：XXX → 推荐在后续项目中继续使用
2. [经验2]：XXX

### 三、做得不够好的（需改进）
1. [教训1]：第三方接口联调预留时间不足 → 建议后续项目预留30%缓冲
2. [教训2]：等保测评启动过晚 → 建议在开发中期启动差距分析

### 四、"如果重来我会…"
1. "如果重来我会在项目启动时就建立等保合规跟踪表。" — PM
2. "如果重来我会要求架构师在技术选型阶段就审核开源许可证。" — 架构师

### 五、可复用的模板/工具
1. [模板/工具名称]：描述 + 存放路径
```

#### 4.2 经验教训分类

| 类别 | 示例 |
|------|------|
| **进度管理** | 第三方依赖的缓冲时间准则 |
| **成本管理** | 软件成本估算的校准系数 |
| **质量管理** | 等保合规的启动时机 |
| **沟通管理** | 政府项目汇报的最佳频率 |

| **采购管理** | 供应商评估的实际表现回溯 |

### 第五步：运维交接

#### 5.1 运维过渡期

| 阶段 | 内容 | 时间 |
|------|------|------|
| **并行期** | 我方运维 + 业主运维并行 | 1-3个月 |
| **过渡期** | 逐步减少我方参与，业主运维独立运作 | 第2-4个月 |
| **独立期** | 业主运维完全独立，我方仅提供质保支持 | 质保期内 |

#### 5.2 运维交接清单

→ 详细运维交接模板见 `pm-bid-proposal` 技能的 `references/软件运维方案模板.md`

|--------|------|----------|
| 系统架构文档 | 部署拓扑/网络配置/数据架构 | ☐ |
| 部署手册 | 安装步骤/环境依赖/配置清单 | ☐ |
| 运维手册 | 日常巡检/备份策略/监控告警/应急处理 | ☐ |
| 账号密码 | 管理员/服务/数据库账号 | ☐ |
| 监控平台 | 监控仪表板权限/告警规则/通知渠道 | ☐ |
| 供应商联系表 | 硬件/软件/云服务供应商及联系方式 | ☐ |
| 应急预案 | 常见故障的应急处理SOP | ☐ |
| 知识库 | FAQ/历史故障处理记录 | ☐ |

#### 5.3 运维培训

| 培训内容 | 对象 | 形式 | 课时 |
|---------|------|------|------|

| 日常运维与巡检 | 运维工程师 | 实操 | 1天 |
| 故障诊断与应急 | 运维工程师 | 演练 | 0.5天 |
| 用户操作 | 业务人员 | 课堂 | 1天 |
| 后台管理 | 管理员 | 课堂+实操 | 1天 |

### 第六步：团队解散与表彰

#### 6.1 团队解散流程

1. **回顾会**：全员参与的项目回顾会（非形式化）
2. **绩效反馈**：PM 向每位成员提供项目绩效反馈
3. **推荐函**：为表现突出的成员起草推荐函
4. **告别活动**：团队散伙饭/团建（可选）
5. **正式解散**：PM 发出项目团队解散通知

#### 6.2 项目庆功

| 活动 | 目的 | 形式 |
|------|------|------|
| **项目回顾会** | 总结经验教训 | 半天工作坊 |
| **成果展示会** | 向公司展示项目成果 | 1小时分享会 |
| **表彰仪式** | 认可团队贡献 | 公司级别表彰 |

---

### 第七步：项目后评价（政府项目可选）

政府投资项目在投入运行1-2年后，主管部门可能组织项目后评价：

| 评价维度 | 内容 |
|---------|------|
| **目标实现度** | 项目建设目标是否实现？ |
| **效益实现度** | 预期的经济/社会效益是否达成？ |
| **可持续性** | 项目成果是否可持续运行？ |
| **经验总结** | 有哪些可推广的经验？ |

## 使用示例

```
输入：某市智慧管廊项目已完成竣工验收，获得验收批文。
     合同额2100万，实际支出2156万，质保期3年(软件1年)。
```

## 核心原则

1. **无批文不收尾**：验收批文是收尾的法定前提
2. **合同关闭不留尾巴**：所有合同条款须逐项核对关闭
3. **文档必须归档**：做过的项目必须留下可追溯的记录
4. **经验教训必须写**：每个项目至少产出5条可复用的经验教训
5. **运维交接要过渡**：不可"一扔了之"，须经过并行期+过渡期
6. **团队解散要体面**：感谢信+绩效反馈+推荐函是PM的基本责任
7. **质保金跟踪到到期**：质保期内定期回访，期满及时申请质保金
8. **收尾不是结束**：项目后评价是检验项目长期价值的最终关口
9. **代码即文档**：软件项目收尾时，代码仓库+API文档+运维手册构成最小可维护交付物，缺一不可
