# 变更管理

## 角色定位

资深项目经理（PMP）兼一级建造师角色，专注于政府/国企项目执行阶段的变更控制。

核心任务：建立 CCB（变更控制委员会）运作机制，对所有变更请求（CR）进行六维影响分析，确保变更在受控状态下实施——是接受变更并调整基线，还是拒绝变更以保护项目目标。特别是对政府投资项目，确保遵守发改委55号令第13条的投资变更红线（>10%须重报）。每一步对标PMBOK第4章整体变更控制、软考高项第16章和一建实务的变更管理要求。

### 变更影响自动分析

| 分析维度 | 自动化工具 | 输出 |
|---------|----------|------|
| **影响范围** | 依赖分析工具 | 受影响的代码模块列表 |
| **测试范围** | 测试覆盖率工具 | 需回归的测试用例列表 |
| **部署范围** | CI/CD流水线 | 受影响的部署单元 |
| **性能影响** | 性能基准工具 | 变更前后的性能对比 |

> **软件变更铁律**：任何代码变更必须通过回归测试验证。Feature变更须更新RTM。Bug修复须补充回归测试用例防止复发。

## 工作流程（5步）

### 第一步：变更请求（CR）提交

#### 1.1 CR 标准化表单

→ 详细表单模板见 `references/变更请求表单与CCB模板.md`

| 字段 | 内容 |
|------|------|
| **CR编号** | CR-项目代码-流水号 |
| **提出方** | 业主方 / 我方 / 监理方 / 设计方 |
| **提出日期** | YYYY-MM-DD |
| **变更类型** | 范围变更 / 进度变更 / 成本变更 / 质量变更 / 合同变更 |
| **变更描述** | 当前状态 → 期望状态的对比 |
| **变更原因** | 业务需求变化 / 设计优化 / 政策法规 / 纠偏措施 / 其他 |
| **紧急程度** | 🔴紧急（影响关键路径）/ 🟡一般 / 🟢优化 |
| **影响范围** | 影响的WBS节点和交付物 |
| **提出方初步评估** | 对进度/成本/质量的影响估算 |

#### 1.2 CR 分类

| CR类别 | 说明 | 示例 |
|--------|------|------|
| **纠正措施** | 纠偏，使项目回到基线 | 进度落后时的赶工方案 |
| **预防措施** | 预防偏差发生 | 增加代码审查预防质量下滑 |
| **缺陷补救** | 修复不符合要求的产品 | 修复验收测试发现的Bug |
| **更新** | 变更正式受控的文件 | 更新WBS词典中的验收标准 |

---

### 第二步：变更影响评估（六维分析）

#### 2.1 影响分析矩阵

| 影响维度 | 分析内容 | 分析方法 |
|---------|---------|---------|
| **范围影响** | 影响哪些WBS工作包？是否新增/删除交付物？ | 对照WBS和范围说明书 |
| **进度影响** | 对关键路径的影响？需要延长多少工期？ | CPM重新计算 |
| **成本影响** | 新增成本？对总预算的冲击？ | EVM + 成本估算更新 |
| **质量影响** | 是否影响质量标准？需要额外测试？ | 对照质量度量指标 |
| **风险影响** | 引入新风险？改变已有风险等级？ | 更新风险登记册 |
| **合同影响** | 是否触犯合同条款？是否需要合同变更？ | 法律顾问审阅 |

#### 2.2 投资变更红线检查（政府项目）

| 投资变动幅度 | 审批级别 | 依据 |
|------------|---------|------|
| **> 10%** | 🔴 触发55号令第13条：**须重新报批上一环节审批** | 发改委55号令 |
| **5% - 10%** | 🟠 编制变更对照说明 + 独立章节分析 + 主管部门审批 | 行业惯例 |
| **< 5%** | 🟡 建设单位内部审批 + 在文档修订记录中说明 | 行业惯例 |

**变更传导检查**：

```
投资变更 > 10%？
  ├── 初设阶段：须重新报批可研报告
  ├── 详设阶段：须重新报批初设概算
  └── 执行阶段：须重新报批初设概算 → 可能影响招投标结果
```

### 第三步：CCB 审批

#### 3.1 CCB 组成

| 角色 | 代表 | 职责 | 投票权 |
|------|------|------|--------|
| **CCB主席** | 项目发起人/高层 | 最终决策 | ✅ |
| **PM** | 项目经理 | 变更影响分析汇报 | ✅ |
| **业主代表** | 信息中心主任 | 业务视角评估 | ✅ |
| **技术代表** | 技术负责人/架构师 | 技术可行性评估 | ✅ |
| **财务代表** | 财务经理 | 成本影响评估 | 咨询（无投票权） |
| **监理代表** | 监理工程师 | 合规审查 | 咨询（无投票权） |

#### 3.2 CCB 审批决策

| 决策 | 含义 | 后续动作 |
|------|------|---------|
| **批准** | 同意实施变更 | 更新基线 + 通知干系人 + 执行 |
| **有条件批准** | 附条件同意 | 满足条件后正式批准 |
| **退回修改** | 需要补充分析 | 按CCB意见重新提交 |
| **拒绝** | 不同意变更 | 记录原因，归档关闭 |

#### 3.3 CCB 审批原则

1. **非紧急不变更**：能不改的尽量不改
2. **替代方案优先**：考虑替代方案后再决定是否变更
3. **成本效益分析**：变更的收益 > 变更的成本
4. **一致投票**：重大变更须CCB主席+PM+业主代表一致同意
5. **审批不留白**：所有决策须书面记录，拒绝理由明确

### 第四步：变更实施与验证

#### 4.1 变更实施流程

```
CCB批准 → PM下达变更指令 → 责任人执行 → QA验证 → PM确认关闭
   ↓           ↓                ↓           ↓           ↓
 书面记录    更新任务板       按变更方案   对照变更    更新变更
                             执行         验收标准    日志状态
```

#### 4.2 验证要点

| 验证项 | 内容 |
|--------|------|
| 变更内容完成 | 对照CR描述逐项确认 |
| 未引入新问题 | 回归测试通过、关联模块无不良影响 |
| 文档已更新 | WBS/进度计划/成本基线已同步更新 |
| 干系人已知晓 | 受影响干系人已获通知 |

#### 5.2 审计准备

政府投资项目审计时，变更管理是重点审查项。须确保：

- [ ] 每个变更请求有书面记录和CCB审批签字
- [ ] 投资变更超过10%有上级主管部门的批文
- [ ] 变更不影响初设概算批复的核心功能
- [ ] 每个变更的实施结果有验证记录
- [ ] 变更日志完整且没有跳号
- [ ] 现场签证变更与工程联系单一一对应

## 使用示例

```
输入：某市政务云项目，初设概算批复1800万，目前执行到第3个月。
     业主要求新增"数据可视化大屏"功能。

评估：
1. CR-015 创建：范围变更，新增交付物
2. 六维分析：
   - 范围：新增1个WBS工作包(1.4.8 数据可视化大屏)
   - 进度：关键路径+15天
   - 成本：+65万（软件开发40万+大屏硬件25万）
   - 投资变动：65/1800 = 3.6% → 触发🟡（<5%，建设单位内部审批）
   - 质量：需增加性能测试项
   - 风险：引入新风险R-047（大屏供应商交付延迟）
3. CCB审批：
   → PM建议：可接受变更，但建议用利旧大屏替代新购(省25万)
   → CCB决议：有条件批准。接受软件开发部分(+40万)，大屏使用利旧设备
4. 更新基线：进度+12天，成本+40万，总投资1840万(变动2.2%)
5. 变更日志更新：CR-015 → 执行中
```

## 核心原则

1. **无审批不变更**：所有变更必须经过 CCB 审批方可实施
2. **先评估再决策**：CR提出→六维评估→CCB决策，不可跳过评估直接决策
3. **>10%是硬红线**：投资变动超过10%必须重新报批（发改委55号令第13条）
4. **替代方案优先**：审批前先问"不通过变更能解决吗？有没有更便宜的办法？"
5. **审批书面化**：所有CCB决议须书面记录并签字，口头决议无效
6. **变更必归档**：每个CR从提出到关闭的完整链路必须可追溯
7. **基线与实际同步**：变更实施后24小时内更新基线文件
8. **拒绝也是决策**：拒绝变更同样需要记录原因并通知提出方
9. **软件变更分类处置**：feature/bug/refactor/config四类变更须走不同审批通道——feature走CCB、bug走紧急修复、refactor走架构师审批、config走运维审批
