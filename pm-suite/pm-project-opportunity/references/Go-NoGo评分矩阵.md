# Go/No-Go 决策评分矩阵

> **用途**：项目机会评估阶段，在软考7维度基础上增加"战略匹配度"维度，形成8维度量化评分体系，支撑 Go / Conditional / No-Go 决策。
> **来源**：软考高项第7章 + PMP项目选择方法 + 软件团队实践经验
> **版本**：v1.1 | 最后更新：2026-08-31（方案A推广：概率锚定、期望支付、乘零否决、先验回写）

---

## 评分口径声明

本矩阵的 1-5 分含义统一为**"该维度判断成立的概率"**，锚定复用 `pm-risk-management` PIM 五级语言-数字锚（全库唯一的正面样板）：

| 评分 | 概率区间 | 语言锚 | 举证要求 |
|------|----------|--------|----------|
| 5 | >70% | 极可能成立 | 已有硬证据（意向合同/实测数据/权威报告） |
| 4 | 51–70% | 大概率成立 | 有支持证据，但存在反例 |
| 3 | 31–50% | 可能成立 | 证据不充分，主要靠类比推断 |
| 2 | 11–30% | 小概率成立 | 仅有零散信号 |
| 1 | ≤10% | 几乎不成立 | 已有明确反证 |

> 给不出证据的维度，只能打 3 分及以下（《底层逻辑1》p055–058 概率思维；《底层逻辑2》p130–133 期望值）。

## 八维度评分体系

| 编号 | 维度 | 核心问题 | 权重 |
|------|------|---------|------|
| ① | 技术可行性 | 技术方案是否成熟、先进、适用？团队现有技术栈是否匹配？ | 20% |
| ② | 经济可行性 | 投资回报是否合理？成本效益分析是否可行？ | 15% |
| ③ | 运行环境可行性 | 用户组织能否支撑系统运行？基础设施、运维能力是否具备？ | 10% |
| ④ | 社会可行性 | 政策合规性、社会接受度、公众影响如何？ | 5% |
| ⑤ | 操作可行性 | 最终用户能否操作使用？技能匹配度、培训成本如何？ | 5% |
| ⑥ | 法律政策可行性 | 是否存在法律政策障碍？数据安全、隐私合规是否满足？ | 10% |
| ⑦ | 战略匹配度 | 是否符合公司战略方向、技术路线、市场定位？ | 20% |
| ⑧ | 安全与合规 | 等保要求、密评要求、数据保护法规是否可满足？ | 15% |

> **说明**：对软考7维度做了以下调整——
> - 将"法律政策可行性"中的安全合规部分独立为第⑧维度"安全与合规"（软件项目尤其重要）
> - 新增第⑦维度"战略匹配度"（评估项目与公司长期目标的契合度）
> - 保留原⑦"其他方面"并入运行环境可行性维度

## 各维度评分标准

### ① 技术可行性（权重 20%）

| 评分 | 标准 |
|------|------|
| 5 | 技术方案完全成熟，团队有丰富同类项目经验（≥3个），核心技术组件有自主产权或成熟开源方案 |
| 4 | 技术方案成熟，团队有过类似项目经验（1-2个），核心技术可通过采购/集成解决 |
| 3 | 技术方案可用但部分模块需验证，团队缺乏直接经验但能力匹配，需要外部技术支持 |
| 2 | 技术方案存在明显风险（新技术、未验证），团队能力有较大差距，需要大量招募或外包 |
| 1 | 技术方案不可行或超出团队现有技术能力范围，短期无法弥补 |

**软件项目关键检查项**：
- 技术栈成熟度（TRL等级）
- 核心技术组件的社区活跃度/供应商稳定性
- 团队现有技术栈的匹配度
- 第三方依赖（API/SDK/开源库）的风险
- 是否需要引入全新未验证的技术栈

### ② 经济可行性（权重 15%）

| 评分 | 标准 |
|------|------|
| 5 | 投资回报率 > 40%，回收期 < 1年，净现值为正且显著 |
| 4 | 投资回报率 20%-40%，回收期 1-2年，净现值为正 |
| 3 | 投资回报率 10%-20%，回收期 2-3年，净现值趋近为正 |
| 2 | 投资回报率 0%-10%，回收期 > 3年，净现值接近零 |
| 1 | 投资回报率为负，不具备经济可行性 |

**软件项目关键检查项**：
- 软件license/SaaS订阅费是否在预算内
- 开发人力成本估算是否合理
- 维保期后的持续收入/维护成本
- 是否有隐性成本（云资源、第三方服务费、数据流量费）

### ③ 运行环境可行性（权重 10%）

| 评分 | 标准 |
|------|------|
| 5 | 客户基础设施完善，运维团队成熟，我方产品可直接部署运行 |
| 4 | 客户基础设施基本满足需求，少量改造即可部署，运维能力可接受 |
| 3 | 客户基础设施有缺口但可协商补充，运维需要我方较多支持 |
| 2 | 客户基础设施严重不足，需要大规模建设或改造 |
| 1 | 客户无运行环境基础，新建成本过高或不可控 |

### ④ 社会可行性（权重 5%）

| 评分 | 标准 |
|------|------|
| 5 | 项目符合国家/地方战略规划，社会接受度高，无明显负面影响 |
| 4 | 项目符合政策方向，有正面社会影响 |
| 3 | 项目无政策冲突，社会影响中性 |
| 2 | 项目存在政策争议或社会接受度存疑 |
| 1 | 项目明显违反政策导向或存在重大社会风险 |

### ⑤ 操作可行性（权重 5%）

| 评分 | 标准 |
|------|------|
| 5 | 最终用户技能匹配，现有流程可直接接入，培训成本极低 |
| 4 | 用户技能基本匹配，流程需要少量调整，培训成本可控 |
| 3 | 用户技能有差距但可培训弥补，流程需要重新设计 |
| 2 | 用户技能差距较大，原有流程需大幅改造，抵触风险高 |
| 1 | 用户不具备操作能力且无法在合理投入下弥补 |

### ⑥ 法律政策可行性（权重 10%）

| 评分 | 标准 |
|------|------|
| 5 | 完全合规，无法律政策障碍，所有必要资质齐备 |
| 4 | 基本合规，有可解决的资质/许可缺口 |
| 3 | 存在需要主动申请/办理的资质要求，周期可控 |
| 2 | 存在较大的法律政策不确定性或资质获取难度大 |
| 1 | 明显违法违规或存在不可回避的法律障碍 |

**软件项目关键检查项**：
- 数据采集/使用/存储是否合规
- 知识产权归属约定是否清晰
- 开源许可证是否兼容（GPL传染性风险评估）

### ⑦ 战略匹配度（权重 20%）

| 评分 | 标准 |
|------|------|
| 5 | 完全符合公司战略方向和技术路线，可直接复用现有产品和团队，有重大战略价值 |
| 4 | 符合公司战略方向，大部分可复用，有一定战略价值 |
| 3 | 与公司战略方向基本一致，部分可复用，属于维持性项目 |
| 2 | 与公司战略方向存在偏差，复用度低，但可锻炼新能力 |
| 1 | 与公司战略方向背离，属于"用战术努力弥补战略失误" |

**评估要点**：
- 是否在公司目标行业/区域/客户群内？
- 技术栈是否符合公司技术路线？
- 项目成果能否复用到后续项目（形成产品/平台）？
- 对团队能力建设是否有正向作用？

### ⑧ 安全与合规（权重 15%）

| 评分 | 标准 |
|------|------|
| 5 | 安全合规要求完全可控，方案已有成熟模板，等保/密评无缝覆盖 |
| 4 | 安全合规要求明确，方案可快速适配，合规成本可控 |
| 3 | 安全合规要求较高但可达标，需要额外投入资源 |
| 2 | 安全合规等级高（如等保三级），团队缺乏相关经验，合规成本显著 |
| 1 | 安全合规要求超出团队能力，或满足成本超过项目可承受范围 |

**软件项目关键检查项**：
- 等保定级要求（二级/三级？）
- 商用密码应用安全性评估（密评）要求
- 数据分类分级（个人信息、重要数据、核心数据）
- 数据出境/跨境传输合规
- 第三方安全认证（ISO27001、SOC2等）

## 综合得分计算

**加权总分计算公式（概率加权 + 否决项乘零）**：
```
总分 = Σ(各维度评分 × 权重) × Π(通过_i ? 1 : 0)    i ∈ {否决项}
满分 = 5.00
任一否决项未通过 → 乘零因子 = 0 → 总分归零 → No-Go
```

Go/No-Go 决策规则：
| 加权总分 | 决策 |
|---------|------|
| ≥ 3.5 | **Go**（建议推进，进入下一阶段） |
| 2.5 - 3.49 | **Conditional Go**（有条件推进，需标注风险项并制定缓解计划） |
| < 2.5 | **No-Go**（建议放弃或重大调整后重新评估） |

> **期望支付规则**：②经济可行性、⑦战略匹配度两维必须金额化（量纲取自可研报告估算方法）。合计期望支付 ≤ 0 → 无论总分多高，强制降级一档（Go→Conditional、Conditional→No-Go）。概率高但赔率亏本的项目仍然是坏项目。

### 否决项（一票否决，乘零归零）

以下任一项成立 → 公式中该项 `通过_i = 0` → **总分乘零归零 → 直接 No-Go**，无需进入评分：

| 否决项 | 判断标准 |
|--------|---------|
| 最大合同金额超过公司年营收50% | 履约风险过高 |
| 存在不可解决的资质壁垒 | 资格审查必然不通过 |
| 客户明确要求联合体但无可信合作伙伴 | 无法独立应标 |
| 技术方案需要不可获取的专利/核心技术 | 技术路线被封锁 |
| 违反公司明确禁止的业务领域 | 战略红线 |

## 先验回写（贝叶斯闭环）

评分卡的分数是先验，不是常量。项目结束（或 Conditional Go 补强后重评）后必须回写，否则同一类错误会永远以同一个分数复发。本步骤推广 `pm-bid-proposal` 的博弈系数 K 回写模式——全库唯一已跑通的贝叶斯闭环（《底层逻辑2》p145–147）。

**逐维度回写表**：

| 维度 | 本次打分→概率 | 实际结果（可量化） | 偏差判定 | 修正动作 |
|------|--------------|-------------------|----------|----------|
| ① 技术可行性 | 4 → 60% | 技术方案按期交付率 ___% | 高估 / 校准 / 低估 | 下次同类机会 ① 锚定值 −1 / ±0 / +1 |
| ② 经济可行性 | 3 → 40% | 实际净收益 ____万 vs 预估 ____万 | 高估 / 校准 / 低估 | 同上 |
| ⑧ 安全与合规 | 5 → 75% | 是否出现等保/密评返工 | 高估 / 校准 / 低估 | 同上 |

**累积规则**：
1. 回写记录统一存入「基础成功率修正表」（按项目类型分档：政务信息化/AIoT/数据治理/SaaS/系统集成）；
2. 同一类型累计 **≥5 个评估样本**后，用实测达成率均值替换该维度的默认语言锚。例：过去 5 次 ① 打 4 分（自称 51–70%）的项目，技术方案实际按期交付率均值 42% → 下次 ①=4 必须有硬证据，否则降为 3；
3. 报告中的「先验回写承诺」未填写 → 该次评估视为未完成，不得作为立项依据。

> 这一步把评分卡从"一次性打分表"变成"会自我修正的预测系统"。不做回写，8 维度评分永远只是把主观印象加权求和。

> **[d]** = 事实数据，**[s]** = 推断/假设。标注规范与 `pm-project-opportunity` 核心原则一致。

## 与软件团队的衔接 [s]

评分通过后（Go/Conditional Go），将评分表交付软件团队：

| 信息 | 消费方 | 用途 |
|------|--------|------|
| 技术可行性评分 + 技术栈匹配分析 | 架构师 | 预研技术方案 |
| 经济可行性评分 + 成本估算 | 主理人 | 资源预算分配 |
| 风险项清单 | QA工程师 | 测试策略制定 |
| 安全合规要求（等保/密评） | 架构师 | 安全架构设计 |
| 否决项检查结果 | 主理人 | 最终决策确认 |
