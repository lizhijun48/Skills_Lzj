# 干系人管理

## 角色定位

资深项目经理（PMP）兼一级建造师角色，专注于政府/国企项目的干系人识别、分析、参与策略制定与监控。

核心任务：系统识别项目所有干系人，分析其权力、利益和影响方向，制定针对性的参与策略，确保关键干系人从"当前状态"向"期望状态"转变。每一步对标 PMBOK 第13章、软考高项第12章（干系人部分），同时融入一建实务中政府项目的干系人管理经验（多层级汇报、审计方、行业主管部门）。

## 软件项目专项支持

### 软件项目特有干系人

除标准政府项目干系人外，软件项目须额外识别以下干系人：

| 干系人类型 | 典型角色 | 权力-利益象限 | 关键影响 | 识别时机 |
|-----------|---------|-------------|---------|---------|
| **架构评审委员会** | 甲方技术总监/CTO | 高权力高利益 | 一票否决技术方案 | 项目启动 |
| **开源社区维护者** | 关键依赖库的Core Committer | 低权力高利益 | 依赖库停止维护=项目风险 | 技术选型阶段 |
| **云服务商技术支持** | AWS/阿里云/腾讯云 TAM | 高权力低利益 | 资源配额/技术支持响应速度 | 部署方案阶段 |
| **等保测评机构** | 测评师 | 高权力高利益 | 不通过=系统无法上线 | 设计阶段 |
| **密码管理局** | 密评审查员 | 高权力低利益 | 涉密系统须通过密评 | 需求阶段 |
| **数据安全官** | DPO | 高权力高利益 | 数据出境/隐私合规一票否决 | 需求阶段 |
| **运维团队** | 甲方运维/DevOps | 低权力高利益 | 系统移交后的实际运营者 | 设计阶段 |

### 软件干系人参与策略补充

| 场景 | 策略 | 执行要点 |
|------|------|---------|
| **架构评审委员会质疑技术方案** | "预沟通+备选方案" | 评审前1周提交方案摘要，准备A/B方案 |
| **开源依赖风险** | "社区参与+备选库" | 关注社区活跃度，评估替代方案成本 |
| **云服务商配合度低** | "合同驱动+升级路径" | SLA条款明确响应时间，升级至客户经理 |
| **等保测评周期不确定** | "提前预约+并行推进" | 设计阶段就预约测评，整改与开发并行 |
| **运维团队抗拒新系统** | "体验优先+知识转移" | 运维参与设计评审，提前培训+文档交付 |

## 工作流程（5 步）

### 第一步：干系人识别

#### 1.1 干系人识别方法

| 方法 | 适用场景 | 输出 |
|------|---------|------|
| **干系人分析会议** | 项目启动阶段 | 初始干系人清单 |
| **文件审查** | 合同/可研/招标文件 | 合同约定的干系人 |
| **专家判断** | 复杂政治环境 | 隐性干系人 |
| **头脑风暴** | 项目团队内部 | 遗漏的干系人 |

#### 1.2 政府项目干系人全景图

```
项目干系人
├── 内部干系人
│   ├── 公司高层（项目发起人/分管副总）
│   ├── 项目团队（PM/技术负责人/现场经理/QA）
│   └── 平行部门（财务/采购/法务/售前）
├── 外部干系人（甲方侧）
│   ├── 业主方领导（分管副局长/主任）        ← 决策层
│   ├── 业主方业务部门（业务科长/科员）       ← 用户层
│   ├── 业主方信息中心（主任/工程师）          ← 技术对接层
│   ├── 监理方（总监/监理工程师）             ← 监督层
│   ├── 审计方（政府审计局/第三方审计）       ← 合规层
│   └── 财政评审中心                          ← 预算层
└── 外部干系人（第三方）
    ├── 分包商/供应商
    ├── 等保测评机构
    ├── 软件测评机构
    ├── 政务云平台运营方
    └── 行业主管部门（如大数据局/工信局）
```

#### 1.3 干系人识别检查清单

| 维度 | 检查项 | 典型遗漏 |
|------|--------|---------|
| 合同方 | 合同中提到的所有甲方对接人 | 验收委员会成员 |
| 监管方 | 行业主管部门、等保/分保要求 | 大数据局、密码管理局 |
| 使用方 | 最终用户、运维人员 | 二级单位使用者 |
| 影响方 | 可能受项目影响的周边方 | 系统对接方、数据提供方 |
| 隐性方 | 有影响力但不在合同中的人 | 甲方高层幕僚、甲方顾问 |

### 第二步：干系人分类与分析

#### 2.1 权力-利益矩阵（核心分类工具）

```
权力（高）
  ↑
  │  令其满意             密切管理
  │  [分管副局长]         [信息中心主任]
  │  [大数据局]            [业务科长]
  │  [审计方]             [监理总监]
  │
  │  监督（最低投入）      及时告知
  │  [平行部门]           [最终用户]
  │  [供应商]             [运维人员]
  └─────────────────────────────→ 利益（高）
```

**四象限管理策略**：

| 象限 | 策略 | 政府项目实例 | 典型错误 |
|------|------|-------------|---------|
| **高权力高利益** | 密切管理 | 信息中心主任、业务科长 | 只汇报不沟通 |
| **高权力低利益** | 令其满意 | 分管副局长、大数据局 | 忽视其潜在影响力 |
| **低权力高利益** | 及时告知 | 最终用户、运维人员 | 到验收才通知 |
| **低权力低利益** | 监督 | 平行部门、供应商 | 投入过多精力 |

#### 2.2 影响力-影响方向矩阵

| 干系人 | 影响方向 | 说明 |
|--------|---------|------|
| 业主方领导 | ↑→ | 自上而下影响决策，横向影响其他部门 |
| 信息中心主任 | ↑→↘ | 影响技术决策，可影响领导判断 |
| 业务科长 | →↗ | 横向推动需求，可向上影响领导 |
| 监理方 | ↓→ | 自上而下监督执行，横向影响各方 |
| 审计方 | ↓ | 自上而下审计合规 |

> ↑ = 自上而下 | ↓ = 自下而上 | → = 横向 | ↗ = 向上 | ↘ = 向下

#### 2.3 Salience 模型（补充分类）

当权力-利益矩阵无法区分时，使用三维度分类：

| 维度 | 说明 | 判断标准 |
|------|------|---------|
| **Power（权力）** | 强制决策的能力 | 能否一票否决/能否调动资源 |
| **Legitimacy（正当性）** | 参与的正当理由 | 是否在合同/法规中有明确角色 |
| **Urgency（紧迫性）** | 需求的紧迫程度 | 是否需要立即回应 |

7类干系人：**潜伏型**（P）、**裁量型**（L）、**要求型**（U）、**支配型**（P+L）、**危险型**（P+U）、**依赖型**（L+U）、**确定型**（P+L+U，最需关注）

### 第三步：干系人参与度评估

#### 3.1 五级参与度模型

| 等级 | 含义 | 行为特征 | 典型政府项目场景 |
|------|------|---------|-----------------|
| **不知晓** | 不知道项目存在 | 不参与任何活动 | 验收委员会外成员 |
| **抵制** | 知道但反对 | 设置障碍/拖延/投诉 | 被替代系统的原供应商 |
| **中立** | 知道但不表态 | 不主动参与/也不反对 | 非核心业务科室 |
| **支持** | 知道且支持 | 提供资源/配合工作 | 业务科长 |
| **领导** | 主动推动项目 | 主动协调资源/推动决策 | 信息中心主任 |

#### 3.2 参与度评估矩阵

| 干系人 | 不知晓 | 抵制 | 中立 | 支持 | 领导 | 当前状态 | 期望状态 | 差距 |
|--------|--------|------|------|------|------|---------|---------|------|
| 张副局长 | | | | ● | | 支持 | 领导 | ↑1级 |
| 李主任 | | | | | ● | 领导 | 领导 | 无 |
| 王科长 | | | ● | | | 中立 | 支持 | ↑1级 |
| 业务科室 | | ● | | | | 抵制 | 中立 | ↑2级 |
| 陈工 | ● | | | | | 不知晓 | 支持 | ↑3级 |

#### 3.3 差距分析方法

差距 = 期望参与度 - 当前参与度

| 差距 | 紧迫度 | 行动策略 |
|------|--------|---------|
| ↑3级（如不知晓→支持） | 高 | 立即制定专项沟通计划 |
| ↑2级（如抵制→中立） | 高 | 优先解决抵制原因 |
| ↑1级（如中立→支持） | 中 | 定期沟通，逐步提升 |
| 0级 | — | 维持现状，防止倒退 |
| ↓负数（如支持→领导） | 低 | 正常现象，注意不要过度依赖 |

### 第四步：干系人参与策略制定

#### 4.1 参与策略工具箱

| 策略 | PMBOK对应 | 适用场景 | 政府项目实例 |
|------|----------|---------|-------------|
| **咨询** | Consult | 需要干系人专业意见 | 技术方案请信息中心审核 |
| **协作** | Collaborate | 需要干系人深度参与 | 需求确认邀请业务科长参加 |
| **授权** | Empower | 将决策权交给干系人 | UI风格让用户代表决定 |
| **信息推送** | Inform | 保持干系人知情 | 项目周报、里程碑简报 |
| **培训** | Train | 干系人能力不足影响参与 | 新系统操作培训给最终用户 |
| **谈判** | Negotiate | 干系人需求冲突 | 多科室需求优先级排序 |

#### 4.2 政府项目特殊参与策略

| 场景 | 策略 | 执行要点 |
|------|------|---------|
| **领导层参与度不足** | "小胜利"策略 | 先在可见度高的小需求上快速交付，赢得信任 |
| **跨部门利益冲突** | "共同目标"策略 | 引导各方回到可研/招标文件，以合同为准绳 |
| **监理方过度干预** | "专业对话"策略 | 用技术标准和行业规范回应，而非情绪对抗 |
| **审计方关注** | "透明合规"策略 | 主动提供过程文档，而非被动配合 |
| **最终用户抵制** | "体验优先"策略 | 安排试用和反馈环节，让用户参与设计 |
| **信息中心主任换人** | "重新建信"策略 | 重新进行参与度评估，从零开始建立关系 |

#### 4.3 干系人参与计划

| 干系人 | 当前→期望 | 关键策略 | 沟通方式 | 频率 | 负责人 | 检查点 |
|--------|----------|---------|---------|------|--------|--------|
| 张副局长 | 支持→领导 | 小胜利+里程碑汇报 | 当面10分钟 | 里程碑 | PM | 每次里程碑 |
| 李主任 | 领导→领导 | 维持+深度技术沟通 | 邮件+当面 | 每两周 | PM | 每周回顾 |
| 王科长 | 中立→支持 | 协作+需求共创 | 当面 | 每周 | PM | 需求确认时 |
| 业务科室 | 抵制→中立 | 谈判+体验优先 | 试用+反馈 | 每Sprint | 产品经理 | 每次迭代 |
| 陈工 | 不知晓→支持 | 信息推送+培训 | 微信群+培训 | 每两周 | 组长 | 培训后 |

### 第五步：干系人参与监控与调整

#### 5.1 监控指标

| 指标 | 衡量方式 | 预警阈值 |
|------|---------|---------|
| **参与度变化** | 定期重新评估（每Sprint/每月） | 任何干系人下降≥1级 |
| **沟通响应率** | 甲方回复率/出席率 | <60%响应率 |
| **问题升级率** | 干系人相关问题升级到高层 | >2次/月 |
| **满意度趋势** | 干系人满意度调查（季度） | 下降>10% |
| **决策延迟** | 因干系人不响应导致的决策延期 | >3天未回复 |

#### 5.2 调整触发规则

| 触发条件 | 调整动作 | 升级路径 |
|---------|---------|---------|
| 关键干系人参与度下降1级 | 立即沟通了解原因 | PM→公司高层 |
| 甲方领导更换 | 重新评估+建信计划 | PM→公司高层→投标关系 |
| 干系人需求冲突升级 | 引导回到合同/可研 | PM→监理→审计 |
| 沟通响应率持续低迷 | 更换沟通方式/频率 | PM→对方上级 |
| 干系人抵制无法化解 | → `pm-risk-management` 记录风险 | PM→项目指导委员会 |

#### 5.3 与其他SKILL的联动

| 联动场景 | 联动SKILL | 数据流 |
|---------|----------|--------|
| 干系人抵制/冲突导致风险 | → `pm-risk-management` | 干系人风险条目 |
| 干系人变更触发CR | → `pm-change-management` | CR + 影响评估 |

## 使用示例

### 示例1：政府信息化项目干系人管理

```
项目：XX市智慧城市大数据平台建设项目
金额：2800万
周期：18个月

触发：用户说"帮我做干系人分析"

执行：
1. 干系人识别 → 产出25位干系人登记册
2. 权力-利益矩阵 → 4人密切管理，3人令其满意
3. 参与度评估 → 发现业务科长"抵制"（担心新系统增加工作量）
4. 参与策略 → "体验优先"策略：安排试用+反馈，让其对设计有话语权
5. 参与监控 → Sprint回顾中持续评估，从抵制→中立→支持

关键风险：分管副局长即将调任 → 触发"领导更换"调整规则
```

### 示例2：干系人参与度下降预警

```
触发：信息中心主任连续2次未出席周例会

执行：
1. 查看参与度评估 → 当前"领导"，响应率从90%降至30%
2. 分析原因 → 通过技术负责人了解：对技术方案有疑虑
3. 制定调整 → 安排1对1技术沟通，提前分享方案文档
4. 监控效果 → 2周后响应率恢复至80%

关键经验：干系人参与度下降往往是问题信号，不要等到升级才处理
```

---

## 核心原则

1. **识别优先**：项目启动第一周完成干系人识别，遗漏关键干系人是重大风险
2. **权力-利益定策略**：不凭感觉分配精力，用矩阵量化决策
3. **参与度差距即行动**：当前≠期望的差距就是行动计划的核心
4. **持续监控不松懈**：干系人立场会变，定期重新评估
5. **政府项目关注隐性权力**：不在合同中但有影响力的人（高层幕僚、甲方顾问）往往被忽略
6. **抵制不是终点**：用"体验优先"策略化抵制为支持
7. **不越级但要知道越级的影响**：了解高层关系但不越级操作
8. **干系人换人=重新建信**：关键干系人更换时，从零开始建立信任关系
9. **软件特有干系人不可遗漏**：架构评审委员会、开源社区维护者、云服务商技术支持、等保测评机构在软件项目中拥有隐性否决权，须纳入干系人登记册
