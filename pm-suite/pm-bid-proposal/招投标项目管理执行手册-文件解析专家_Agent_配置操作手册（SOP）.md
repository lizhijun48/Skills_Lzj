# 招投标文件解析专家 Agent 配置操作手册（SOP）

------

## 概述

本手册用于指导 **招投标文件解析专家 Agent** 的完整配置流程。配置基于已确定的角色指令，按顺序逐项完成。

> **配置总览顺序：角色指令 → 模型设置 → 工具 → 知识 → 记忆 → 对话**

------

## Step 1｜配置角色指令

| 项目         | 说明                                                         |
| ------------ | ------------------------------------------------------------ |
| **目的**     | 定义 Agent 的行为宪法，是所有后续模块的运行框架              |
| **操作**     | 基于已确认的角色指令文本，确保 `@工具名` 和 `{变量名}` 引用与后续配置一致 |
| **语法支持** | `@工具名` 调用工具，`{变量名}` 引用记忆变量                  |
| **输出**     | 完整的 System Prompt                                         |

```
# Role: 招投标文件解析专家 # Profile: 你是一个精确、严谨的招投标文件解析专家。你的唯一职责是接收招标文件和公司信息，按照@三读法解析工具 调用 @三读法SOP知识库 进行结构化解析，输出JSON格式数据。你不做任何判断、不做任何决策、不生成任何文件。 # 核心任务： 1. 读取全局变量中的 {bid_document} 和 {company_info} 2. 调用 @三读法解析工具，按三读法流程解析 3. 输出结构化JSON，写入 {parse_result} # JSON必须包含以下字段： - project_name: 项目名称 - bid_deadline: 投标截止时间 - qualification_requirements: 资质要求（数组） - evaluation_criteria: 评审标准（数组） - mandatory_documents: 必须提供的文件清单（数组） - risk_flags: 风险标记（数组，如"资质不足"/"时间不够"/"业绩缺失"） - score_breakdown: 评分细则（如有） - special_requirements: 特殊要求（如有） # 约束规则（必须严格遵守）： - 你只做解析，不做任何判断 - 你只输出JSON，不输出任何解释性文字 - JSON中的所有字段必须从招标文件原文中提取，不得虚构 - 如果某字段在文件中不存在，填null，不要省略字段 - 写之前必须先读全局变量，确认数据完整再写 - 输出长度控制在3000字以内 
```

| **输出** | 完整 System Prompt（如上） |
| -------- | -------------------------- |
|          |                            |

> ✅ `@三读法解析工具` → 对应 Step 3 工具①
> ✅ `{bid_document}` `{company_info}` `{parse_result}` → 对应 Step 5 记忆变量

## Step 2｜配置模型设置

| 项目     | 说明                      |
| -------- | ------------------------- |
| **目的** | 定义 Agent 的推理引擎参数 |
| **操作** | 按下表逐项填写            |

| 参数         | 定义                                                   | 推荐值       | 说明                                                         |
| ------------ | ------------------------------------------------------ | ------------ | ------------------------------------------------------------ |
| 规划思考模型 | 负责任务拆解与推理（如拆解招标文件结构、规划解析步骤） | 独立设置参数 | 与总结模型分开配置                                           |
| 总结生成模型 | 负责输出最终结构化 JSON 结果                           | 独立设置参数 | 与规划模型分开配置                                           |
| 对话轮数     | 传入大模型上下文的最大对话轮数                         | **2**        | 值越大，多轮上下文相关性越强，但 Tokens 消耗越多             |
| 最大思考次数 | 一轮对话中组件调用的最大次数                           | **2**        | 值越大，可处理更复杂任务，但响应耗时↑、Tokens↑；值越小，可减少组件重复调用 |

| **输出** | 规划模型参数 + 总结模型参数 + 对话轮数 + 最大思考次数 |
| -------- | ----------------------------------------------------- |
|          |                                                       |

| 子项         | 参数         | 值   | 说明                                    |
| ------------ | ------------ | ---- | --------------------------------------- |
| 规划思考模型 | temperature  | 0.3  | 低温度，保证解析步骤不发散              |
|              | top_p        | 0.9  |                                         |
|              | max_tokens   | 2048 | 单步推理，不需要长文本                  |
| 总结生成模型 | temperature  | 0.1  | 极低温度，JSON 输出必须精确，不允许创意 |
|              | top_p        | 0.9  |                                         |
|              | max_tokens   | 4096 | JSON 可能较长，预留足够空间             |
| 全局         | 对话轮数     | 2    | 多轮场景少，单次上传即解析              |
|              | 最大思考次数 | 2    | 配合 4 个工具，2 次调用足够完成一轮解析 |

## Step 3｜配置工具

| 项目     | 说明                                                         |
| -------- | ------------------------------------------------------------ |
| **目的** | 扩展 Agent 的执行能力                                        |
| **操作** | 添加函数 / API / 插件，在角色指令中通过 `@工具名` 调用       |
| **约束** | **建议不超过 4 个**                                          |
| **原因** | 配合「最大思考次数 = 2」，超过 4 个会导致单轮内无法充分调用，降低准确率，增加无效调用和重复调用 |

> 以下为基于最佳实践的参考定义，工程落地时需根据实际接口和能力进行匹配调整。

| 序号 | 工具名称        | 类型     | 描述                                                         |
| ---- | --------------- | -------- | ------------------------------------------------------------ |
| 1    | @文件读取工具   | function | 读取全局变量中的 {bid_document}（招标文件内容）和 {company_info}（公司信息），返回结构化文本 |
| 2    | @三读法解析工具 | function | 调用 @三读法SOP 知识库，按「一读通览→二读精析→三读校验」流程逐层解析，输出中间结构化数据 |
| 3    | @JSON生成工具   | function | 将解析结果按角色指令要求的字段格式，生成标准 JSON，写入 {parse_result} |
| 4    | @风险标记工具   | function | 扫描解析结果，对照资质要求、时间节点、业绩条件，自动标记风险项，填充 risk_flags 数组 |

| **输出** | 工具列表（4 个），含名称、类型、描述 |
| -------- | ------------------------------------ |
|          |                                      |

> 🔧 工程落地调整建议：
>
> - 如果招标文件是 PDF/图片，工具①需接入 OCR 能力
> - 如果风险规则复杂，工具④可拆为多个子工具，但总数仍控制在 4 个以内
> - 工具②是核心，必须与知识库「三读法SOP」强绑定

## Step 4｜配置知识

| 项目     | 说明                                                |
| -------- | --------------------------------------------------- |
| **目的** | 构建 Agent 的知识来源，用户发消息时可引用知识库答复 |
| **操作** | 上传或关联知识库，按下表填写                        |

| 配置项 | 说明 | 约束 |
|--------|------|
| 知识库类型 | ① 本地文本数据 ② 表格型数据（含 FAQ 问答、多列索引问答）③ 在线网页数据 | — |
| 关联数量 | **最多 50 个** | 超过 50 个配合「最大思考次数 = 2」无法有效检索 |
| 备注信息 | **建议详细填写** | 写清知识类型和模式，提高问答匹配准确率 |

| 序号 | 知识库名称         | 类型        | 来源（路径/URL）                  | 备注                                                         |
| ---- | ------------------ | ----------- | --------------------------------- | ------------------------------------------------------------ |
| 1    | 三读法SOP          | local_text  | /knowledge/three_read_sop.md      | 核心知识库：一读通览→二读精析→三读校验的完整流程和字段映射规则 |
| 2    | 招投标法律法规汇编 | local_text  | /knowledge/law_bidding.txt        | 包含政府采购法、招标投标法及实施条例，用于风险标记参考       |
| 3    | 资质要求FAQ        | table_faq   | /knowledge/qualification_faq.xlsx | FAQ 模式：一问一答，如"工程类项目需要哪些资质"               |
| 4    | 评分标准索引表     | table_index | /knowledge/scoring_index.xlsx     | 多列索引模式：按项目类型、评分方法、权重筛选                 |
| 5    | 投标文件模板库     | local_text  | /knowledge/templates/             | 含工程类、货物类、服务类模板，用于 mandatory_documents 匹配  |
| 6    | 废标条件清单       | table_faq   | /knowledge/invalid_bid_faq.xlsx   | FAQ 模式，用于 risk_flags 填充                               |
| 7    | 行业术语词库       | local_text  | /knowledge/terms_bidding.txt      | 招投标专用术语及释义，提升解析准确率                         |
| 8    | 各省招投标平台规则 | web_page    | https://...                       | 备注：按省份分类，检索时优先匹配用户所在省                   |
| 9~50 | （按需扩展）       |             |                                   | 每项必须填写备注                                             |

| **输出** | 知识库列表（≤ 50 个），含名称、类型、来源、备注 |
|----------|

> ⚠️ 知识库①「三读法SOP」是工具②的直接依赖，必须优先配置，备注中需写清三读法的字段映射规则，否则工具②无法正确输出中间数据。

## Step 5｜配置记忆

| 项目     | 说明                                        |
| -------- | ------------------------------------------- |
| **目的** | 让 Agent 记住对话中的用户信息，回答更个性化 |
| **操作** | 按三种类型分别配置                          |

### 5.1 记忆变量

| 项目     | 说明                                     |
| -------- | ---------------------------------------- |
| 定义     | 记录**一维、单个**的应用信息或用户信息   |
| 结构     | Key-Value                                |
| 适用场景 | 让回答更个性化（如当前项目名、截止日期） |
| 关联     | 直接被角色指令中的 `{变量名}` 引用       |

| Key | Value（初始为空，待运行时填充） | 描述 |
|-----|-------------------------------|
| bid_document | {待运行时填充} | 招标文件完整文本内容 |
| company_info | {待运行时填充} | 投标公司信息（名称、资质、业绩等） |
| parse_result | {待运行时填充} | 解析输出的 JSON 结果 |
| current_project_name | {待运行时填充} | 当前项目名称，从 bid_document 中提取 |
| bid_deadline | {待运行时填充} | 投标截止时间，从 bid_document 中提取 |

### 5.2 记忆表

| 项目     | 说明                                     |
| -------- | ---------------------------------------- |
| 定义     | 记录**多维、大量**的应用信息或用户信息   |
| 结构     | 结构化表格，支持**智能问数**             |
| 适用场景 | 复杂数据查询（如历史项目列表、资质清单） |

| 表名         | 列名                                     | 数据（初始为空） | 描述                                                   |
| ------------ | ---------------------------------------- | ---------------- | ------------------------------------------------------ |
| 解析历史记录 | [项目名称, 解析日期, 风险项数量, 匹配度] | [待对话中积累]   | 记录每次解析的关键指标，支持问数如"哪个项目风险项最多" |
| 资质清单     | [资质名称, 等级, 有效期, 状态]           | [待对话中积累]   | 记录已识别的资质信息，支持问数如"哪些资质快过期了"     |

### 5.3 记忆片段

| 项目     | 说明                                                   |
| -------- | ------------------------------------------------------ |
| 定义     | 记录所有关于**用户信息、用户偏好、用户计划**的文本片段 |
| 结构     | 非结构化，自由文本                                     |
| 适用场景 | 长周期上下文召回                                       |

| 内容（初始为空） | 标签 | 描述 |
|------------------|------|
| {待对话中积累} | preference | 用户偏好的解析方式，如"优先看废标条件" |
| {待对话中积累} | plan | 用户的投标计划，如"下周三前要完成解析" |
| {待对话中积累} | user_info | 用户背景信息，如"甲方采购负责人" |

| **输出** | 记忆变量（5个）+ 记忆表（2个）+ 记忆片段（3个），三类分别填写 |
| -------- | ------------------------------------------------------------ |
|          |                                                              |

## Step 6｜配置对话

| 项目     | 说明                                           |
| -------- | ---------------------------------------------- |
| **目的** | 配置交互层，不影响核心逻辑，但直接影响用户体验 |
| **操作** | 按下表逐项填写                                 |

| 配置项   | 说明                           | 填入内容                                                     |
| -------- | ------------------------------ | ------------------------------------------------------------ |
| 声音     | 语音合成，填写 voice_id        | `bidding_expert_male`（专业沉稳男声）                        |
| 形象     | 数字人形象，填写 avatar_url    | `/avatar/bidding_expert.png`（商务正装形象）                 |
| 开场白   | 首次进入时的主动引导语         | "您好，我是招投标文件解析专家。请上传招标文件和公司信息，我将按三读法为您输出结构化解析结果。" |
| 推荐问题 | 引导用户快速发起对话的预设问题 | ① "帮我解析这份招标文件的关键信息" ② "检查投标文件是否满足资质要求" ③ "输出这份招标文件的JSON结构化数据" |
| 追问     | 对话中的智能追问策略           | `auto`（自动判断是否需要追问，如 bid_document 不完整时主动询问） |
| 背景图片 | 对话界面背景视觉               | `/bg/office_blue.jpg`（深蓝色商务风格）                      |

| **输出** | 对话配置完整填写 |
| -------- | ---------------- |
|          |                  |

## 依赖关系总览

```
Step 1 角色指令  ├─ @三读法解析工具 ← Step 3 工具②  ├─ @三读法SOP知识库 ← Step 4 知识库①  └─ {bid_document} {company_info} {parse_result} ← Step 5 记忆变量       ↓ Step 2 模型设置（全局控制）  ├─ 对话轮数 = 2  └─ 最大思考次数 = 2       ↓ Step 3 工具（4个）  ├─ ① 文件读取工具 → 读取 {bid_document} {company_info}  ├─ ② 三读法解析工具 → 调用 @三读法SOP知识库  ├─ ③ JSON生成工具 → 写入 {parse_result}  └─ ④ 风险标记工具 → 填充 risk_flags       ↓ Step 4 知识（≤50个）  └─ ① 三读法SOP 是工具②的直接依赖       ↓ Step 5 记忆  └─ 为 Step 1 提供 {变量名} 引用源       ↓ Step 6 对话（独立层，不影响逻辑） 
```
