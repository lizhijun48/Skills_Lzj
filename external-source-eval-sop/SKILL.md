# 外部来源多视角评估 SOP（external-source-eval-sop）

> 来源：SRC-004（product-management-expert-source）引入复盘沉淀（2026-09-21）——原评估被判定为"单一吸收视角"存在片面性，故补齐客观/上帝视角。对齐 GOV_SkillGovernance v3.7 原则十一。

## 一、适用场景

- 引入 marketplace / 第三方作者署名 / 带 IP 声明的技能
- fork 外部技能并改造（与原则十「外部技能通用化」配套，先过评、后通用化）
- 外部文档 / 课程 / PDF 喂养技能并登记 SRC 条目
- 已引入的来源做**回头看**复评（验证镜头可用性、补齐当初缺失的镜头）
- 判定某个外部内容"值不值得进体系"

## 二、核心原则（对齐 GOV v3.7）

1. **原则十一 客观多视角评估（引入前置）**：禁止"对我有无用 / 能否填洞"单一视角，8 镜头全过评方可入库
2. **原则十 外部技能通用化**：先过评 → 再决定是否拆分 → 拆分时才做通用化（顺序不可颠倒）
3. **原则八 修改前置治理判定**：评估后若涉及改动我方技能，先判定「严格符合 / 特殊情况偏离」
4. **原则九 模块融合去重**：镜头③ 检出与既有模块重叠 → 须评估融合，不重复实现
5. **QG4 数据溯源 / QG6 变更管理**：结论记 SOURCE-REGISTRY，变更记 CHANGELOG，决策记 DECISION-LOG
6. **不杜撰**：找不到权威出处一律标 **`待核实`**，禁止把启发式当标准公式
7. **认知增强层自动触发（pull→push）**：评估前强制跑三层透视，把 S-006 / S-007 / perspective-kernel 从"用户主动调用"改为"评估门禁自动触发"，治"你不知道自己不知道"的盲区（详见 §三「认知增强层」章）

## 三、8 镜头评估模型

| #   | 镜头                 | 要回答的核心问题                                       | 不做的后果       | 认知增强指针（评估前自动触发）                                                                 |
| :-- | :------------------- | :----------------------------------------------------- | :--------------- | :--------------------------------------------------------------------------------------------- |
| ①   | 技术正确性独立核验   | 公式 / 模型 / 方法是否为业界标准口径？有无权威出处？   | 误导性方法论入库 | 三层透视 + perspective-kernel 第六步「幸存者偏差检查」：先看权威框架（宏观）→对照同类（中观）→核验公式/数字（微观）；主动问"沉默的失败者在哪里" |
| ②   | 外部基准对比         | 是否有可对照的独立基准或同类样本？                     | 单点偏差         | 三层透视「中观层（虎眼）」强制找 ≥1 个独立对照样本，避免单样本误导                             |

### 镜头 ① 技术正确性独立核验

**核验对象**：公式、模型、方法论、阈值、术语定义、流程步骤。

**方法**：查权威出处（原始论文 / 官方标准 / 行业公认框架 / 一手发布方文档）；对照已知标准口径；必要时联网核验。

**判定口径**：

| 情形                                       | 判定            | 处置                                   |
| :----------------------------------------- | :-------------- | :------------------------------------- |
| 有权威出处且口径一致                       | ✅ 过评         | 入库，正文标注出处                     |
| 找不到出处但逻辑自洽                       | ⚠️ 待核实       | 可入库，**必须显式标注"启发式 / 经验公式"**，不得冒充标准 |
| 与权威口径冲突且无说明                     | ❌ 不过评       | 不入库；或降级为启发式并显式标注后另案评估 |
| 存在事实性硬伤（数字/年份/条款错误）       | ❌ 不过评       | 修正后再评，未修正不得入库             |

> **警示案例**：RICE 的"机会规模 = 用户数 × 频次 × 严重度"只是**启发式估算**，与 Intercom 2015 原文口径不同——不得作为标准公式入库，须标注为启发式。

---

### 镜头 ② 外部基准对比

**要回答**：是否有 ≥1 个独立基准或同类样本可交叉验证？结论是否建立在单一样本上？

**判定口径**：

- 有独立基准且结论一致 → ✅ 过评，信心高
- 有基准但结论有差异 → ⚠️ 记录差异原因，标注适用范围
- 无任何外部基准 → ⚠️ 标「**无外部基准·单样本**」，降级信心，结论仅作参考

> 单一样本下的"写得好 / 不足"评价极易受样本特性误导，须在结论中显式声明。

---

### 镜头 ③ 融合二阶风险

**要回答**（**最易被忽略的一阶盲区**——原评估只评"它有什么弱点"，未评"它接入后对我造成什么"）：

1. **耦合度**：接入后与我方多少技能产生依赖？是否形成新的中心节点？
2. **复杂度债**：是否新增入口 / 编号 / 路由 / 概念，增加认知负担？
3. **可发现性债**：用户在需要时**能否找得到**？（用户原话痛点："后续用到的时候最少有一个可以查询的地方，而不是一抹黑"）
4. **重叠度**：与既有模块是否功能重叠（对齐 QG2 / 原则九）→ 重叠须评估融合

**判定口径**：

| 情形                                       | 判定      | 处置                     |
| :----------------------------------------- | :-------- | :----------------------- |
| 已登记入 REGISTRY/CATALOG/FLOW-MAP，路径可达 | ✅ 过评   | 正常入库                 |
| 与既有模块重叠但已评估融合并归并入口       | ✅ 过评   | 记融合决策               |
| 重叠未评估融合                             | ❌ 不过评 | 先做融合评估             |
| 接入后无人知道怎么用（无路由、无入口）     | ❌ 不过评 | 先补可发现性路径再入库   |

---

### 镜头 ④ 使用者价值

**要回答**：真实使用场景是什么？使用频次多高？不用会怎样（严重度）？

**判定口径**：

- 有明确场景 + 可预期频次 + 有一定严重度 → ✅ 过评
- 场景明确但频次低 → ⚠️ 可入库，标「低频」，不占主干路由
- 只"觉得有用"但说不出具体场景 → ⚠️ 降级为「**观察 / 待用**」，不入库或入库不入主干

> 反模式：以"以后可能有用"作为唯一理由入库——这是僵尸技能的主要来源。

---

### 镜头 ⑤ 生命周期 TCO

**要回答**：

1. **维护成本**：谁来更新？多久一次？上游失联怎么办？
2. **更新成本**：上游更新后，我方合并还是永久 fork？
3. **废弃成本**：能否干净移除？有无下游依赖？删除需要改几处？

**判定口径**：

- 维护主体明确 + 废弃路径清晰 → ✅ 过评
- 无维护主体（上游失联 / 无人认领）→ ⚠️ 标「**无维护主体**」，慎入；若入，须登记废弃预案
- 废弃时需大范围改动下游 → ❌ 先解耦再入库

---

### 镜头 ⑥ 来源可信度与许可

**要回答**：

1. 作者 / 机构可信度（可核验身份？有无代表作？）
2. 许可条款（MIT / Apache / CC-BY / 商用限制 / 署名要求 / 是否允许改编与再分发）
3. 来源是否为官方一手，还是二手转载

**判定口径**：

- 许可明确且允许使用 + 改编 → ✅ 过评，frontmatter 记许可
- 许可不明 / 限制商用 / 禁止改编 → ❌ 不过评（或仅作内部参考，**不入库、不分发**）
- 公有领域内容（如中国法律文本，著作权法第 5 条）→ ✅ 过评，注明公有领域依据
- 无署名、无法溯源作者 → ⚠️ 标「来源不可溯」，谨慎采信其内容断言

---

### 镜头 ⑦ 战略契合（PM + PM 双轨知识库主线）

**主线定义**（用户 2026-09-21 明确）：

- **产品经理轨（PM¹）**：产品战略 / 需求 / PRD / 市场研究 / 生命周期 / 运营增长
- **项目经理轨（PM²）**：整合 / 范围 / 进度成本 / 质量 / 风险 / 干系人 / 招投标 / 验收收尾
  - 分支：**一建（一级建造师）**是项目经理轨的一个分支，不是独立主线
- **交叉层**（两轨共有，非独立主线）：法律法规 / 合同 / 工程保单相关风险转移与索赔
- **体系中的"点"**：保单分析等属体系中**很小的点**，允许存在但不占主干

**判定口径**：

| 情形                                       | 判定            | 处置                       |
| :----------------------------------------- | :-------------- | :------------------------- |
| 直接服务双轨主线或交叉层                   | ✅ 过评（优先） | 正常入库，占主干编号       |
| 属体系中"小点"但可查询                     | ✅ 过评（降级） | 可入库，不占主干路由，标"体系小点" |
| 完全游离于双轨主线                         | ⚠️ 观察         | 不入库，或单列观察区       |

> **重要**：不得仅因"只是体系中的一个小点"就否定入库——用户明确意图是"现在能补充的就补充，能考虑就考虑，后续用到时最少有一个可以查询的地方"。否定标准应是"完全游离"，而非"体量小"。

---

### 镜头 ⑧ 治理自反（元治理）

**要回答**：本次评估过程本身，是否暴露 GOV 的盲点？（如出现本 8 镜头未覆盖的维度、或原则之间互相冲突）

**触发 GOV 自反评审的条件**（对齐原则十一）：

1. 镜头 ⑧ 标出 GOV 盲点
2. 每 **+20 个技能** 或每 **6 个月**例行（季度自查 + 半年度深查）
3. 发生 skill 合并 / 拆分导致**可发现性回归**

**处置**：产出记 `DECISION-LOG.md`（决策）+ `CHANGELOG.md`（变更），**复用既有四记录，不新建平行元治理系统**。若自反发现需新增原则，走原则八（改治理原则 vs 改技能由人类裁决）。

---

### 认知增强层（宏观 / 中观 / 微观 三层透视自动触发）

> **优化①（2026-09-22）**：既有思维类技能（S-006 / S-007 / perspective-kernel）原为 **pull 型**——用户主动调用才生效，治不了"你不知道自己不知道"的盲区（飞行员 checklist 类比：再牛的飞行员也靠强制清单防漏）。本 SOP 将其改为 **push 型**：每次评估外部源，**自动触发**三层透视，作为镜头①~②（及④⑦部分）的"想透"前置，与 8 镜头清单的"不漏"互补。

**三层透视定义**（引用 `expert-suite/high-vision-perspective/SKILL.md` §3，跨引不复制文本）：

- **宏观（鹰眼）**：时代 / 趋势 / 该领域权威框架是什么
- **中观（虎眼）**：博弈 / 结构 / 同类做法与体系耦合点
- **微观（蚂蚁眼）**：执行 / 自身 / 具体公式与数字对不对

**自动触发动作**（评估前必跑，记为步骤②的前置）：

1. 读 `expert-suite/perspective-kernel.md` 的 6 步决策内核与「跨视角比较协议」（§3），套用到候选来源
2. 跑三层透视：宏观定权威框架 → 中观找独立对照样本 → 微观核验公式/数字
3. 落地 perspective-kernel 第六步「幸存者偏差检查」：主动问"我依据的案例里，沉默的失败者在哪里？"——避免只评活下来的样本
4. 镜头④借 S-007（周鸿祎·用户视角）复核"真实用户场景"；镜头⑦借 S-006（高格局·终局倒推 / 战略取舍）判定主干归属

**边界（重要）**：三层透视只补 **①②**（想得深 / 不被带偏），部分支持 **④⑦**；**补不全 ③④⑤⑥⑧**（登记事实、治理动作、硬许可门禁）。触发点负责"想透"，8 镜头清单负责"不漏"——二者互补，不能互相替代。思维技能治认知偏误，治不了"体系里找不到"（可发现性债由镜头③与 §五第7步管）。

## 四、最易错的关键边界

> **"评估外部来源" ≠ "证明它有用"。**

- 评估目的是**判定要不要进、怎么进**，不是为已做的引入决定找理由——先有结论再补评估属反模式。
- **8 镜头不是 8 个加分项**：任一镜头判 ❌ 即不过评，不是加权求和后"总体还行"。
- **⚠️ 待核实不是通过**：标待核实可入库，但必须显式标注，且在结论中单列跟踪项。

## 五、执行步骤（7 步）

1. **登记候选**：先在 SOURCE-REGISTRY 建 SRC 条目（或指向既有条目），标状态「评估中」
2. **逐镜头过评（前接三层透视自动触发）**：先按「认知增强层」章跑完宏观/中观/微观三层透视与幸存者偏差检查，将结论作为镜头①②（及④⑦）的输入；再按 ①~⑧ 逐项填写判定与证据，禁止跳过、禁止合并填写
3. **出结论**：过评 / 不过评 / 有条件过评（列明条件与跟踪项）
4. **决定引入方式**：全量引入 / 部分吸收 / fork 改造 / 仅作参考不入库
5. **过评后动作**：引入 →（若拆分）通用化（原则十）→ 登记编号与路由（可发现性）
6. **回填记录**：SOURCE-REGISTRY 记评估结论；CHANGELOG 记变更；DECISION-LOG 记决策；镜头⑧有发现则另起自反条目
7. **联动表 4 张逐表打勾（交付自检）**：新增技能/专家包纳管后，逐表确认已同步，缺一即视为交付未完成（GOV §8 硬性联动表清单）——

   | 联动表 | 路径 | 打勾 |
   |--------|------|:----:|
   | 编号注册表 | `SKILL-ID-REGISTRY.md` | ☐ |
   | 业务流路由表 | `BUSINESS-FLOW-MAP.md` | ☐ |
   | PT 关系表 | `pd-suite/pd-workflow-chains/SKILL.md` | ☐ |
   | JT 关系表 | `pm-suite/pm-workflow-chains/SKILL.md` | ☐ |

> **本步骤由 S-072 首次实战（SRC-004 回头看）反向催生**：复评检出 JT-021 仅同步 1/4 张表，属执行漏项而非规则缺口（登记 DECISION-LOG T-002）。教训：登记进编号表 ≠ 挂进业务流程链，二者缺一即产生"可发现性债"。

## 七、反模式（勿犯）

- ✗ 只写"对我有什么用、能填什么洞"（单一吸收视角，本次 SRC-004 的原问题）
- ✗ 只评对方弱点、不评接入后对我方的二阶影响（漏镜头③）
- ✗ 把启发式公式当标准公式入库（漏镜头①）
- ✗ 加权求和式判定——任一 ❌ 即不过评
- ✗ 先引入、后补评估（结论先行）
