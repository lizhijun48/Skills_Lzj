## 产品-项目协同桥接（PD↔PM）

### PD→PM 协作协议

```
产品决策需转项目交付时：

pd-integration                    pm-integration
    │                                  │
    ├─ PRD已确认 ─────────────────→ 项目章程输入
    ├─ 需求基线(RTM) ────────────→ 范围基线
    ├─ 优先级排序 ────────────────→ WBS+排期
    ├─ 非功能需求 ────────────────→ 质量标准
    └─ GTM计划 ──────────────────→ 项目里程碑
```

### PM→PD 协作协议

```
项目执行影响产品决策时：

pm-integration                    pd-integration
    │                                  │
    ├─ 进度延迟 ──────────────────→ 版本路线图调整
    ├─ 技术约束 ──────────────────→ 需求方案调整
    ├─ 质量问题 ──────────────────→ 上线时间调整
    └─ 变更请求 ──────────────────→ 需求变更评估
```

### PD↔PM 冲突解决矩阵

| 冲突场景 | PD立场 | PM立场 | 解决原则 |
|----------|--------|--------|----------|
| 功能范围 | 全做 | 时间不够砍功能 | 优先级排序，P0必做P2可砍 |
| 上线时间 | 做完再上 | 按时交付 | MVP先上，增量迭代 |
| 质量标准 | 体验优先 | 进度优先 | P0 Bug为0，P1可带1-2个 |
| 需求变更 | 加功能 | 变更走流程 | 重大变更走CCB，轻微下版 |

## 开发方法选择

### 5种开发方法对比

| 方法 | 特征 | 适用场景 | 产品类型 |
|------|------|----------|----------|
| **预测型（瀑布）** | 需求明确、一次性交付 | 政府信息化项目、合规要求高 | ToG项目 |
| **迭代型** | 需求逐步明确、反复完善 | 核心功能明确但细节待探索 | B端平台 |
| **增量型** | 分模块交付、每模块完整 | 功能模块独立性强 | 大型系统 |
| **敏捷型** | 小团队、快速迭代、用户参与 | 需求变化快、市场不确定 | C端产品 |
| **混合型** | 预测+敏捷结合 | 整体规划+局部敏捷 | 政企信息化（推荐） |

### 政府信息化项目混合法推荐

```
整体用预测型（满足审计/合规/验收要求）
  ├── 需求阶段：瀑布（完整PRD+评审）
  ├── 设计阶段：瀑布（架构设计+评审）
  ├── 开发阶段：敏捷（2周Sprint+演示）
  ├── 测试阶段：瀑布（完整测试+验收）
  └── 部署阶段：瀑布（正式上线+培训）

决策矩阵：
| 市场确定性\技术确定性 | 低 | 高 |
|---------------------|----|----|
| 高 | 迭代型 | 预测型 |
| 低 | 敏捷型 | 增量型 |
```

## 职业道德与专业行为规范

### PMI 4大核心价值观

| 价值观 | 定义 | 产品管理中的体现 |
|--------|------|-----------------|
| **责任** | 为行为和决策承担后果 | 产品决策用数据说话，不为KPI造假 |
| **尊重** | 尊重他人和资源 | 尊重用户隐私，不做过度数据采集 |
| **公正** | 公平客观地决策 | A/B测试不能损害用户体验，利益冲突要披露 |
| **诚实** | 真实透明地沟通 | 不夸大产品能力，不隐瞒已知问题 |

### 产品经理8类行为规范

| # | 规范 | 正面案例 | 反面案例 |
|---|------|----------|----------|
| 1 | 不虚构用户需求 | 基于访谈数据写需求 | 把自己的需求当用户需求 |
| 2 | 不隐瞒产品缺陷 | 上线前告知已知限制 | 明知有Bug不说 |
| 3 | 不操纵数据 | 真实呈现运营数据 | 挑好看的数据汇报 |
| 4 | 保护用户隐私 | 遵循最小采集原则 | 过度采集"以后可能有用"的数据 |
| 5 | 不抄袭竞品 | 研究竞品但独立设计 | 1:1复制竞品功能+交互 |
| 6 | 利益冲突披露 | 有投资关系主动说明 | 暗中推荐自己投资的产品 |
| 7 | 知识产权尊重 | 使用开源需合规审查 | 抄代码不检查许可证 |
| 8 | 团队诚信 | 如实评估工作量 | 迎合老板压缩合理工期 |

### 举报与维权3步流程

```
Step 1: 内部报告 → 向直属上级或合规部门报告
Step 2: 如果无效 → 向公司高层或董事会报告
Step 3: 如果仍无效 → 向相关监管机构报告

⚠️ 举报人保护：PMI要求组织不得对举报人报复
```

## 与软件开发团队的协作接口

### PD Suite ↔ 软件开发团队

```
pd-integration                    软件开发团队
    │                                  │
    ├─ PRD ──────────────────────→ 产品经理(许清楚)输入
    ├─ 需求基线 ────────────────→ 架构师(高见远)设计依据
    ├─ 验收标准(AC) ────────────→ QA工程师(严过关)测试用例
    └─ 优先级排序 ──────────────→ 工程师(寇豆码)开发顺序
```

### 协作铁律

1. **PD定义What，PM/团队决定How**——产品经理说做什么，不规定怎么做
2. **PRD是契约**——approved后不可单方面修改，变更走流程
3. **AC是验收的唯一标准**——不满足AC=没完成，超越AC是锦上添花
4. **优先级是PD的权力**——先做什么后做什么由产品经理决定
5. **技术可行性是团队的专业判断**——PD提需求，团队评估可行性

## 核心原则

1. **PD管What，PM管How**——产品经理定方向，项目经理管交付，不越界
2. **质量门是防线不是障碍**——每个衔接点的质量门防止问题后流
3. **数据驱动是信仰**——产品决策必须有数据支撑，"我觉得"不算
4. **职业道德是底线**——虚构需求、隐瞒缺陷、操纵数据都是红线
5. **开发方法因项目而异**——政府项目混合法，C端敏捷法，不一刀切
6. **PD↔PM协作是双向的**——产品影响项目，项目也影响产品
7. **整合管理的本质是确保全链路贯通**——从发现到运营不能断链
