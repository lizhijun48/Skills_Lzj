## 核心工作流程

### Step 1：确认公司创新战略类型

**迈尔斯-斯诺4种创新战略**（决定产品战略的底色）：

| 类型 | 特征 | 产品策略倾向 | 典型企业 | 风险 |
|------|------|-------------|----------|------|
| **探索者(Prospector)** | 先发制人，持续创新 | 激进创新，快速试错 | 字节跳动、特斯拉 | 资源消耗大，失败率高 |
| **分析者(Analyzer)** | 快速跟随，模仿+改良 | 快速跟随，微创新 | 腾讯、美团 | 时机窗口稍纵即逝 |
| **防御者(Defender)** | 稳守细分，渐进改良 | 深耕垂直，功能深化 | 用友、金蝶 | 错失市场变革 |
| **反应者(Reactor)** | 被动响应，无明确战略 | 无规律，被动开发 | — | 最高风险，战略失焦 |

**实操判断**：
- 问CEO/创始人3个问题即可判断：
  1. "我们更倾向于做第一个，还是做更好的那个？" → 探索者vs分析者
  2. "我们是拓宽新领域，还是深耕现有领域？" → 探索者vs防御者
  3. "我们有明确的3年产品规划吗？" → 否=反应者预警

**⚠️ 踩坑**：如果公司是"反应者"类型，产品经理的首要任务是推动战略明确化，而非埋头做产品规划。

### 破坏性创新 vs 持续性创新（Christensen框架）

> **NPDP Ch1核心**：Clayton Christensen提出的破坏性创新（Disruptive Innovation）理论是创新战略的基石概念，也是NPDP认证高频考点。

| 维度 | 持续性创新 | 破坏性创新 |
|------|-----------|-----------|
| **目标** | 把好产品做得更好 | 用更简单/更便宜/更便捷的方案服务被忽视的市场 |
| **目标客户** | 现有高端客户 | 非消费者或被过度服务的低端客户 |
| **技术路径** | 沿现有技术轨道提升 | 引入新的价值维度 |
| **在位者反应** | 积极投入，维持领先 | 忽视——"这不是我们的客户" |
| **盈利模式** | 高毛利/高定价 | 低毛利/高周转/新盈利模型 |
| **竞争结果** | 在位者持续领先 | 新进入者最终颠覆在位者 |

**两种破坏类型**：

| 类型 | 机制 | 经典案例 | 产品经理启示 |
|------|------|----------|------------|
| **低端破坏(Low-end)** | 在位者过度服务→低端被忽视→新进入者用更低成本满足基础需求 | 小米早期千元机颠覆山寨机市场 | 不要一味堆功能，基础场景的极致性价比也是战略 |
| **新市场破坏(New-market)** | 在位者服务不到→非消费者无人管→新进入者创造新市场 | iPhone创造智能手机市场 | 不是从竞品抢用户，而是让"不用的人开始用" |

**创新者窘境的3个机制**：
1. 在位者依赖现有客户→资源向现有客户倾斜→忽视边缘市场
2. 小市场不能满足大公司的增长需求→破坏性创新起步的市场太小
3. 在位者的价值网络（成本结构/渠道/流程）不适合新市场

**与迈尔斯-斯诺的对应关系**：

| 迈尔斯-斯诺类型 | 创新模式倾向 |
|----------------|------------|
| 探索者(Prospector) | 主动发起破坏性创新 |
| 分析者(Analyzer) | 跟随破坏性创新，快速复制+改良 |
| 防御者(Defender) | 专注持续性创新，在细分市场深耕 |
| 反应者(Reactor) | 被动应对，没有明确创新策略 |

**产品经理实战决策框架**：
```
面对创新方向的3个问题：
1. 这个创新是让现有客户更满意（持续性），还是吸引新类型客户（破坏性）？
2. 如果我们的在位者逻辑认为"这不是我们的市场"，是否可能是破坏性创新的信号？
3. 我们的成本结构/渠道体系/价值网络是否支持新市场模式？不支持=需要独立团队
```

### Step 2：制定产品愿景与使命

**产品愿景公式**：
```
[产品名] 帮助 [目标用户] 通过 [核心方式] 实现 [终极价值]，
从而 [改变的状态/达成的目标]。
```

**实操示例**：

| 产品 | 愿景陈述 |
|------|----------|
| 某智慧园区平台 | "智慧园区平台帮助园区运营方通过AIoT数据中台实现全场景智能管理，从而降低30%运营成本" |
| 某安防SaaS | "XX安防云帮助中小企业通过SaaS化视频管理实现专业级安防能力，从而用1/5成本获得同等安全保障" |

**愿景质量检查**：
- [ ] 是否明确说明了目标用户？
- [ ] 是否说明了核心方式（而非功能列表）？
- [ ] 是否量化了终极价值？
- [ ] 团队每个人能否复述？（不能=太长或太模糊）

### Step 3：选择增长策略（安索夫矩阵）

```
           现有产品        新产品
          ┌──────────┬──────────┐
 现有市场 │ 市场渗透  │ 产品开发  │
          │ (低风险)  │ (中风险)  │
          ├──────────┼──────────┤
 新市场   │ 市场开发  │ 多元化   │
          │ (中风险)  │ (高风险)  │
          └──────────┴──────────┘
```

**决策逻辑**：

| 当前状态 | 推荐策略 | 产品动作 |
|----------|----------|----------|
| 产品成熟+市场未饱和 | 市场渗透 | 优化转化/留存，扩大渠道 |
| 市场饱和+有能力做新产品 | 产品开发 | 基于现有用户需求扩展产品线 |
| 产品成熟+新市场机会 | 市场开发 | 行业拓展/区域扩张 |
| 需要第二曲线 | 多元化 | 谨慎评估，必须过pd-go-nogo |

**⚠️ 踩坑**：多元化≠随意扩张。必须经过pd-go-nogo的8维度评估，否则就是"赌"不是"策略"。

### Step 4：设计商业模式

**3种商业模式画布选择**：

| 画布类型 | 适用场景 | 复杂度 |
|----------|----------|--------|
| **商业模式画布(BMC)** | 成熟市场、已有参照 | 标准9格 |
| **精益画布** | 创业/新市场、高不确定性 | 9格（适配创业） |
| **价值主张画布** | 专注产品-市场匹配(PMF) | 6格+客户画像 |

**BMC 9要素速填指南**：

| # | 要素 | 填写要点 | 常见错误 |
|---|------|----------|----------|
| 1 | 客户细分 | 谁？按行为/需求/价值分层 | "所有人"=没聚焦 |
| 2 | 价值主张 | 解决什么问题？提供什么价值？ | 列功能而非价值 |
| 3 | 渠道 | 如何触达？如何交付？ | 只考虑线上忽略线下 |
| 4 | 客户关系 | 获取/留存/增长？自服务/人工？ | 只考虑获客忽略留存 |
| 5 | 收入来源 | 怎么赚钱？订阅/交易/广告/许可？ | 只有一种收入模式 |
| 6 | 核心资源 | 需要什么？技术/品牌/人才/数据？ | 列出现有而非必需 |
| 7 | 关键活动 | 必须做什么？平台运营/内容/研发？ | 列日常而非关键 |
| 8 | 关键伙伴 | 谁帮我们？供应商/渠道/战略伙伴？ | 漏掉生态伙伴 |
| 9 | 成本结构 | 花什么钱？固定/变动/边际成本？ | 只算开发不算运营 |

**ToB SaaS BMC模板**：
```
┌────────────────────────────────────────────────────┐
│ KP: 云厂商/集成商/ISV   │ VP: 降本增效/合规/数据   │
│ KA: 产品开发/平台运营   │     驱动的业务决策支撑     │
│ KR: 技术平台/数据/团队  │ CR: 客户成功经理/自助服务 │ │
│                          │ CH: 直销+渠道/行业展会    │
│ CS$: 软件许可/实施服务   │                          │
│                          │ KR: 中大型企业/政府       │
│ C$: 研发60%/销售20%/     │                          │
│     运维10%/管理10%      │                          │
└────────────────────────────────────────────────────┘
```

### Step 5：制定产品路线图

**3种路线图格式选择**：

| 格式 | 适用场景 | 时间粒度 | 示例 |
|------|----------|----------|------|
| **基于功能** | 对内沟通、开发团队 | 季度/月 | Q1:用户管理→Q2:数据分析→Q3:AI推荐 |
| **基于目标(OKR)** | 管理层、战略对齐 | 季度 | Q1:达到1万DAU→Q2:实现PMF→Q3:营收100万 |
| **基于主题(Now/Next/Later)** | 对外沟通、客户 | 不精确 | Now:核心功能→Next:智能分析→Later:生态开放 |

## 产品平台战略

> **NPDP Ch1+Ch7核心**：产品平台（Product Platform）是产品战略的核心要素——多个产品共享的一组技术/组件/流程/知识。平台战略决定了产品线的扩展性和研发效率。

### 平台 vs 单点产品

| 维度 | 单点产品 | 产品平台 |
|------|---------|---------|
| **复用度** | 各产品独立开发，几乎不复用 | 核心组件跨产品复用，开发效率×N |
| **扩展性** | 加新产品=重新开发 | 加新产品=在平台上组装 |
| **维护成本** | N个产品=N套维护 | N个产品=1套平台+N套扩展 |
| **典型场景** | 小团队、快速试错 | 多产品线、ToG/ToB |
| **失败风险** | 单个产品失败不影响其他 | 平台失败→所有产品受影响 |

### 平台架构三层模型

```
┌─────────────────────────────────────────────┐
│                  产品应用层                   │
│   产品A       产品B       产品C              │
│  (智慧安防)  (智慧园区)  (智慧交通)           │
├─────────────────────────────────────────────┤
│                  通用服务层                   │
│  用户管理 │ 权限系统 │ 流程引擎 │ 数据分析     │
│  消息中心 │ 配置管理 │ 日志监控 │ 计费引擎     │
├─────────────────────────────────────────────┤
│                  基础设施层                   │
│  云原生底座 │ IoT接入 │ AI中台 │ 安全合规     │
└─────────────────────────────────────────────┘
```

| 层级 | 职责 | 变更频率 | 负责人 |
|------|------|---------|--------|
| **基础设施层** | 统一技术底座和安全合规 | 低（半年一次大版本） | 平台架构师 |
| **通用服务层** | 跨产品可复用的业务服务 | 中（季度迭代） | 平台产品经理 |
| **产品应用层** | 具体产品的差异化功能 | 高（月度迭代） | 各产品线产品经理 |

### 平台代际规划

```
第1代(1.0) → 第2代(2.0) → 第3代(3.0)
单体平台      微服务化平台    智能化平台
    │              │              │
MVP验证        规模化支撑      差异化竞争
核心闭环       多产品接入      AI赋能
```

| 代际 | 技术特征 | 产品特征 | 典型里程碑 |
|------|---------|---------|-----------|
| **第1代** | 单体架构、快速构建 | 1-2个产品、核心闭环 | 首单交付 |
| **第2代** | 微服务化、模块解耦 | 3-5个产品复用、开放API | 第3个产品复用率>60% |
| **第3代** | AI/大数据驱动、智能化 | 生态开放、ISV入驻 | 外部开发者>10个 |

**⚠️ 踩坑**：不要一开始就做平台——第1个产品先做成单点MVP，验证PMF后再平台化。"过早平台化"是ToG/ToB产品最常见的战略错误。

### 平台生态构建

| 生态角色 | 价值 | 吸引策略 | 度量指标 |
|---------|------|---------|---------|
| **开发者** | 贡献插件/应用 | SDK+文档+社区 | 活跃开发者数 |
| **ISV/SI** | 交付+定制 | 分成机制+认证 | 伙伴收入占比 |
| **客户** | 需求反馈+案例 | 共创+种子客户 | NPS+案例数 |

### ToG/ToB平台战略特殊考量

| 维度 | ToG平台 | ToB平台 |
|------|---------|--------|
| 核心能力 | 数据打通+可视化驾驶舱 | 降本增效+管理闭环 |
| 扩展方式 | 标准接口+政务数据共享 | API+ISV生态 |
| 合规要求 | 信创适配+等保+密评（强制） | 行业合规（视领域定） |
| 典型案例 | 城市大脑/一网统管 | SaaS+低代码平台 |

### 工具2：产品-市场匹配(PMF)自测

```
PMF信号检测（Sean Ellis测试法中文版）：
问用户："如果不能再使用这个产品，你会？"
□ 非常失望 → PMF达成（需>40%用户选此项）
□ 有点失望 → 接近但未达到
□ 无所谓   → 未达到PMF
□ 不在使用 → 产品有问题

ToB版本：
问客户决策人："如果取消这个产品，对你们业务影响多大？"
□ 重大影响，无法替代 → 强PMF
□ 有影响，但有替代方案 → 弱PMF
□ 影响不大 → 无PMF
```

## 踩坑预警

| # | 坑点 | 表现 | 规避 |
|---|------|------|------|
| 1 | **愿景墙上的画** | 写了愿景但没人记得 | 用公式写，1句话能复述 |
| 2 | **路线图变承诺** | 客户/销售拿路线图当交付承诺 | 明确标注"方向性指引"，加免责声明 |
| 3 | **战略对齐假阳性** | 口头对齐但执行走样 | 每季度用战略对齐检查表验证 |
| 4 | **商业模式只画不管** | 画了BMC但不验证 | 关键假设必须做市场验证 |
| 5 | **ToG战略=做项目** | 把项目当产品，无产品化思维 | 区分"做项目"vs"做产品"——产品有可复制性 |

## 政企产品专项支持（ToG/ToB）

### ToG产品战略特殊考量

| 维度 | ToG差异 | 实操要点 |
|------|---------|----------|
| 创新战略 | 多为防御者/分析者 | 政府需求稳定，不适合探索者战略 |
| 愿景 | 必须对齐政策文件 | 愿景中引用"十四五""数字中国"等关键词 |
| 安索夫 | 市场开发（跨区域）>产品开发 | 同一产品适配不同区域/部门是主旋律 |
| BMC | 收入来源=财政预算，非市场付费 | 客户细分按"预算级别"分（省/市/区） |
| 路线图 | 与财政年度对齐 | Q4申报→Q1审批→Q2采购→Q3实施→Q4验收 |

### ToB产品战略特殊考量

| 维度 | ToB差异 | 实操要点 |
|------|---------|----------|
| 创新战略 | 分析者为主 | 跟随+微创新是ToB主流策略 |
| BMC | 实施服务收入占30-50% | 不只算软件许可，实施/定制化是重要收入 |
| 路线图 | 需考虑大客户定制需求 | 路线图预留20%容量给KA定制 |

## 核心原则

1. **战略是产品的GPS**——没有战略的产品是"随机漫步"，有战略的产品是"定向航行"
2. **愿景必须能被团队复述**——如果说不出来，就不是愿景，是墙上的画
3. **路线图是方向不是承诺**——方向可调，承诺不可违；混淆两者是产品经理最大的雷
4. **商业模式必须验证**——画完BMC只是起点，关键假设必须通过市场验证
5. **ToG战略看政策，ToB战略看客户**——政企产品的战略锚点与2C完全不同
6. **战略对齐是持续动作**——不是一次性的，每季度必须验证产品方向与公司战略的一致性
