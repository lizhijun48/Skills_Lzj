## 核心工作流程

### Step 1：需求收集与分类

**需求来源全景**：

| 来源 | 方法 | 可信度 | 常见问题 |
|------|------|--------|----------|
| 用户访谈 | pd-user-research | ★★★★ | 样本偏差 |
| 数据分析 | 行为数据/漏斗分析 | ★★★★★ | 相关≠因果 |
| 销售反馈 | 丢单分析/客户需求池 | ★★★ | 只说不要不说为什么 |
| 竞品分析 | pd-market-research | ★★★ | 竞品有的≠用户需要的 |
| 老板/战略 | 管理层决策 | ★★ | 缺乏用户验证 |
| 客服/运营 | 工单/投诉分析 | ★★★★ | 只反映存量用户问题 |
| 技术驱动 | 技术可行性 | ★★ | 技术可行≠用户需要 |

### Step 2：需求分析（Y模型）

```
         用户需求（表面）
              │
     ┌────────┴────────┐
     │  1. 倾听+记录    │
     ▼                  │
 用户说："我要一匹更快的马"
     │                  │
     │  2. 分析+挖掘    │
     ▼                  │
 真实需求："我需要更快到达目的地"
     │                  │
     │  3. 转化+创新    │
     ▼                  │
 产品方案：汽车/火车/飞机 ←──┘
     │
     │  4. 验证+选择
     ▼
 具体需求：功能需求+非功能需求
```

**Y模型4步实操**：

| 步骤 | 动作 | 输入 | 输出 | 关键问题 |
|------|------|------|------|----------|
| 1.倾听 | 原样记录用户原话 | 访谈/工单/反馈 | 需求原始记录 | "用户原话是什么？" |
| 2.分析 | 问5个Why挖到根因 | 需求原始记录 | 真实需求 | "他为什么这么说？" |
| 3.转化 | 从真实需求出发生成方案 | 真实需求 | 产品方案(≥2个) | "有哪些解决方案？" |
| 4.验证 | 用MVP/原型验证方案 | 产品方案 | 确认的需求 | "用户是否认可？" |

### Step 3：KANO需求分类

**KANO问卷设计（含具体模板）**：

```
正问："如果有这个功能，你觉得？"
□ 我很喜欢     (5)
□ 理所当然     (4)
□ 无所谓       (3)
□ 勉强接受     (2)
□ 我很不喜欢   (1)

反问："如果没有这个功能，你觉得？"
□ 我很喜欢     (1)  ← 注意！反问评分反向
□ 理所当然     (2)
□ 无所谓       (3)
□ 勉强接受     (4)
□ 我很不喜欢   (5)
```

**KANO分类判定表**（正问×反问交叉查表）：

| 正问\反问 | 喜欢 | 理所当然 | 无所谓 | 勉强接受 | 不喜欢 |
|-----------|------|----------|--------|----------|--------|
| **喜欢** | Q | A | A | A | O |
| **理所当然** | R | I | I | I | M |
| **无所谓** | R | I | I | I | M |
| **勉强接受** | R | R | R | R | M |
| **不喜欢** | R | R | R | R | Q |

M=必备型 O=期望型 A=兴奋型 I=无差异 R=反向型 Q=可疑结果

**KANO分类→优先级映射**：

| KANO类型 | 优先级 | 策略 | 版本规划 |
|----------|--------|------|----------|
| **M 必备型** | P0 最高 | 做不好=不用 | V1.0必须包含 |
| **O 期望型** | P1 高 | 做得好=竞争力 | V1.0尽可能包含 |
| **A 兴奋型** | P2 中 | 做得出=差异化 | V1.0/V2.0选择包含 |
| **I 无差异** | P3 低 | 不做 | 不做 |
| **R 反向** | 删除 | 做了=用户讨厌 | 绝对不做 |

**⚠️ 踩坑**：
- 兴奋型需求会随时间变为期望型→版本2需重新评估KANO
- 样本量<30人不具备统计意义→至少30份有效问卷
- 正反问逻辑不一致的答卷应剔除

### Step 4：5W1H需求描述

**5W1H需求描述模板**：

```
Who(谁)：      目标用户/角色
What(什么)：   用户要完成什么任务
When(何时)：   使用场景/触发条件
Where(何地)：  使用环境/设备
Why(为什么)：  用户目的/动机
How(如何)：    预期交互方式

示例：
Who：    园区运营主管
What：   查看当日设备告警统计
When：   每日早9:00到办公室时
Where：  电脑Web端+手机App
Why：    快速了解昨日设备异常情况，安排当日巡检
How：    登录后首页即展示告警统计卡片
```

### Step 5：用户故事编写（INVEST原则）

**INVEST质量检查**：

| 字母 | 含义 | 好的用户故事 | 差的用户故事 |
|------|------|-------------|-------------|
| I | Independent独立 | "用户可以创建门禁规则" | "用户先创建再配置门禁"（依赖其他故事） |
| N | Negotiable可协商 | "用户可以管理设备"（范围可商量） | "用树形结构展示设备列表"（锁死实现） |
| V | Valuable有价值 | "用户可以一键生成报告" | "系统使用React框架"（技术而非价值） |
| E | Estimatable可估算 | "用户可以导入1000条数据" | "系统能处理大数据"（多大？） |
| S | Small小 | 1-2周可完成 | "系统实现全部安防功能" |
| T | Testable可测试 | "用户3次点击内完成任务" | "用户体验好"（无法测试） |

**用户故事标准格式**：
```
作为 [角色]，
我想要 [功能/动作]，
以便于 [价值/目的]。

验收标准(AC)：
1. Given [前置条件] When [动作] Then [预期结果]
2. Given [前置条件] When [动作] Then [预期结果]
3. ...
```

**实操示例**：
```
作为 园区运营主管，
我想要 按告警级别筛选设备告警，
以便于 优先处理紧急告警。

验收标准：
AC1: Given 告警列表页 When 选择"紧急"筛选 Then 只显示级别为"紧急"的告警
AC2: Given 已筛选的告警列表 When 点击"全部" Then 恢复显示所有告警
AC3: Given 筛选结果 When 无匹配告警 Then 显示"暂无匹配的告警记录"
```

### Step 6：信息架构设计

**信息架构3步法**：

```
Step 1: 内容盘点（列出所有内容/功能）
Step 2: 分类组织（卡片分类法——开放分类或封闭分类）
Step 3: 导航设计（全局导航+局部导航+面包屑+搜索）
```

**卡片分类法实操**：

| 方法 | 做法 | 适用场景 |
|------|------|----------|
| 开放式 | 用户自己分组并命名 | 全新产品、不确定导航结构 |
| 封闭式 | 用户将卡片放入预设分类 | 已有分类体系、验证分类是否合理 |

**最小成本做法**：
1. 写50张功能卡片（便利贴）
2. 找5个目标用户做开放分类
3. 合并5人的分类结果→取交集为核心导航

### Step 7：非功能需求定义

**8大非功能需求维度**：

| 维度 | 定义 | 量化指标 | 常见忽略后果 |
|------|------|----------|-------------|
| **性能** | 响应速度/吞吐量 | 页面加载<3s，API<500ms | 用户流失 |
| **可用性** | 系统正常运行时间 | 99.9%(年停机<8.76h) | SLA违约 |
| **安全性** | 数据保护/访问控制 | 等保2.0三级 | 数据泄露 |
| **可扩展性** | 用户/数据增长适应 | 支持10倍用户量 | 峰值崩溃 |
| **兼容性** | 浏览器/设备/系统 | Chrome/Safari/Edge+iOS/Android | 部分用户无法使用 |
| **可维护性** | 修改/部署的容易度 | 部署<30min，回滚<10min | 运维成本高 |
| **可访问性** | 无障碍使用 | WCAG 2.1 AA | 法律风险 |
| **本地化** | 多语言/多地区 | 中/英/日 → 本地货币/时区/法规 | 无法出海 |

**ToG必须非功能需求**：

| 维度 | ToG要求 | 说明 |
|------|---------|------|
| 安全性 | 等保2.0二级/三级 | 根据系统定级 |
| 可用性 | 99.99% | 关键系统要求4个9 |
| 兼容性 | 国产化适配 | 信创要求：麒麟/统信+龙芯/飞腾 |
| 审计 | 操作日志全留痕 | 6个月以上可追溯 |

### Step 8：需求跟踪矩阵(RTM)

**RTM模板**：

| 需求ID | 需求描述 | 来源 | KANO类型 | 优先级 | 用户故事 | 设计稿 | 开发状态 | 测试状态 | 验收结果 |
|--------|----------|------|----------|--------|----------|--------|----------|----------|----------|
| R001 | | | M/O/A | P0/P1/P2 | | | ☐未开始 ☐开发中 ☐完成 | ☐未测试 ☐通过 ☐失败 | ☐通过 ☐不通过 |

**RTM管理规则**：
- 每个需求必须可追溯到来源（用户/市场/战略）
- RTM从需求定义开始维护，直到验收完成
- 优先级变更必须同步更新RTM

### 服务设计：服务蓝图（Service Blueprint）

> **实战增强**：产品+服务一体化是ToG/ToB主流模式（如"智慧城市平台+运维服务"），服务蓝图是描述服务交付全流程的核心工具。

**服务蓝图 vs 用户旅程图**：

| 维度 | 用户旅程图(CJM) | 服务蓝图(Service Blueprint) |
|------|---------------|---------------------------|
| 关注点 | 用户视角的体验流程 | 服务交付的全链路（前台+后台） |
| 层级 | 用户看得见的部分 | 用户看得见+看不见的服务支撑 |
| 适用 | 产品功能体验设计 | 产品+服务一体化交付设计 |
| 典型场景 | App交互优化 | 平台上线+实施+运维+客服串联 |

**服务蓝图5层结构**：

```
┌─────────────────────────────────────────────────┐
│ 1. 客户行为层 (Customer Actions)                 │
│    客户在服务过程中的每一个动作                   │
│    示例：报修 → 等待 → 确认修复 → 评价           │
├─────────────────────────────────────────────────┤
│              ──互动线(Line of Interaction)──      │
├─────────────────────────────────────────────────┤
│ 2. 前台服务层 (Onstage)                          │
│    客户可见的服务人员/界面                       │
│    示例：客服电话/在线聊天/App界面               │
├─────────────────────────────────────────────────┤
│              ──可见线(Line of Visibility)──       │
├─────────────────────────────────────────────────┤
│ 3. 后台服务层 (Backstage)                        │
│    客户不可见但支持前台的工作                    │
│    示例：工单系统/工程师调度/库存管理            │
├─────────────────────────────────────────────────┤
│              ──内部交互线(Line of Internal)──     │
├─────────────────────────────────────────────────┤
│ 4. 支撑系统层 (Support Systems)                  │
│    基础设施/IT系统/第三方服务                    │
│    示例：CRM系统/支付网关/短信平台              │
├─────────────────────────────────────────────────┤
│ 5. 物理证据 (Physical Evidence)                  │
│    客户接触到的实物/数字证据                     │
│    示例：维修报告/发票/服务确认短信             │
```

**服务蓝图绘制4步法**：
```
Step 1：选择1个核心服务场景（如：客户报修→修复完成）
Step 2：从客户行为开始，按时间线画完
Step 3：加上前台→后台→支撑系统的对应动作
Step 4：标记关键指标（响应时间/SLA/满意度）和故障点（哪些环节容易断链）

投入：团队workshop 2-4小时
产出：1份服务蓝图 + 3-5个待优化瓶颈
```

**ToG/ToB服务蓝图典型场景**：

| 场景 | 关键发现 | 优化动作 |
|------|---------|---------|
| 客户报修流程 | 工单在客服→技术→现场3次转手 | 统一工单平台，减少转手次数 |
| 新客户上线 | 销售→实施→运维交接环节断裂 | 指定客户成功经理贯穿全程 |
| 版本升级 | 通知→测试→部署→验证链路长 | 自动化部署+灰度发布 |

## 踩坑预警

| # | 坑点 | 表现 | 规避 |
|---|------|------|------|
| 1 | **照搬用户原话当需求** | "用户说要XX功能"直接写进PRD | 用Y模型分析，区分表面需求vs真实需求 |
| 2 | **跳过KANO直接排优先级** | 所有需求都是"高优先级" | 必须先KANO分类再排优先级 |
| 3 | **非功能需求忽略** | 只写功能需求不写性能/安全 | 8大维度逐项检查 |
| 4 | **验收标准模糊** | "体验流畅""操作简单" | 用Given-When-Then格式写可测试的AC |
| 5 | **需求无追溯** | 不知道某个需求从哪来的 | RTM必须关联需求来源 |
| 6 | **信息架构凭直觉** | PM自己拍导航结构 | 至少做5人卡片分类 |

## 政企产品专项支持（ToG/ToB）

### ToG需求分析特殊方法

**政策解读→业务需求→功能需求三步法**：

```
Step 1: 政策解读
  政策文件："推进智慧社区建设，实现社区管理数字化"
  提取关键词：智慧社区、数字化管理

Step 2: 业务需求
  业务场景：社区人员/车辆/设备的数字化管理
  业务目标：管理效率提升30%，人工成本降低20%

Step 3: 功能需求
  功能1：人员出入管理（人脸识别+访客登记）
  功能2：车辆出入管理（车牌识别+车位管理）
  功能3：设备监控告警（IoT设备状态监控+异常告警）
```

### ToB需求分析特殊考量

| 维度 | ToB差异 | 实操要点 |
|------|---------|----------|
| 需求来源 | 3类人(决策者/影响者/使用者)需求可能矛盾 | 分别收集，冲突时决策者优先 |
| 定制化 | KA定制需求vs标准产品需求 | 定制需求≤20%，否则产品化失败 |
| 非功能 | SLA要求严格 | 提前定义SLA等级+违约条款 |

## 核心原则

1. **Y模型是需求分析的灵魂**——用户说"要一匹更快的马"不是真要马，是要更快到达
2. **KANO先于优先级**——不做KANO分类就排优先级=盲排
3. **INVEST是用户故事的质量门**——不符合INVEST的用户故事不允许进Sprint
4. **非功能需求不能忘**——功能决定"能不能用"，非功能决定"好不好用/安不安全"
5. **RTM从第一天开始维护**——需求无追溯=后期无法验证
