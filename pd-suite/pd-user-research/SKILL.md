# pd-user-research · 用户研究与需求洞察

> **核心定位**：回答"用户真正要什么"——从表面需求挖到深层动机，避免做用户说不要但真正需要的产品。
> **NPDP对标**：Ch4 市场研究（定性方法+用户洞察）+ 发现阶段

## 法规与标准依据

| 标准/框架 | 关联内容 |
|-----------|----------|
| NPDP Body of Knowledge | Ch4 发现与交付阶段、VOC(客户之声) |
| JTBD理论 | Christensen"雇佣"理论三层模型 |
| Norman用户心理模型 | 执行评估7阶段 |
| 老妈测试原则 | Rob Fitzpatrick《老妈测试》 |

## 核心工作流程

### Step 1：识别关键假设

**假设映射表**（在花时间做研究之前，先搞清楚你在假设什么）：

| # | 假设描述 | 风险等级(高/中/低) | 验证方法 | 验证成本 |
|---|----------|-------------------|----------|----------|
| 1 | 用户有X痛点 | 高 | 访谈8人 | 0 |
| 2 | 用户愿为Y付费 | 高 | 访谈+着陆页 | <5000 |
| 3 | 用户会用Z方式使用 | 中 | 原型测试 | 1-3万 |

**实操规则**：
- 列出所有假设，按风险排序
- 先验证高风险假设（如果假设错了，产品就不成立）
- 低风险假设可后续验证或直接跳过

### Step 2：用户画像(Persona)

**Persona不是人口统计，是行为画像**：

| 维度 | ❌ 错误做法 | ✅ 正确做法 |
|------|-----------|-----------|
| 年龄 | "25-35岁" | "刚晋升为管理者的技术骨干" |
| 需求 | "需要高效工具" | "每周花3小时做周报，觉得是浪费" |
| 目标 | "提高效率" | "减少80%重复性数据整理时间" |
| 痛点 | "操作复杂" | "在3个系统间切换复制数据" |

**Persona模板**：

```
┌──────────────────────────────────────────┐
│  Persona：[名字+标签]                      │
│  如：老张 · 焦虑的园区运营主管               │
├──────────────────────────────────────────┤
│  背景：                                    │
│  - 职务/角色：_________                    │
│  - 工作场景：_________                     │
│  - 技术水平：_________                     │
│                                            │
│  目标(Goals)：                             │
│  1. _________                             │
│  2. _________                             │
│                                            │
│  痛点(Pain Points)：                       │
│  1. _________                             │
│  2. _________                             │
│  3. _________                             │
│                                            │
│  行为特征：                                 │
│  - 信息获取：_________                     │
│  - 决策方式：_________                     │
│  - 使用频率：_________                     │
│                                            │
│  与产品的交互点：                           │
│  1. _________                             │
│  2. _________                             │
└──────────────────────────────────────────┘
```

**Persona数量**：3-5个，覆盖80%目标用户即可。超过5个=没聚焦。

### Step 3：用户旅程地图(CJM)

```
┌─────────────────────────────────────────────────────────┐
│ Persona：_______  场景：_______                           │
├─────────┬─────────┬─────────┬─────────┬─────────────────┤
│ 阶段     │ 认知     │ 考虑     │ 使用     │ 续约/推荐       │
├─────────┼─────────┼─────────┼─────────┼─────────────────┤
│ 行为     │         │         │         │                 │
│ "我在做" │         │         │         │                 │
├─────────┼─────────┼─────────┼─────────┼─────────────────┤
│ 触点     │         │         │         │                 │
│ "我接触" │         │         │         │                 │
├─────────┼─────────┼─────────┼─────────┼─────────────────┤
│ 情绪     │ 😐      │ 😟      │ 😊      │ 😃              │
│ "我感觉" │         │         │         │                 │
├─────────┼─────────┼─────────┼─────────┼─────────────────┤
│ 痛点     │         │ 🔴      │         │ 🔴              │
│ "我卡在" │         │         │         │                 │
├─────────┼─────────┼─────────┼─────────┼─────────────────┤
│ 机会     │         │         │ 🟢      │ 🟢              │
│ "我们可以"│         │         │         │                 │
└─────────┴─────────┴─────────┴─────────┴─────────────────┘
```

**CJM实操要点**：
- 基于5-8次用户访谈的真实行为，不是产品经理的想象
- 痛点(🔴)是产品机会，机会(🟢)是差异化卖点
- 旅程阶段数量=3-7个，太少看不清，太多太碎片

### Step 4：JTBD需求洞察（Jobs To Be Done）

**JTBD三层模型**：

| 层次 | 问题 | 示例 |
|------|------|------|
| **功能型Job** | 用户要完成什么任务？ | "我需要管理门禁设备" |
| **情感型Job** | 用户想获得什么感受？ | "我不想每天被领导问'那个门怎么又坏了'" |
| **社会型Job** | 用户想被别人怎么看？ | "我想在领导面前显得专业、可靠" |

**JTBD陈述公式**：
```
当 [情境] 时，我想要 [动机]，
以便于 [期望结果]。
```

**实操示例**：
```
当 设备频繁故障被投诉 时，我想要 提前收到预警，
以便于 在领导问起之前我已经在处理了。

→ 产品方向：预测性维护/智能预警，而非被动报修
```

**⚠️ 关键**：功能型Job是表层需求（竞品都能满足），情感型+社会型Job才是差异化机会。

### Step 5：客户访谈

**访谈脚本模板（30-45分钟）**：

```
开场（5min）：
- 感谢参与，说明目的（"不是卖东西，是理解您的工作"）
- 录音许可

行为挖掘（20min）——核心！
- "能描述一下上次做[任务]的过程吗？" ← 最重要的1个问题
- "当时是什么情况？"
- "然后呢？"
- "最麻烦/最耗时的是哪个环节？"
- "后来怎么解决的？"

痛点深挖（10min）：
- "如果有个工具能帮您解决这个问题，您觉得最重要的是什么？"
- "现在有没有用什么方法/工具解决这个问题？效果怎么样？"
- "这个问题一个月出现几次？"

付费意愿试探（5min）：
- "如果有个产品能解决[痛点]，您觉得值多少钱/预算大概多少？"
- "您目前在这方面的年支出大约多少？"

结束（5min）：
- "还有什么想补充的吗？"
- "能推荐2-3个有类似问题的同事吗？" ← 滚雪球招募
```

**老妈测试原则**（The Mom Test）：

| ❌ 不要问 | ✅ 应该问 | 原因 |
|----------|----------|------|
| "你觉得这个功能怎么样？" | "你上次做这个任务是什么时候？" | 前者问观点（讨好式回答），后者问事实 |
| "你会用这个产品吗？" | "你现在用什么解决这个问题？" | 前者问意愿（90%会说会），后者问行为 |
| "你觉得定价多少合适？" | "你去年在这上面花了多少钱？" | 前者问心理价（会压低），后者问实际支出 |
| "你需要X功能吗？" | "上次遇到X问题你怎么处理的？" | 前者问假想需求，后者问真实行为 |

**核心原则**：**问过去的行为，不问未来的意愿。** 人们对未来的预测从来都不准。

### Step 6：可用性测试

**5人法则**：5个用户能发现85%的可用性问题，不需要更多。

**测试脚本**：

```
任务1：[具体任务描述，不给操作步骤]
  "请你完成______"
  ☐ 能独立完成  ☐ 需要提示  ☐ 完成失败
  耗时：____秒   错误次数：____次

任务2：[具体任务描述]
  "请你完成______"
  ☐ 能独立完成  ☐ 需要提示  ☐ 完成失败
  耗时：____秒   错误次数：____次

任务3：[具体任务描述]
  "请你完成______"
  ☐ 能独立完成  ☐ 需要提示  ☐ 完成失败
  耗时：____秒   错误次数：____次

整体评价：
SUS评分：______（>68分为良好）
最严重的问题：________
```

### Step 7：机会方案树(OST)

```
                    产品愿景
                       │
           ┌───────────┼───────────┐
           │           │           │
        机会1        机会2        机会3
        (用户痛点)   (用户痛点)   (用户痛点)
           │           │           │
      ┌────┼────┐  ┌──┴──┐    ┌──┴──┐
      │    │    │  │     │    │     │
    方案A 方案B 方案C 方案D 方案E 方案F 方案G

选择规则：
- 先选机会（哪个痛点最大/最普遍）
- 再选方案（哪个方案可行性最高）
- 不要过早锁定单一方案
```

### 领先用户分析（Lead User Research）

> **NPDP Ch4核心**：von Hippel的领先用户（Lead User）理论——具有超前需求且能从解决方案中获益的用户，是重要创新来源。

**领先用户 vs 普通用户 vs 极端用户**：

| 用户类型 | 特征 | 在产品研究中的价值 | 举例 |
|---------|------|------------------|------|
| **普通用户** | 当前需求、当前场景 | 验证现有功能是否好用 | 正常使用视频监控的保安 |
| **极端用户** | 极端场景、边缘需求 | 发现产品极限和鲁棒性 | 同时看64路视频的监控中心 |
| **领先用户** | 超前需求、高收益预期 | **发现未来主流需求** | 已自建AI预警系统的安防运维主管 |

**领先用户2个识别标准**：
1. **超前需求**：领先用户面临的需求，将是市场主流用户几个月/几年后面临的需求
2. **高收益预期**：领先用户预期从解决方案中获得显著收益，因此有强烈动机参与

**领先用户 vs 早期采用者（重要区别）**：

| 维度 | 领先用户 | 早期采用者 |
|------|---------|-----------|
| 时间 | 需求超前于市场 | 采用行为早于大众 |
| 驱动 | 从解决方案中获益 | 对新技术感兴趣 |
| 行为 | 可能已自己开发workaround | 购买并使用早期产品 |
| 研究价值 | **创新来源**（告诉你做什么） | **验证来源**（告诉你做对了没） |

**领先用户工作坊4步法**：
```
Step 1：识别（筛选满足2个标准的用户，通常3-5人）
Step 2：共创（与领先用户共同设计解决方案原型，1-2天workshop）
Step 3：验证（将共创方案与普通用户验证，看是否也有需求）
Step 4：转化（将已验证的方案纳入产品路线图）

投入：1-2天workshop + 1周验证
产出：1-3个高价值创新概念/功能方向
```

## 能力模块：录音 / 文本 PM 洞察抽取（Insight Extraction）

> **本能力可被其他 SKILL 直接调用**（调用约定见 §6）。
> **来源**：从外部 AI PM 工具集（ai-pm-exploration-toolkit）音频智能流水线提取并适配，剥离 Whisper/Docker 依赖，仅保留与部署无关的方法论与规则。详细词表与报告模板见 `references/insight-extraction.md`。

### 1. 功能（What it does）

把**真实录音的转写文本**（用户访谈、干系人会议、产品演示、竞品情报、语音备忘、客服电话），按 PM 场景自动抽取结构化洞察。采用**轻量规则法**（关键词/句式匹配），无需大模型即可运行，结果确定、可复现、可审计。

- **输入**：`{ text: 转写文本, use_case: 场景标识 }`
- **处理**：按 `use_case` 选抽取维度 → 关键词/句式匹配（句级）→ 去重取 Top-5
- **输出**：`{ 结构化洞察清单(按维度分栏), Markdown 格式化报告, 相关性评分 }`

### 2. 解决的问题（Why it exists）

| 痛点 | 传统做法 | 本能力 |
|------|---------|--------|
| 访谈/会议录音堆积，人工听写归纳慢且易漏 | 逐条听写，数天 | 分钟级出四栏结构化洞察 |
| 会议纪要黑洞：决策/行动项/风险常丢失 | 会后才补，记忆偏差 | 自动抽决策/行动项/风险/下一步 |
| 竞品/客服/演示反馈无人系统整理 | 散落各人笔记 | 标准化维度沉淀为情报库 |
| 录音资产不可搜索 | 存在本地无人看 | 结构化后可检索、可聚合 |

### 3. 什么情况下使用（When to use）

✅ **使用**：
- 已有一段**真实转写文本**（或音频已转写），需要快速得到 PM 结构化洞察
- 场景属于六类之一：用户访谈 / 干系人会议 / 产品演示 / 竞品研究 / 语音备忘 / 客服电话
- 需要把零散反馈喂入 PRD 需求池、backlog、或会议纪要

❌ **不使用（改走本技能其它步骤）**：
- **没有真实素材、想"造"用户** → 走 Step 2 Persona（基于真实访谈，**禁止随机生成**）
- 需要深层动机挖掘 → 走 Step 4 JTBD / Step 5 客户访谈（本能力只做表层关键词抽取）

### 4. 六类场景速览

| use_case | 场景 | 抽取维度 |
|----------|------|---------|
| `user_interview` | 用户访谈 | 痛点 / 功能请求 / 用户目标 / 可用性问题 |
| `stakeholder_meeting` | 干系人会议 | 决策 / 行动项 / 风险担忧 / 下一步 |
| `demo_feedback` | 产品演示 | 反应 / 提问 / 改进建议 / 正向反馈 |
| `competitive_research` | 竞品研究 | 功能 / 定价 / 定位 / 优劣势 |
| `voice_memo` | 语音备忘 | 关键想法 / 行动项 / 跟进 / 任务分类 |
| `customer_support` | 客服电话 | 痛点 / 功能请求 / 用户目标 / 可用性问题 + 情绪层 |

> 完整关键词词表、报告模板、原项目未实现而本次补全的 `competitive_research`/`voice_memo` 词表，见 `references/insight-extraction.md`。

### 5. 调用示例

**输入**（用户访谈转写片段）：
```
text: "Our users struggle to find the export button. I wish we could add batch export.
       What goal are they trying to accomplish? Reduce weekly reporting time."
use_case: "user_interview"
```
**输出**：
```
insights:
  pain_points:      ["Our users struggle to find the export button."]
  feature_requests: ["I wish we could add batch export."]
  user_goals:       ["...trying to accomplish? Reduce weekly reporting time."]
report:  "# 用户访谈洞察\n## 用户痛点\n1. Our users struggle to find the export button.\n..."
relevance: "medium"
```


## 即用工具

### 工具1：5人快速验证法

```
Day 1: 招募5个目标用户（通过社群/朋友/同事介绍）
Day 2-3: 5次30分钟访谈（严格执行老妈测试原则）
Day 4: 整理洞察（找共性痛点+付费意愿信号）
Day 5: 决策——验证通过进入下一阶段，验证失败调整方向
```

| # | 假设 | 验证方法 | 结果 | 下一步 |
|---|------|----------|------|--------|
| 1 | | | ☐通过 ☐未通过 ☐不确定 | |
| 2 | | | ☐通过 ☐未通过 ☐不确定 | |
| 3 | | | ☐通过 ☐未通过 ☐不确定 | |

**规则**：所有高风险假设通过→进入产品规划；任一高风险假设未通过→要么验证方法有问题，要么假设有错。

## 踩坑预警

| # | 坑点 | 表现 | 规避 |
|---|------|------|------|
| 1 | **用户说想要但不用** | 访谈时都说好，上线没人用 | 用老妈测试原则问行为，不问意愿 |
| 2 | **Persona=虚构人物** | 凭想象画用户画像 | Persona必须基于5+次真实访谈 |
| 3 | **只做功能型JTBD** | "用户需要管理设备"→做管理系统 | 挖到情感型/社会型Job才有差异化 |
| 4 | **问引导性问题** | "你觉得这个功能好不好？" | 用开放式问题："上次怎么做的？" |
| 5 | **5个人不够** | "5个人能代表什么？" | 5人发现85%问题，15人发现100%，性价比5人最优 |
| 6 | **验证一次就信了** | 5人说好就认为市场验证通过 | 不同渠道验证2-3次再信 |
| 7 | **CJM变成产品经理的自嗨** | 旅程是PM想象的不是用户真实行为 | CJM必须标注"数据来源：XX访谈" |

## 政企产品专项支持（ToG/ToB）

### ToG用户研究特殊方法

| 维度 | ToG差异 | 实操要点 |
|------|---------|----------|
| 访谈对象 | 决策者≠使用者 | 必须分别访谈决策者(局长/主任)和使用者(科员/网格员) |
| 访谈难度 | 政府人员难约、说话保守 | 通过关系介绍+提前发访谈提纲+现场观察补充 |
| Persona | 政府组织角色为主 | 按职级+职能画Persona(决策者/执行者/监督者) |
| CJM | 多角色交叉旅程 | 画"部门协作旅程"而非个人旅程 |
| JTBD | 社会型Job很强 | "不犯错"比"做得好"更重要→合规/留痕是刚需 |

**ToG访谈特殊话术**：
```
❌ "您觉得这个系统怎么样？"（政府人员会说"挺好的"）
✅ "上次XX事件处理中，系统帮上忙了吗？哪个环节最费时间？"
✅ "如果有笔预算改善这个系统，您最想改善哪个环节？"
✅ "其他单位有类似问题吗？他们怎么解决的？"（通过同行案例获取真实信息）
```

### ToB用户研究特殊考量

| 维度 | ToB差异 | 实操要点 |
|------|---------|----------|
| 访谈对象 | 3类：决策者/影响者/使用者 | 3类都需访谈，需求可能矛盾 |
| JTBD | 组织型Job | "让团队效率提升20%"比个人效率更重要 |
| 验证方式 | POC>原型测试 | ToB客户更接受POC而非低保真原型 |
| 痛点量化 | ROI驱动 | "节省XX人天/年"比"体验更好"更有说服力 |

## 核心原则

1. **问行为不问意愿**——用户对未来说的都是假话，对过去说的才是真话（老妈测试）
2. **5个人够了**——5人发现85%问题，性价比最高
3. **挖到情感型Job才有差异化**——功能型Job谁都能做，情感型/社会型Job是护城河
4. **Persona基于真实访谈**——凭想象画的Persona比没有更危险
5. **验证假设而非确认假设**——去证明自己错了，而不是证明自己对了
6. **ToG访谈问行为不问评价**——政府人员默认"挺好的"，必须问具体事件和流程
