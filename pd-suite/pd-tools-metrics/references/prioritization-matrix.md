# 优先级排序矩阵（Prioritization Matrix）

> 用途：多维度量化排序需求优先级，替代拍脑袋决策。
> 适用场景：需求池排序、版本规划、资源分配决策。
> 对标：NPDP Ch6 工具与度量 + `pd-tools-metrics` Step 2

---

## 一、ICE 评分矩阵（最常用，推荐）

| 需求ID | 需求描述 | Impact(影响) 1-10 | Confidence(信心) 1-10 | Ease(容易度) 1-10 | ICE得分 | 优先级 |
|--------|---------|---------------------|--------------------------|---------------------|-----------|--------|
| REQ-001 | [需求] | | | | I×C×E = |
| REQ-002 | | | | | |
| REQ-003 | | | | | |

> **ICE 计算**：得分 = Impact × Confidence × Ease（不除以3，保留绝对值方便排序）
> **评分标准**：
> - Impact：1=仅影响个别用户，10=影响全部用户/核心指标
> - Confidence：1=纯猜测，10=有数据验证
> - Ease：1=需要3个月，10=1天就能做完

---

## 二、RICE 评分矩阵（资源受限时用）

| 需求ID | Reach(触达人数/周期) | Impact(影响) 1-10 | Confidence(信心) 1-10 | Ease(人天) | RICE得分 | 优先级 |
|--------|---------------------|---------------------|--------------------------|--------------|-----------|--------|
| REQ-001 | | | | | R×I×C/E = |
| REQ-002 | | | | | |

> **RICE 计算**：得分 = Reach × Impact × Confidence / Ease
> 与 ICE 的区别：RICE 引入 Reach（触达人数）和 Ease 作分母（成本越高得分越低）

---

## 三、MoSCoW 分类矩阵（向业务方汇报用）

| 分类 | 定义 | 本版本需求清单 | 版本目标占比 |
|--------|------|--------------|-------------|
| **M**ust have（必须有） | 没有就无法发布 | [REQ-001, REQ-002] | 60% |
| **S**hould have（应该有） | 很重要但不是阻塞 | [REQ-003, REQ-004] | 20% |
| **C**ould have（可以有） | 有了更好，没有也行 | [REQ-005] | 15% |
| **W**on't have（本次不做） | 明确排除，下版本再说 | [REQ-006, REQ-007] | 5% |

> **向业务方汇报技巧**：先展示 MoSCoW 分类，再展开 ICE/RICE 具体得分，避免被质疑"为什么XX排后面"

## 四、加权评分矩阵（自定义维度，最灵活）

**Step 1：定义评分维度（根据你的产品特点定制）**

| 维度 | 权重 | 评分标准（0-10分） |
|--------|------|---------------------|
| 用户价值 | 30% | 0=无价值，10=核心痛点 |
| 战略契合度 | 25% | 0=无关，10=完全契合年度OKR |
| 技术可行性 | 20% | 0=做不到，10=现成方案 |
| 开发成本（反向） | 15% | 0=需要3个月，10=3天搞定 |
| 竞品对标 | 10% | 0=竞品都没有，10=竞品都有我们必须有 |

## 五、KANO + 优先级交叉矩阵

| 需求 | KANO类别 | ICE得分 | 最终优先级 | 理由 |
|--------|----------|-----------|------------|------|
| REQ-001 | 基本型（必须有） | 180 | **P0** | 没有用户会骂 |
| REQ-002 | 期望型 | 240 | **P0** | 有了满意度显著提升 |
| REQ-003 | 魅力型 | 120 | **P1** | 有了惊喜，但没有不扣分 |
| REQ-004 | 无差异型 | 60 | **P2** | 做不做没区别 |
| REQ-005 | 反向型 | - | **排除** | 做了用户更不满意 |

> **规则**：KANO 基本型/期望型自动升一级优先级，魅力型可延后

## 六、3 种矩阵选择指南

| 场景 | 推荐矩阵 | 理由 |
|--------|-----------|------|
| 初创产品/快速迭代 | ICE | 简单，3个维度，15分钟出结果 |
| 资源紧张/需要向老板汇报ROI | RICE | 引入 Reach 和 Effort，更量化 |
| 业务方对优先级有争议 | MoSCoW | 分类法，容易达成共识 |
| 多维度复杂决策（ToG/大B） | 加权评分矩阵 | 可定制维度，最严谨 |
| 已有 KANO 分析结果 | KANO + 优先级交叉 | 双重验证，避免遗漏基本型需求 |

## 七、输出交付物检查清单

- [ ] 评分维度已确定（ICE/RICE/MoSCoW/加权）
- [ ] 所有 P0/P1 需求已评分（≥3人独立打分取平均）
- [ ] 争议需求（分差<20%）已组织讨论对齐
- [ ] 最终排序已同步到需求管理工具（PingCode/Jira/Tapd）
- [ ] 版本规划已根据优先级排序制定（P0 必须在本版本，P1 尽量，P2 看资源）
