# law-repository — 中央法规库（法律内容基础设施）

> 定位：legal-suite 的**单一事实来源**（Single Source of Truth）。按用户需求 #1 承载**完整三层**内容：**L1 原文层**（法律/法规/司法解释/部门规章原文快照，含版本元数据）、**L2 领域解读层**（官方释义/权威实务解读）、**L3 案例引用层**（指导案例/公报案例/典型案例要旨）。
> **解耦边界**：行业技能内的「场景化蒸馏数据」（如 law-skills 的 A3/A9 法条、pm-bid 的法规依据）属独立「初始数据」，**不迁入本库、不删除**，库补全后建立「引用库原文+溯源」正向闭环（而非把蒸馏数据塞进库）。本库存「原文/解读/案例」权威内容，技能层存「场景化蒸馏」可执行内容。
> 治理身份：**不占技能编号**（同 perspective-kernel / business-underlying-logic 模式），作为数据基础设施挂在 legal-suite 下，纳入 GOV_SkillGovernance v3.6 管辖（QG4 数据溯源 / QG6 变更管理）。

## 目录结构

```
legal-suite/law-repository/                 ← 中央法规库（data 基础设施，不占技能编号）
├── README.md              ← 本文件（定位 + 三层架构 + 更新规程）
├── law-manifest.md        ← 法规清单（已入库/待补/待核），唯一盘点入口
├── laws/                  ← 【L1 原文层】法律/法规/司法解释/部门规章原文快照（一部法一个 .md，含版本戳）
│   └── <法律名称>_<版本>.md
├── L2-interpretation/     ← 【L2 领域解读层】官方释义/权威实务解读（README 规范的文件头）
│   └── <主题>_解读_<来源>.md
├── L3-case/              ← 【L3 案例引用层】指导案例/公报案例要旨（README 规范的文件头）
│   └── <案由>_案例_<案号>.md
├── registry/             ← 反向登记（蒸馏数据 → 库原文 的可追溯链路）
│   └── reverse-registry.md
└── sources/              ← 原始来源归档（PDF 等），保溯源
```

## 文件头规范（强制）

每个 laws/ 下的 .md 必须带 YAML frontmatter：

```yaml
---
法律名称: 中华人民共和国招标投标法
层级: 法律            # 法律 / 行政法规 / 部门规章 / 司法解释 / 地方性法规
现行版本: 2017修订
版本说明: <通过/修订/施行的时间与会议信息，缺失则标"待核实">
施行日期: 2017-12-28   # 缺失标"待核实"
快照日期: 2026-08-31   # 本文件入库/核对日期
来源: <发布机构 + 文档形态>
来源文件: ../sources/<原始文件名>   # 无原件可指时标"无原件（在线来源）"
状态: 新鲜            # 新鲜 / 待核(180天) / 待核(版本待核实) / 已废止
规模: 6章 68条
---
```

**不杜撰原则**：版本信息（文号/年份/施行日期）缺失时一律标「待核实」，禁止编造。文本内容保持提取原样（含少量 reflow 合并瑕疵），不做语义改写。

## 更新规程（六条）

1. **仅人工触发**：不自动抓取。任何更新由用户在真实会话中下令（"更新X法"），或 AI 检出下游引用失效时提请用户触发。
2. **三粒度**：
   - 单法更新：核对一部法的现行版本，更新快照与 frontmatter
   - 分片更新：核对某个领域（如招投标领域全部4部）
   - 全量审计：对照 law-manifest.md 逐条核对（建议每季度一次）
3. **180天阈值**：快照日期距今超过180天 → 状态改「待核(180天)」，提示优先级链上的下游技能注意。
4. **git 一更新一 commit**：每次更新独立 commit，commit message 含法规名+版本变化（旧版→新版），可回滚。
5. **级联标记**：某法原文变更（修订/废止）→ 在 law-manifest.md 该法条目的「下游引用」列登记受影响技能 → 受影响技能自己的引用处加「⚠️ 上游已更新」标记。反向同理：行业技能发现场景缺口（缺某法/某司法解释）→ 在 manifest「待补」区登记 → 人工补充入库。
6. **优先级链**：官方网站原文（人大网/中国政府网）> 官方汇编PDF（政府交易平台发布）> 权威转载（律所/平台全文）。每级须在 frontmatter「来源」中如实记录级别。

## 数据流（三层库 × 技能蒸馏层 的关系）

```
[L1 laws/ 原文] ──┐
[L2 解读/] ───────┼──蒸馏(引用+溯源标注)──> 行业技能蒸馏层(初始数据，独立不删)
[L3 案例/] ──┘        (A3/A9 / pm-bid 法规依据 / references)
      ^                                            |
      └──── 反向登记(缺口→manifest待补 / 引用→registry) ←─┘
```

- **正向（蒸馏）**：行业技能引用库内 L1/L2/L3 做场景化解读时，必须标注「来源：law-repository/<层>/<文件名>（快照日期）」。
- **反向（缺口登记）**：技能使用中发现库内缺某法/某司法解释/某案例 → 在 law-manifest.md「待补」登记 → 人工补库 → 在 registry/reverse-registry.md 登记引用关系；库更新时据此级联通知下游技能。

## 数据源策略（2026-09-01 评估结论）

经实测评估（2026-09-01），对国家法律法规数据库（flk.npc.gov.cn）官方接口与开源镜像做对比，确定如下数据源策略：

**1. 主源：开源镜像（git 同步，每周自动更新）**
- `china-law-db`（GitHub: qisehong/china-law-db）：YAML frontmatter + Markdown 单法文件，源自国家法律法规数据库，MIT 许可。
- `laws-data`（GitHub: 13098806890/laws-data）：结构化 JSON/SQLite/Markdown 全文（2,377 部，含司法解释 1,157 + 公报案例），源自国家法律法规数据库，MIT 许可。
- 二者文本均源自官方公开渠道（法律文本属公有领域，见著作权法第5条），维护成本极低（`git pull` 即同步），是法规库补全与待核稿转正的首选数据源。

- **本地镜像落地（2026-09-01）**：已 fork 至 `lizhijun48/laws-data`，本地克隆于 `D:\00_Lee\00-相关资料\00_laws-data`（**独立 git 仓库，不在 skills 治理树内**，避免污染 Skills_Lzj）；上游 `13098806890/laws-data`。同步脚本：`law-repository/sync-laws-data.ps1`（`git pull upstream main && git push origin main`）。

**2. 降级：flk 官方仅人工核验/补漏**
- 实测：`POST /api/` 返回 405；旧 `GET /api/` 已返回 SPA 空白页（官网改版，无开放 API 契约）。程序化调用随时失效、维护不可控。
- 故 flk 不再程序化调用，仅作为需要最新/罕见法条时的人工访问核验通道。

**3. 待核稿转正流程（本库标准动作）**
1. 从主源镜像取对应法的权威结构化全文（Markdown/JSON）；
2. 对照写入 `laws/<法名>_<版本>.md`，frontmatter `状态` 由 `待核(知识起草·待官方核验)` 改为 `新鲜`，`来源` 记主源镜像 + 同步日期，`核实` 记 `已对照开源镜像(china-law-db/laws-data)转正`；
3. 在 `law-manifest.md` 该条目状态改「已入库（新鲜）」，在 `registry/reverse-registry.md` 补/核引用登记；
4. 一更新一 commit（commit message 含法规名+版本变化）。

## 已知限制（2026-08-31 建库时点）

- 在线官方 API 不可用（flk.npc.gov.cn 改版无契约，实测 POST 405 / 旧 GET 返回 SPA），已评估并确定**主源切换为开源镜像（china-law-db / laws-data）**、flk 降级为人工核验（详见「数据源策略」）。原标「待核」的 8 部待核稿可按该流程转正。
- 现有 4 部入库文件来自机器提取（pypdf + 页面切片），段落 reflow 存在少量章标题与首条合并现象（如"第六章附则第六十五条…"），**不影响检索与引用，后续优化**。
