# 法规库架构与逻辑说明（law-repository）

> 文档性质：**架构与逻辑说明**。与同目录 `README.md`（操作手册，讲"怎么做"）互补——本文件讲"是什么、为什么"。
> 适用范围：`legal-suite/law-repository/`
> 关联治理：`GOV_SkillGovernance v3.6`（QG4 数据溯源 / QG6 变更管理）
> 最后更新：2026-09-01

---

## 1. 一句话定位

`law-repository` 是 `legal-suite` 的**中央法规库**，也是整个技能体系的**单一事实来源（SSOT）数据基础设施**。它只承载"有法律/实务权威性的原文、解读、案例"，**不承载**"场景化蒸馏的可执行内容"。

---

## 2. 为什么需要它（解决的问题）

| 问题 | 本库的解法 |
|---|---|
| 法条来源分散、版本混乱——各行业技能各自内嵌法条，版本一更新难全网同步 | 集中存权威原文 + 版本元数据，技能改为"引用库原文+溯源" |
| 蒸馏数据 vs 权威原文耦合——库不全时蒸馏不敢用、库全时蒸馏被吞 | **解耦**：技能蒸馏数据独立存在、照常使用；库补全后建立溯源，而非把蒸馏塞进库 |
| 库缺口无反馈闭环 | 技能发现缺某法 → 登记缺口 → 反向推动补库（见 §5） |

---

## 3. 三层架构模型

法规库按"权威度 + 内容形态"分三层，全部落在库内（对齐用户需求 #1：原文、司法解释、领域解读、案例引用同库）。

### L1 原文层（`laws/`）
- **内容**：法律 / 行政法规 / 司法解释原文 / 部门规章原文——一切"有法律效力的权威文本"。
- **颗粒度**：一部法一个 `.md`，文件名含版本戳（如 `招标投标法_2017修订.md`）。
- **硬边界**：只存原文，不含任何解读、不含案例、不含场景化改写。

### L2 领域解读层（`L2-interpretation/`）
- **内容**：官方释义、权威实务解读、学理解释汇编——无独立法律效力，但有强实务指引价值。
- **硬边界**：是对 L1 原文的"解读"，不是原文本身；每个文件必须 `关联原文:` 指向 L1 某文件。

### L3 案例引用层（`L3-case/`）
- **内容**：指导案例 / 公报案例 / 典型案例的裁判要旨与引用锚点（案号、来源）。
- **硬边界**：是"具体案件裁判"，每个文件必须 `关联原文:` 登记本案援引的 L1 法条（反向登记入口）。

**三层关系**：L1 是根，L2/L3 依附于 L1；行业技能蒸馏层依附于 L1/L2/L3。越往下越"场景化"，越往上越"权威"。

---

## 4. 核心解耦逻辑（最关键的边界）

> **技能蒸馏数据 ≠ 法规库内容。**

- 技能层（如 `law-skills` 的 A3/A9 内嵌法条、`pm-bid-proposal` 的招标投标法规依据、各 `references/*.md`）里的是**场景化蒸馏的初始数据**。按用户纠正：这是独立资产，**不删、不迁、不阻塞**。
- 法规库是"权威原文/解读/案例"的**溯源层**。
- **库未补全时**：蒸馏数据照常使用，业务不受影响。
- **库补全后**：蒸馏引用库原文时加"来源标注"（正向闭环），**而非把蒸馏搬进库**。

这条边界解决了"下沉是否等于删除"的疑虑——下沉是"建立引用关系"，初始数据原样保留。

---

## 5. 双向闭环逻辑

```
        ┌──────────── 正向（蒸馏引用库）────────────┐
        │                                           ↓
  [行业技能蒸馏数据]                           [L1 原文 / L2 解读 / L3 案例]
        ↑                                           │
        └──────────── 反向（缺口登记）──────────────┘
                  (manifest 待补区 / registry 反向登记)
```

### 正向（蒸馏引用库）
技能引用库内 L1/L2/L3 时，必须标注：`来源：law-repository/<层>/<文件名>（快照日期）`。
→ 保证每条蒸馏都可溯源到权威原文，版本一变即可级联发现。

### 反向（缺口登记）
技能使用中发现库缺某法 / 某司法解释 / 某案例 →
1. 在 `law-manifest.md`「待补」区登记（含优先级 P0~P3）；
2. 人工补库后，在 `registry/reverse-registry.md` 登记"该蒸馏数据 ← 依赖库内哪部法"；
3. 库某法修订/废止时，查 registry 找下游技能 → 在技能引用处加「⚠️ 上游已更新」标记。
→ 实现用户需求 #2："新要求反向推动法规库更新机制"。

---

## 6. 版本迭代机制（六条要点）

详细规程见 `README.md`「更新规程」。要点：

1. **仅人工触发**：不自动抓取；由用户下令或 AI 检出失效时提请。
2. **三粒度**：单法更新 / 分片更新（某领域）/ 全量审计（每季度）。
3. **180 天阈值**：快照超 180 天 → 状态改「待核」，提示下游技能。
4. **git 一更新一 commit**：commit message 含法规名 + 版本变化，可回滚。
5. **级联标记**：原文变更 → manifest 登记下游 → 技能加「⚠️」；反向同理。
6. **优先级链**：人大网/中国政府网原文 > 官方汇编 PDF > 权威转载（frontmatter「来源」如实记级别）。

**不杜撰原则**：版本文号/年份/施行日期缺失一律标「待核实」，禁止编造；文本保持提取原样，不做语义改写。

## 7. 目录结构

```
legal-suite/law-repository/                ← 中央法规库（data 基础设施，不占技能编号）
├── README.md              ← 操作手册（定位 + 文件头规范 + 更新规程 + 数据流）
├── 法规库架构与逻辑说明.md ← 本文件（架构与逻辑说明）
├── law-manifest.md        ← 法规清单（已入库 / 待补 / 待核），唯一盘点入口
├── laws/                  ← 【L1 原文层】法律/法规/司法解释/部门规章原文快照
│   └── <法律名称>_<版本>.md
├── L2-interpretation/     ← 【L2 领域解读层】官方释义/权威实务解读
│   └── <主题>_解读_<来源>.md
├── L3-case/              ← 【L3 案例引用层】指导案例/公报案例要旨
│   └── <案由>_案例_<案号>.md
├── registry/             ← 反向登记（蒸馏数据 → 库原文 的可追溯链路）
│   └── reverse-registry.md
└── sources/              ← 原始来源归档（PDF 等），保溯源
```

## 8. 对齐用户原始三项需求

| 用户需求 | 落地方式 |
|---|---|
| **#1** 单独法规库，含原文/司法解释/领域解读/案例引用 + 更新+版本迭代机制 | L1 原文层（含司法解释原文）+ L2 解读层 + L3 案例层 + §6 版本迭代六条 |
| **#2** 蒸馏单独放行业/业务场景；来源从库取原文再蒸馏+更新；新要求反向推动库更新 | §4 解耦逻辑（蒸馏不迁入库）+ §5 反向登记闭环（manifest 待补 → registry） |
| **#3** 其他按建议 | 三层 + registry 反向登记即建议的最佳实践方案 |

- **不占技能编号**：同 `perspective-kernel` / `business-underlying-logic` 模式，作为数据基础设施挂在 `legal-suite` 下。
- **纳入 GOV_SkillGovernance v3.6 管辖**：QG4（数据溯源）、QG6（变更管理）为直接适用质量门。
