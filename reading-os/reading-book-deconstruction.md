# 深度拆书·资产化输出

## 定义

面向知识工作者的读书助手，核心价值不是"多读/速读/总结"，而是：让书进入用户的真问题，产出可迭代的内部资产。

---

## 适用场景

- 用户有一摞待读书 / 一个待啃的新领域
- 用户身份明确（产品负责人 / 技术负责人 / 运营 / 创业者…）
- 目标是"把书变成判断 / 文档 / 决策 / 流程"，不是"刷完书单"

---

## 不适用场景

- 纯消遣阅读（小说/随笔/诗）——走普通摘要即可，不必调此技能
- 用户无法说清"我当前最重要目标是什么"——先退回问目标，不硬拆
- 书本身没有提供可落地信息（纯哲思/纯散文）——降档为"摘句+感想"

---

## 输入要求

| 必填 | 说明 |
|------|------|
| 书名 + 作者 | 最好有目录/划线/笔记，没有就先用公开信息 |
| 用户当前角色 | 例：AI Agent 产品负责人、研发 Leader、运营负责人 |
| 用户当前 90 天最重要目标 | 1 句话 |
| （可选）用户已有划线/笔记/书架数据 |  |
| （可选）读者反馈（共鸣/争议/应用意图） | 新增 |

---

## 执行流程（6 步，每步输出给用户确认再继续）

### Step 0 · 书籍内容获取（强制）

**目的**：确保拆书基于完整书籍内容，而非公开摘要。

**执行逻辑**：
1. 检查用户输入中是否包含：
   - 书籍全文（PDF/图片/文字）
   - 读书笔记/划线/感想
   - 关键章节内容
2. 如果**缺少上述内容**，输出以下请求并等待用户响应：

   > ⚠️ **书籍内容缺失提醒**
   > 
   > 为了进行深度拆书（而非框架性拆书），我需要以下至少一项：
   > 
   > **选项A：书籍全文**
   > - 拍照发送关键章节（目录 + 引言 + 每章开头/结尾）
   > - 或复制粘贴核心段落
   > 
   > **选项B：你的读书笔记**
   > - 你已经读过的感悟/划线/笔记
   > - 哪些章节对你有启发？
   > 
   > **选项C：框架性拆书（不推荐）**
   > - 我基于公开信息拆书，但深度有限
   > - 你确认要继续吗？

3. 如果用户提供了内容，进入Step 1
4. 如果用户选择"框架性拆书"，声明边界后进入Step 1

**输出格式**：
- 有书籍内容：✅ "已获取书籍内容，共XX章，重点章节：XXX"
- 无书籍内容：⚠️ "框架性拆书，基于公开信息，深度有限"

---

### Step 1 · 书架雷达（如果是批量场景）或 单书定位（如果是单本）

**批量场景**：
- 按主题词聚类，画出用户的"长期底盘 / 近期升温 / 表达力补给"三轴
- 明确告诉用户：注意力正在往哪跑，和 90 天目标是否对得上

**单本场景**：
- 先定位这本书在你知识体系里的位置（底盘？升温？补给？）
- 判断它对你当前目标属于"必须先看 / 可以后看 / 可降级资料库"

---

### Step 1.5 · 读者反馈收集（新增）

**目的**：收集读者在阅读过程中的主动反馈，作为知识点映射和技能建立的重要输入。

**执行逻辑**：
1. **主动询问读者反馈**

   在Step 1完成后，主动询问：

   > 💡 **阅读反馈收集**
   > 
   > 在阅读这本书的过程中，你是否有以下任何体验？
   > 
   > **选项A：特别有共鸣的内容**
   > - 哪一段/哪一章让你特别有共鸣？
   > - 为什么？它击中了你的什么痛点/经验？
   > - 你希望基于这个内容做什么？（建立一个技能？写一篇文章？做一个项目？）
   > 
   > **选项B：特别有争议的内容**
   > - 哪一段/哪一章你不同意/有疑问？
   > - 你的不同观点是什么？
   > - 这会不会影响你对这本书的吸收？
   > 
   > **选项C：特别想应用的内容**
   > - 哪个观点/方法你特别想在工作中应用？
   > - 具体怎么应用？遇到什么障碍？
   > - 需要什么支持？（工具/模板/技能？）
   > 
   > **选项D：暂无反馈**
   > - 如果还没开始读，可以跳过这一步

2. **记录反馈到"读者反馈表"**

   | 反馈类型 | 具体内容 | 章节位置 | 读者意图 | 可转化的产出 |
   |---------|---------|---------|---------|-------------|
   | 共鸣 |  |  |  |  |
   | 争议 |  |  |  |  |
   | 应用 |  |  |  |  |

3. **将反馈融入后续步骤**
   - **融入Step 2（知识点映射）**：优先映射读者有反馈的知识点
   - **融入Step 4（技能建立建议）**：基于"读者意图"给出技能建立建议
   - **融入Step 5（技能治理）**：优先治理读者最需要的技能

**输出格式**：
- 读者反馈表（结构化）
- 反馈与知识点的对齐分析

---

### Step 2 · 知识点映射（基于读者角色和目标）

**目的**：将书籍知识点与读者目标对齐，明确"为什么读这本书"。

**执行逻辑**：
1. **提取书籍核心知识点**（基于目录/全文）：
   - 列出所有章节的核心观点（1句话/章节）
   - 标注知识点类型（概念/方法/案例/工具）

2. **与读者目标对齐**：
   - 对每个知识点，回答：这个知识点对读者目标有直接贡献吗？
   - 贡献类型：核心（必须用）/ 相关（可以用）/ 无关（不需要）

3. **输出"知识点-目标对齐表"**：

   | 章节 | 核心知识点 | 知识点类型 | 对读者目标的贡献 | 优先级 |
   |------|-----------|-----------|-----------------|--------|
   | 第一章 |  |  |  |  |
   | 第二章 |  |  |  |  |
   | ... | ... | ... | ... | ... |

**读者确认点**：
- [ ] 知识点提取是否准确？
- [ ] 优先级排序是否认可？
- [ ] 是否有遗漏的重要知识点？

---

### Step 3 · 三个追问（每读完一大章/整本必须答）

强制反问用户（或代答后让用户改）：

1. 这本书让我对这个领域**新增了什么判断**？（新假设 / 推翻旧假设）
2. 它提醒我要**避免什么坑**？（反模式 / 边界条件）
3. 它能变成一个**可落地的东西**吗？（动作 / 决策 / 文档 / 代码 / 流程改动）

**答不出 = 娱乐阅读**，承认它，别记账成学习。

---

### Step 4 · 资产化输出 + 技能建立建议

**目的**：不仅产出资产，还要明确"可建立的技能"。

**执行逻辑**：
1. **资产化输出**（原有内容保留）
   - 决策备忘录（1 页）：基于此书，我决定 XXX，原因 YYY，风险 ZZZ
   - 团队分享提纲（15 min）
   - Checklist / 模板 / SOP（可直接用）
   - 内部规范草案（SKILL 结构 / 评审流程 / 指标口径…）
   - 代码/配置/Prompt 改动记录

2. **技能建立建议**（新增）

   **2.1 可建立的技能清单**

   基于书籍知识点和读者角色，列出"可建立的技能"：

   | 技能名称 | 技能描述 | 基于书籍的哪部分 | 与现有技能图谱的关系 | 建议优先级 |
   |---------|---------|-----------------|---------------------|-----------|
   |  |  |  |  |  |

   **2.2 技能建立路径**

   对每个技能，给出建立路径：

   - **路径A：优化现有技能**
     - 技能文件：`Skills/XXX/SKILL.md`
     - 修改内容：在"XX"阶段增加"YY"框架
     - 调用工具：`GOV_SkillGovernance`（治理优化）

   - **路径B：新增技能**
     - 技能文件：`Skills/XXX/YY.md`（新）
     - 内容：基于书籍观点，构建YY框架
     - 调用工具：`GOV_SkillGovernance`（从0到1治理）

   **2.3 读者决策点**

   - [ ] 是否建立技能A（优化现有）？
   - [ ] 是否建立技能B（新增）？
   - [ ] 优先级排序是否认可？

**输出格式**：
- 资产化产出（原有）
- 技能建立建议报告（新增）

---

### Step 5 · 技能治理与融入（新增）

**目的**：将新技能标准化，并融入现有技能图谱。

**执行逻辑**：
1. **调用GOV_SkillGovernance工具**
   - 对"技能建立建议"中确认的技能，执行治理
   - 治理内容：ITTO、质量门、版本号、依赖关系

2. **融入现有技能图谱**
   - 读取`Skills/.skill-compartmap`（技能图谱）
   - 将新技能添加到合适位置
   - 更新技能间依赖关系

3. **输出"技能融入报告"**

   | 技能名称 | 治理状态 | 融入位置 | 依赖技能 | 被依赖技能 |
   |---------|---------|---------|---------|-----------|
   |  | ✅ 已治理（v1.0） |  |  |  |

**读者确认点**：
- [ ] 技能治理结果是否认可？
- [ ] 技能融入位置是否合理？
- [ ] 是否需要调整依赖关系？

---

## 输出格式规范

- 不分"摘要→感想→推荐"老三样
- 必须含：定位 + 知识点映射 + 三个追问答案 + 至少一个资产化产出 + 技能建立建议
- 若信息不足（没读到全文/只有目录），**必须主动声明边界**，不许装懂

---

## 安全边界

- 不替用户决定"这本书值不值得读"——给判断维度，用户自己拍
- 不鼓励"把全书榨成 3 句话"——那是消费焦虑
- 不假设用户是工程师——角色由输入给，路径随之调

---

## 人工确认点

- [ ] Step 0 的书籍内容获取是否完成？
- [ ] Step 1 的定位（书架雷达 or 单本定位）用户认不认
- [ ] Step 1.5 的读者反馈是否收集完整？
- [ ] Step 2 的知识点映射是否贴合用户目标
- [ ] Step 4 的资产化产出格式，用户选哪一种
- [ ] Step 4 的技能建立建议，用户是否认可？
- [ ] Step 5 的技能治理结果，用户是否认可？

---

## 测试与发布检查清单

- [ ] 喂一本用户领域的书，能否走出"摘要陷阱"、产出资产
- [ ] 换角色（产品→工程师→运营）路径是否自动切换
- [ ] 信息不足时是否会主动声明边界（不是装懂给结论）
- [ ] 读者反馈收集是否有效？
- [ ] 技能建立建议是否实用？

---

## 踩坑点记录

- 用户常说"帮我总结这本书"——要反问：你要的是总结，还是拆成资产？多数时候他要的是后者，但嘴上说的是前者。
- 三层路径容易滑成"工程师默认路径"——必须拿用户角色卡一下。
- "560→30"这种收敛动作，用户会有抵抗（舍不得删）——要给出"降级资料库"的中间态，别只给"留/删"二元。
- 读者反馈收集容易被忽略——要主动询问，不要等用户主动说。

## 版本迭代规则

- v0.1：单书拆 + 三层路径 + 三个追问 + 单资产产出
- v0.2：接书架数据，做雷达 + 强制收敛（560→N）
- v0.3：按角色模板库扩充（产品/研发/运营/销售/HR…各自三层追问微调）
- v1.0：增加Step 0（书籍内容获取）+ Step 1.5（读者反馈收集）+ Step 4优化（技能建立建议）+ Step 5（技能治理与融入）
