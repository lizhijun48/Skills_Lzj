# SKILL 治理方案对比分析报告

> 对比对象：
> - **方案 A**：之前的 SKILL 整理工作（PD 模板 + PM 协作接口优化）
> - **方案 B**：当前 `skill-governance-system` 治理系统（基于 PMP/NPDP/一建三标准融合）
>
> 生成时间：2026-06-06
> 目的：评估哪种方案更能解决实际使用问题，为后续决策提供依据

---

## 一、方案概述

### 方案 A：渐进式 SKILL 整理（前期工作）

**核心思路**：基于现有 139 个 SKILLs，通过局部优化提升实用性和协作能力。

**已完成工作**：

| 工作项 | 内容 | 覆盖 SKILLs |
|--------|------|--------------|
| Option A | 为 PD SKILLs 添加 `references/` 模板和"参考资料"部分 | 14 个 PD SKILLs |
| Option B | 优化 PM SKILLs 协作接口（角色映射 + 消费接口 + 移交检查清单） | 15 个 PM SKILLs |
| 验证测试 | 随机调用 4 个 SKILLs 确认功能 | 4 个 SKILLs |

**方案特点**：
- ✅ 实用导向 — 直接解决 SKILL 间协作问题
- ✅ 渐进优化 — 不推翻现有结构，基于现有 SKILLs 改进
- ✅ 快速落地 — 改动局部，风险可控
- ⚠️ 缺乏顶层设计 — 没有统一的分类框架和路由逻辑
- ⚠️ 覆盖有限 — 仅覆盖 29 个 SKILLs（21%），剩余 110 个未触及

---

### 方案 B：`skill-governance-system` 治理系统（当前方案）

**核心思路**：基于 PMP + NPDP + 一建三大标准，构建融合型 SKILL 治理框架，实现从"技能集合"到"标准体系"的升级。

**已完成工作**：

| 文件 | 内容 | 作用 |
|------|------|------|
| `00_POLARIS.md` | 北极星文档：服务人设（三证持有者）、双轨触发场景、交付定义（ITTO 模型）、边界 | 定义治理系统的"宪法" |
| `STANDARDS_FRAMEWORK.md` | 架构基础：双轨模型（PT/JT/S）+ 六阶段（P1-P6）+ CX 知识域 + ITTO 映射 | 理论基础和架构设计 |
| `SKILL_REGISTRY.md` | 139 个 SKILLs 注册表：分类、触发词、阶段归属、成熟度 | 全局索引和目录 |
| `ROUTING_TABLE.md` | 三级路由：Level 1（Track 识别）→ Level 2（Phase 识别）→ Level 3（Skill 选择） | 调度和分发逻辑 |
| `MERGE_STRATEGY.md` | 合并策略：14 个重叠组分析，138 → 117 SKILLs | 去重和优化 |
| `SYSTEM_RULES.md` | 五条铁律：单入口 + 双轨路由、阶段完整性、冲突解决、ITTO 标准化、专业性保障 | 强制约束 |
| `taxonomy/PHASES.md` | 六阶段过程定义（P1-P6 + CX），双轨共用 | 阶段划分和定义 |
| `taxonomy/PROBLEM_TYPES.md` | 问题类型定义（5 大类、25+ 种类型），用于路由和调度 | 问题分类和信号词 |
| `skills/` | 3 个新 SKILL 示例（data-analyst, portfolio-rebalancing, product-sunset-assessment） | 新标准下的 SKILL 编写模板 |

**方案特点**：
- ✅ 理论扎实 — 基于 PMP + NPDP + 一建三大标准
- ✅ 结构完整 — 双轨 + 六阶段 + CX + 三级路由 + ITTO
- ✅ 全局视角 — 覆盖全部 139 个 SKILLs（通过注册表）
- ✅ 可扩展 — 问题类型、路由规则、CX 知识域均可扩展
- ⚠️ 复杂度高 — 需要理解和维护整套框架（9 个核心文件）
- ⚠️ 落地成本高 — 需要按新标准重写/改造现有 SKILLs
- ⚠️ 过度设计风险 — 某些场景可能不需要这么重的框架

## 二、核心差异对比

| 维度 | 方案 A（前期整理） | 方案 B（治理系统） |
|------|---------------------|---------------------|
| **设计理念** | 渐进优化，务实主义 | 顶层设计，标准融合 |
| **理论基础** | 无明确理论框架 | PMP + NPDP + 一建三标准融合 |
| **覆盖范围** | 29/139 SKILLs（21%） | 139/139 SKILLs（100%，通过注册表） |
| **分类逻辑** | 原有 PD/PM 分类 | 双轨（PT/JT）+ 六阶段（P1-P6）+ CX |

## 三、实际使用问题解决能力对比

### 3.1 用户触发 SKILL 的准确性

**问题场景**：用户说"帮我做个竞品分析"，系统应该准确触发 `pd-market-research` 而不是其他 SKILL。

| 方案 | 机制 | 准确性 | 评价 |
|------|------|--------|------|
| 方案 A | 依赖 SKILL 的 `description` 和触发词 | 中（依赖编写质量） | 无系统路由，可能触发错误 SKILL |
| 方案 B | 三级路由：先识别 Track（PT/JT）→ 再识别 Phase（P1-P6）→ 最后选择 Skill | 高（分层过滤） | 通过问题类型定义和信号词，准确率更高 |

**结论**：方案 B 更准确，但方案 A 可以通过优化 `description` 和触发词达到类似效果（成本更低）。

---

### 3.2 SKILL 间协作的顺畅度

**问题场景**：`pd-market-research` 完成后，应该自动将输出传递给 `pd-product-strategy`。

| 方案 | 机制 | 顺畅度 | 评价 |
|------|------|--------|------|
| 方案 A | 为 15 个 PM SKILLs 添加"协作接口三要素"（角色映射 + 消费接口 + 移交检查清单） | 中高（仅覆盖 PM SKILLs） | PD SKILLs 未覆盖，跨轨（PT↔JT）协作未定义 |
| 方案 B | ITTO 模型（Input-Tools/Techniques-Output）+ Handoff To + 三级路由 | 高（全局定义） | 每个 SKILL 都有明确的 Input/Output，协作接口标准化 |

**结论**：方案 B 更系统，但方案 A 的"三要素"思路可以直接借鉴到方案 B 中（互补而非对立）。

---

### 3.3 新 SKILL 创建的一致性

**问题场景**：需要创建一个新 SKILL（如"用户访谈设计"），如何确保它与现有 SKILLs 不重复、分类正确、接口一致？

| 方案 | 机制 | 一致性 | 评价 |
|------|------|--------|------|
| 方案 A | 无系统方法，依赖创建者经验 | 低 | 容易产生重复 SKILLs 或接口不一致 |
| 方案 B | 1. 先查 `SKILL_REGISTRY.md`（检查是否已存在）<br>2. 按双轨+六阶段分类<br>3. 使用 ITTO 模板编写<br>4. 通过 `SYSTEM_RULES.md` 铁律检查 | 高（有章可循） | 新 SKILL 创建有明确的流程和模板 |

**结论**：方案 B 明显优于方案 A，尤其当 SKILL 数量增长到 200+ 时。

---

### 3.4 问题诊断和需求理解能力

**问题场景**：用户说"我们产品做不起来，怎么办？"，系统应该能诊断问题是出在 P1（识别）还是 P2（论证）还是 P3（规划）。

| 方案 | 机制 | 诊断能力 | 评价 |
|------|------|----------|------|
| 方案 A | 无系统方法，依赖 SKILL 内部逻辑 | 低 | 无法区分"问题定义不清"和"优先级混乱" |
| 方案 B | 问题类型定义（`PROBLEM_TYPES.md`）+ 信号词匹配 + 阶段归属 | 高（可区分 25+ 种问题类型） | 可以精准识别用户问题的阶段和类型，路由到正确的 SKILL |

**结论**：方案 B 的诊断能力远超方案 A，这是方案 B 的最大优势。

---

### 3.5 维护和演进成本

**问题场景**：3 个月后，发现某些 SKILLs 需要合并或拆分，某些路由规则需要调整。

| 方案 | 维护成本 | 演进灵活性 | 评价 |
|------|-----------|--------------|------|
| 方案 A | 低（无复杂结构） | 低（缺乏框架指导） | 维护简单，但演进时无章可循，容易混乱 |
| 方案 B | 高（需要维护 9 个核心文件 + 139 个 SKILL 注册信息） | 高（有框架指导） | 维护成本高，但演进时有明确规则（如合并策略、路由更新流程） |

**结论**：方案 A 短期成本低，方案 B 长期可维护性更好（但有前期投入）。

## 四、优劣势总结

### 方案 A（前期整理）优劣势

**优势**：
1. **快速落地** — 局部优化，不需要重写现有 SKILLs
2. **成本低** — 仅覆盖 29 个 SKILLs，投入有限
3. **风险可控** — 不推翻现有结构，渐进式改进
4. **务实** — 直接解决协作接口问题（Option B 的"三要素"很实用）

**劣势**：
1. **覆盖有限** — 仅 21% SKILLs 被优化，剩余 110 个仍是"孤岛"
2. **缺乏顶层设计** — 没有统一的分类框架，SKILLs 之间关系不清晰
3. **路由不准确** — 依赖触发词匹配，容易误触发
4. **难以扩展** — 缺乏框架指导，新增 SKILL 容易产生混乱

**适用场景**：
- 短期快速改进，先让部分核心 SKILLs 好用起来
- 资源有限，无法投入大量时间重构
- 作为方案 B 的"先导试验"（先优化核心 SKILLs，再逐步扩展到全局）

---

### 方案 B（治理系统）优劣势

**优势**：
1. **理论扎实** — 基于 PMP + NPDP + 一建三大标准，专业性强
2. **全局视角** — 覆盖 139 个 SKILLs，有统一的分类和路由
3. **诊断精准** — 问题类型定义 + 三级路由，可以精准识别用户需求
4. **可扩展** — 有框架指导，新增 SKILL 或调整路由都有章可循
5. **合并策略** — 通过重叠分析减少冗余（138 → 117）

**劣势**：
1. **复杂度高** — 需要理解和维护 9 个核心文件 + 注册表
2. **落地成本高** — 需要按新标准重写/改造现有 SKILLs（工作量巨大）
3. **过度设计风险** — 某些场景可能不需要这么重的框架（如简单的数据分析任务）
4. **理论重于实践** — 框架设计很"完美"，但实际使用中是否真的需要这么复杂？

**适用场景**：
- 长期建设，打造专业级 SKILL 治理体系
- 团队有一定规模，需要标准化和规范化
- 作为"终极目标"，但需要分阶段实施（避免一口气吃成胖子）

## 五、核心判断：哪种方案更能解决实际使用问题？

### 5.1 短期（1-3 个月）：方案 A 更实用

**理由**：
1. **快速见效** — 优化 15 个 PM SKILLs 的协作接口，立即可用
2. **成本低** — 不需要重写现有 SKILLs，局部改动即可
3. **风险可控** — 不推翻现有结构，渐进式改进

**建议行动**：
- 先落地方案 A 的 Option B（PM SKILLs 协作接口优化）
- 同时启动方案 B 的"先导项目"：选择 5-10 个核心 SKILLs，按新标准改造，验证框架可行性

---

### 5.2 中期（3-6 个月）：方案 A + 方案 B 混合

**理由**：
1. **方案 A 的"三要素"思路很好**，应该保留并扩展到所有 SKILLs
2. **方案 B 的"问题类型定义"和"三级路由"很价值**，可以逐步引入
3. **不需要一次性重写所有 SKILLs**，可以"新旧并存、逐步迁移"

**建议行动**：
- 将方案 A 的"协作接口三要素"整合到方案 B 的 ITTO 模型中（互补）
- 选择 20-30 个核心 SKILLs，按方案 B 标准改造（作为"标杆"）
- 其余 SKILLs 保持原样，但通过 `SKILL_REGISTRY.md` 注册和分类（不改写，只分类）

---

### 5.3 长期（6-12 个月）：方案 B 作为终极目标

**理由**：
1. **SKILL 数量增长到 200+ 时**，必须有顶层设计（否则无法维护）
2. **专业级应用**（如企业级产品/项目管理），需要标准框架支撑
3. **社区贡献场景**，需要明确的 SKILL 创建规范和审查流程

**建议行动**：
- 完成全部 139 个 SKILLs 的改造（按方案 B 标准）
- 建立 SKILL 治理的"宪法"：`SYSTEM_RULES.md` 铁律 + 审查流程
- 开源核心框架（双轨模型 + 六阶段 + ITTO 模板），让社区贡献标准化

## 七、关键决策点（需要你判断）

在启动上述实施路径之前，有几个关键决策需要你明确：

### 决策 1：是否需要"双轨模型"？

**选项**：
- **A. 保留双轨（PT + JT）** — 适合"产品+项目"双重身份的 practitioner
- **B. 简化为单轨** — 如果你主要做产品，可以去掉 JT 轨；如果主要做项目，可以去掉 PT 轨

**我的建议**：保留双轨，但前期可以先实现"产品轨（PT）"，项目轨（JT）作为扩展。

---

### 决策 2：是否需要"三级路由"？

**选项**：
- **A. 完整三级路由** — 更准确，但复杂度高
- **B. 简化二级路由** — 先做 Phase 识别 → Skill 选择，暂时跳过 Track 识别

**我的建议**：先实现简化二级路由（Phase → Skill），后期再扩展到三级。

---

### 决策 3：是否按新标准重写所有 SKILLs？

**选项**：
- **A. 全部重写** — 一致性高，但成本巨大
- **B. 新旧并存、逐步迁移** — 成本低，但一致性差
- **C. 仅改造核心 SKILLs（20-30 个），其余保持原样但通过注册表分类** — 折中方案

**我的建议**：选项 C。核心 SKILLs 决定 80% 的使用场景，优先改造这 20-30 个即可。

---

### 决策 4：合并策略是否执行？

**选项**：
- **A. 执行合并（138 → 117）** — 减少冗余，但可能误杀"有用但重叠"的 SKILLs
- **B. 暂不合并，先优化协作接口** — 保持多样性，但存在冗余

**我的建议**：暂缓合并，先优化协作接口。合并是"后期优化项"，不应该阻塞前期落地。
