# SKILL 编排规则（System Rules）— v3 双轨版

> 基于 PMP + NPDP + 一级建造师 三标准融合框架的双轨六阶段模型。
> 更新：2026-06-06

---

## 铁律 1：单入口 + 双轨路由（Single Front Door + Dual Track）

用户只面对一个入口——Dispatcher 总控。
Dispatcher 执行三级路由：

```
用户输入 → 第一级：识别轨道（产品轨 PT / 项目轨 JT / 共用层 S）
         → 第二级：识别阶段（PT1-6 / JT1-5 / 共用 P1-P6）
         → 第三级：识别 Skill（含分支条件）
```

用户不需要知道有 136 个 Skill，也不需要知道自己在走 NPDP 还是 PMP 流程。

**落地规则：**
- Dispatcher 必须在 1 轮追问内完成轨道+阶段识别
- 如果轨道不明确，追问："这个问题更偏产品决策还是项目交付？"
- 如果阶段不明确，默认路由到该轨道的第一阶段（PT1 或 JT1）

---

## 铁律 2：轨道不混淆 + 阶段不越权（Track Integrity + Phase Boundary）

### 轨道完整性
- **产品轨的 Skill 用 NPDP 方法论** — Stage-Gate 门径不能跳过，VOC 分析不能省略
- **项目轨的 Skill 用 PMP/一建方法论** — 过程组不能省略，变更控制不能跳过
- **共用层的 Skill 同时遵守两轨标准** — 输出格式需同时满足产品和项目的使用场景

### 阶段边界
每个阶段只做自己该做的事，只把"结论包"交给下一阶段：

```
产品轨：PT1→PT2→PT3→PT4→PT5→PT6
项目轨：JT1→JT2→JT3→JT4→JT5
共用层：P1→P2→P3→P4→P5→P6（按需）
CX 知识域：任何阶段按需调用
```

**禁止越权行为：**
- PT 阶段不能跳过 Stage-Gate 门径直接出产品方案
- JT 阶段不能跳过 P2 论证直接出项目计划
- 共用层 Skill 不能替产品轨做战略决策或替项目轨做合规判断

**允许的正常跨轨：**
- PT 产品论证完成后 → 触发 JT 项目立项（跨轨串联）
- JT 项目执行中发现产品问题 → 触发回到 PT 重新评估
- 共用层可在任何轨道的任何阶段被调用

---

## 铁律 3：冲突消解按"轨道 + 阶段 + 标准域"

当两个 Skill 都能接同一句话时，按以下优先级裁决：

**第一级：轨道优先**
- 涉及产品决策（做什么/为谁做/市场定位）→ 走产品轨（PT）
- 涉及项目交付（怎么做/进度/合同/验收）→ 走项目轨（JT）
- 两者都涉及 → 走共用层（S），或串联 PT→JT

**第二级：阶段优先**
- 更模糊、问题不清楚 → 路由到该轨道的更早阶段
- 有明确需求和计划 → 路由到中间阶段
- 有明确交付时间点 → 路由到执行阶段

**第三级：标准域优先**
- 产品轨内 → 优先 NPDP 方法论
- 项目轨内 → 优先 PMP 过程 / 一建规范
- 共用层内 → 根据问题类型选择最合适的标准

**第四级：场景分支**
- 同一 Skill 内有多个分支 → 根据 MERGE_STRATEGY.md 中定义的 branch_conditions 选择

## 铁律 4：每个 SKILL 必须具备标准 ITTO

基于 PMP 的 ITTO 模式，每个 Skill 必须包含以下元数据：

```yaml
name: skill-name
track: PT | JT | S                            # 双轨归属
phase: P1 | P2 | P3 | P4 | P5 | P6 | CX    # 主阶段
crosscut: [CX-N, ...]                         # 涉及的专业知识域
standard_source: "NPDP.Stage2 | PMP.Planning.Scope | 一建.经济.投资估算"  # 标准出处

trigger_signals: ["关键词1", "关键词2"]

input:
  required:
    - field_name: "描述"
      source: "用户直接提供 | 上游 Skill 输出 | 系统自动获取"
  optional:
    - field_name: "描述"

tools_techniques:
  methodology: "方法论名称"
  standard_reference: "PMBOK 6th §5.1 / NPDP Ch.3 / 一建项目管理 Ch.4"

output:
  primary: "主要输出 + 格式"
  quality_gate: "验收标准"

boundary:
  does_not: ["明确不做的事"]
  handoff_to: ["下游 Skill 名称"]
```

**ITTO 三规则：**
1. **输入可验证** — 缺输入必须追问，不能硬编
2. **处理可追溯** — 每个步骤标注标准出处
3. **输出有验收** — 明确格式 + 质量标准 + 边界声明

## 铁律 5：标准专业性不降级

融合三个标准不等于稀释专业性。

- 该走 PMP 完整流程的，不能简化为"大概列个计划"
- 该走 NPDP Stage-Gate 的，不能跳过门径评审
- 该走一建法规审查的，不能用"应该没问题"跳过
- 每个 Skill 引用的方法论必须准确对应标准原文

## 铁律 6：相对引用优先 + 路径可移植（Relative Path Priority）

所有 SKILL 文件内的路径引用必须使用**相对路径**，禁止使用绝对路径。

### 规则详情

| 引用类型 | ❌ 禁止（绝对路径） | ✅ 要求（相对路径） | 说明 |
|:--------|:-------------------|:-------------------|:-----|
| 技能文件引用 | `C:/Users/Lee/.workbuddy/skills/pd-suite/pd-product-strategy/SKILL.md` | `pd-suite/pd-product-strategy/SKILL.md` | 从 `skills/` 根目录开始 |
| 治理系统文件引用 | `C:/Users/Lee/.workbuddy/skills/meta-suite/governance-system/SKILL_REGISTRY.md` | `meta-suite/governance-system/SKILL_REGISTRY.md` | 从 `skills/` 根目录开始 |
| 知识源引用 | `C:/Users/Lee/Documents/standards/NPDP.pdf` | `references/NPDP.pdf` 或标准名称 | 优先用标准名称，其次用项目内相对路径 |
| 跨技能引用 | `/home/user/.workbuddy/skills/economic-suite/economic-npv/SKILL.md` | `economic-suite/economic-npv/SKILL.md` | 统一用 Unix 风格斜杠 `/` |

### 强制要求

1. **路径分隔符**：统一使用 Unix 风格斜杠 `/`，禁止使用 Windows 反斜杠 `\`
2. **引用基准**：所有路径从 `skills/` 根目录开始计算（即 `skills/` 是隐式的当前工作目录）
3. **标准知识源**：优先使用标准名称（如 `PMBOK 6th §5.1`），其次用项目内 `references/` 相对路径
4. **外部文件**：若必须引用外部文件，在 SKILL 文件中标注"需用户确认路径"，由用户运行时提供

### 检查清单

每个 SKILL 文件在创建/更新时必须检查：
- [ ] 所有文件路径引用均为相对路径（无 `C:/` `/home/` 等绝对路径前缀）
- [ ] 路径分隔符均为 `/`（无 `\`）
- [ ] 引用的目标文件确实存在（或标注为"待创建"）
- [ ] 标准知识源优先使用标准名称而非文件路径

### 历史数据处理

- **新创建/更新的 SKILL**：立即遵守本规则
- **历史 SKILL**：在后续更新过程中逐步修正（不需要一次性全量更新）
- **修正优先级**：高频引用的 SKILL 优先（如 `GOV_SkillGovernance.md`、`pd-product-strategy/SKILL.md` 等）

## 铁律 7：避免过度工程化（Avoid Over-Engineering）

禁止使用"虚拟专家协作"模式组织 SKILL。

### ❌ 禁止行为

1. **角色冗余** — 为同一AI设计多个"专家角色"来"协作"
2. **协作伪复杂** — 设计复杂的"信息传递机制"（AI直接读上下文即可）
3. **流程伪必要** — 为简单任务设计多层协调（如"项目经理"协调虚拟团队）
4. **验证伪独立** — 把"提示词切换"伪装成"专家协作"

### ✅ 正确行为

1. 每个 SKILL 是"**能力**"不是"**角色**"
2. 工作流是"**顺序调用**"不是"**专家协作**"
3. 复杂任务用"**分阶段交付**"而非"**多角色并行**"
4. 自验证即可，不需要独立"测试角色"

### 反面教材参考

详细反面教材见 [`ANTI_PATTERNS.md`](ANTI_PATTERNS.md)（专家团自动组建-软件开发-反面教材演示）。

**核心警告**：

| # | 问题模式 | 具体表现 | 正确方式 |
|:---:|---------|---------|---------|
| 1 | **角色冗余** | 10个"专家"= 同一AI的10次提示词切换 | 直接调用能力 |
| 2 | **协作伪复杂** | "信息传递"在AI内部是上下文读取 | 直接读上下文 |
| 3 | **流程伪必要** | 25天"协作流程"可压缩到1次对话 | 端到端执行 |
| 4 | **协调伪需求** | "项目经理"协调的是同一AI | 不需要虚拟协调层 |
| 5 | **验证伪独立** | "测试工程师"和"开发"是同一AI | 自验证即可 |

### 设计检查清单

每个 SKILL 在创建/更新时必须检查：

- [ ] **无虚拟专家协作** — 没有"专家团"、"协作机制"、"角色传递"等设计
- [ ] **无过度工程化** — 流程是直接调用能力，不是多层协调
- [ ] **无角色扮演过度** — 使用"视角"不是"角色"
- [ ] **无时间延迟伪装** — 不模拟"等待3天"、"并行协作"
- [ ] **工具调用清晰** — 使用 `Call:` 不是"专家A → 专家B"
- [ ] **端到端执行** — 复杂任务用"分阶段交付"不是"多角色并行"

## 铁律 8：治理后必须更新索引文件（Update Index Files After Governance）

**核心要求**：治理操作（新增/合并/删除技能）完成后，必须立即更新所有相关的索引文件，保证全局对应关系的一致性。

### ❌ 禁止行为

1. **治理后不更新索引文件** — 技能已变更，但索引文件仍指向旧状态
2. **遗漏索引文件更新** — 只更新了部分索引文件，导致映射关系不一致
3. **索引文件与技能实际状态不一致** — 索引文件中记录的技能路径、名称、状态与实际不符

### ✅ 正确行为

1. **治理后立即更新索引文件** — 在完成技能治理操作后，第一时间更新索引文件
2. **使用检查清单确保不遗漏** — 按照"索引文件更新检查清单"逐一检查并更新
3. **保证全局对应关系的一致性** — 所有索引文件中的映射关系必须相互一致

### 索引文件更新检查清单

以下索引文件在治理后**必须检查并更新**：

| 优先级 | 索引文件 | 文件路径 | 更新时机 |
|:-------:|---------|---------|---------|
| 🔴 高 | 技能编号注册表 | `SKILL-ID-REGISTRY.md` | 每次治理后 |
| 🔴 高 | 业务流程映射 | `BUSINESS-FLOW-MAP.md` | 新增/合并技能后 |
| 🟡 中 | 三级路由表 | `governance-system/ROUTING_TABLE.md` | 新增/合并技能后 |
| 🟡 中 | Skill详细盘点表 | `governance-system/SKILL_REGISTRY.md` | 使用SKILLS体系时 |
| 🟢 低 | 套件技能地图 | 各套件下的 `SKILL-MAP.md`（如有） | 套件内技能变更后 |
| 🟢 低 | 记忆文件 | `.workbuddy/memory/MEMORY.md` | 涉及用户习惯变更时 |

### 更新时机详解

#### 1. 新增技能时

- ✅ 添加治理ID到 `SKILL-ID-REGISTRY.md`
- ✅ 添加业务流程映射到 `BUSINESS-FLOW-MAP.md`
- ✅ （可选）更新 `ROUTING_TABLE.md` 添加路由规则

#### 2. 合并技能时

- ✅ 更新 `SKILL-ID-REGISTRY.md`：标记被合并的技能为"已合并"，更新目标技能的治理能力
- ✅ 更新 `BUSINESS-FLOW-MAP.md`：将多个业务流程映射到合并后的技能
- ✅ 删除被合并技能的索引记录（或在备注中标注"已合并到XXX"）

#### 3. 删除技能时

- ✅ 更新 `SKILL-ID-REGISTRY.md`：标记技能为"已删除"，释放治理ID（不重复使用）
- ✅ 更新 `BUSINESS-FLOW-MAP.md`：删除或更新指向被删除技能的业务流程
- ✅ 检查其他索引文件：确保没有遗漏的引用

### 验证方法

治理完成后，使用以下方法验证索引文件已正确更新：

1. **路径验证**：检查索引文件中记录的技能路径是否真实存在
2. **状态验证**：检查索引文件中记录的状态（✅有效/⏳待处理/❌已删除）是否与实际一致
3. **映射验证**：检查业务流程→技能的映射关系是否完整、准确
4. **交叉验证**：对比多个索引文件，确保同一技能的治理ID、路径、状态一致

### 反面案例

❌ **错误做法**：
```
1. 合并 resume-optimizer + resume-optimization
2. 删除 resume-optimization/ 文件夹
3. 忘记更新 SKILL-ID-REGISTRY.md
4. 忘记更新 BUSINESS-FLOW-MAP.md
5. 结果：用户查找"简历优化"业务流程时，找不到对应的技能
```

✅ **正确做法**：
```
1. 合并 resume-optimizer + resume-optimization
2. 删除 resume-optimization/ 文件夹
3. 立即更新 SKILL-ID-REGISTRY.md（添加S-018，标注合并）
4. 立即更新 BUSINESS-FLOW-MAP.md（添加"简历优化"业务流程）
5. 验证：确认索引文件中的路径、状态、映射关系正确
```

## 铁律 10：关系类型判定（Relationship Type Classification）

每个SKILL必须明确其"关系类型"，避免冗余和过度工程化。

### 六类关系类型

| 类型标记 | 类型名称 | 定义 | 处理方式 |
|---------|---------|------|---------|
| ✅ 核心 | 生产本身需要的关系 | 企业方向确定、供应商选择、质量检验、财务核算等生产本身逻辑 | 必须保留 |
| 🔶 校准 | 过程中起纠偏作用的关系 | 库存盘点、销售数据分析、培训体系、年度战略规划等过程中校准 | 保留为基元内分步校准点 |
| ❌ 传递 | 历史/技术局限导致的信息传递 | 层层下达、逐级汇报、信息上行传递等 | 应消除（AI可实时直通） |
| ❌ 协调 | 信息孤岛导致的协调 | 跨部门协调、项目协调会议、资源协调等 | 应消除（AI可统一数据平台） |
| ⚡ 校验 | 法规/制度要求的校验 | 合规审查、合同审批、绩效考核等 | 精简为关键节点 |
| ❌ 格式 | 形式化报告/审批 | 繁琐审批流程、形式化报告等 | 应消除（AI可自动处理） |

### 判定方法

**追问准则**："如果执行者是一个拥有无限信息和零协调损耗的AI，这个关系还需要吗？"

- 需要 → ✅核心 或 🔶校准 或 ⚡校验
- 不需要 → ❌传递 或 ❌协调 或 ❌格式

### ❌ 禁止行为

1. **未标注关系类型** — 每个SKILL必须明确其关系类型
2. **保留❌传递/❌协调/❌格式关系** — 除非有特殊理由
3. **校准关系丢失** — 🔶校准关系必须保留为基元内分步校准点
4. **校验关系跳过** — ⚡校验关系必须保留（可精简但不能删除）

### ✅ 正确行为

1. **明确标注关系类型** — 在SKILL的ITTO合同中标注关系类型
2. **消除补偿关系** — 识别并消除❌传递/❌协调/❌格式三类关系
3. **保留核心与校准** — ✅核心和🔶校准关系必须保留
4. **精简校验关系** — ⚡校验关系保留为关键节点

### 设计检查清单

每个 SKILL 在创建/更新时必须检查：

- [ ] **关系类型已标注** — 在ITTO合同中标注了关系类型（✅核心/🔶校准/❌传递/❌协调/⚡校验/❌格式）
- [ ] **无❌传递关系** — 没有需要消除的信息传递关系
- [ ] **无❌协调关系** — 没有需要消除的协调关系
- [ ] **无❌格式关系** — 没有需要消除的形式化关系
- [ ] **校准关系不丢失** — 🔶校准关系已保留为基元内分步校准点
- [ ] **校验关系不跳过** — ⚡校验关系已保留（可精简）

## 铁律 11：禁止使用 Emoji 字符（No Emoji in Governance Files）

所有治理体系文件、索引文件、SKILL.md 文件中**禁止使用 Emoji 字符**（包括彩色图标、表情符号等）。

### 状态标记规范

使用纯文本标记替代 Emoji：

| 含义 | 文本标记 | 说明 |
|------|---------|------|
| 有效 | [有效] | 技能正常可用 |
| 可用 | [可用] | 编号已释放，可分配 |
| 待处理 | [待处理] | 已分配但未完成治理 |
| 已删除 | [已删除] | 技能已移除 |
| 已合并 | [已合并] | 已合并到其他技能 |

### 关系类型标记规范

铁律 10 中的关系类型使用文本标记：

| 原标记 | 新标记 |
|--------|--------|
| ✅ 核心 | [核心] |
| 🔶 校准 | [校准] |
| ❌ 传递 | [传递-消除] |
| ❌ 协调 | [协调-消除] |
| ⚡ 校验 | [校验] |
| ❌ 格式 | [格式-消除] |

### 禁止行为

1. **在 SKILL.md 中使用 Emoji** — 包括 frontmatter 的 description、name 等字段
2. **在索引文件中使用 Emoji** — SKILL-ID-REGISTRY、BUSINESS-FLOW-MAP、DEPLOYED_SKILLS_INVENTORY 等
3. **在治理体系文件中使用 Emoji** — SYSTEM_RULES、STANDARDS_FRAMEWORK 等
