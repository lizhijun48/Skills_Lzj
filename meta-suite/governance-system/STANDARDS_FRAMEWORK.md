# 三标准融合框架：PMP + NPDP + 一建

> 本文件是 SKILL 治理体系的架构根基。
> 以"解决实际问题"为导向，融合三大职业认证标准为一套统一的能力框架。
> 生成时间：2026-06-06

---

## 一、为什么融合：三个标准各自的缺角

| 标准 | 擅长 | 缺角 |
|------|------|------|
| **PMP**（PMBOK 6th/7th） | 项目全生命周期过程管理、49 个过程组、ITTO 标准化 | 不覆盖产品创新前端（从 0 到 1 的需求发现）、不覆盖行业合规细节 |
| **NPDP** | 新产品开发战略、组合管理、市场研究、Stage-Gate 门径管理 | 不覆盖工程项目执行细节、不覆盖法律法规刚性约束 |
| **一级建造师** | 工程项目管理实务、中国法律法规体系、工程经济、合同管理 | 不覆盖产品创新方法论、不覆盖通用项目管理的完整过程组 |

任何一个标准单独使用都无法覆盖 139 个 Skill 的全部场景。融合后形成完整能力图谱：PMP 管过程、NPDP 管创新、一建管合规。

---

## 二、双轨模型：产品轨 + 项目轨 + 共用层

**服务对象定位：** 持有 PMP + NPDP + 一建三证的双轨实践者，日常在产品创新和项目交付之间频繁切换。

### 产品轨（Product Track / PT）

**主标准：NPDP**  |  **核心命题：做正确的事**  |  **思维模式：探索→验证→规模化**

| 阶段 | NPDP 对应 | 核心问题 | 关键交付物 |
|:---:|---------|---------|-----------|
| PT1 机会识别 | Discovery + Strategy | 市场上有什么机会？和我们的战略匹配吗？ | 机会评估 + 战略对齐分析 |
| PT2 概念评估 | Concept Evaluation | 这个产品概念好不好？用户买不买账？ | 概念评估报告 + VOC 分析 |
| PT3 商业分析 & 开发 | Business Analysis + Development | 商业上可行吗？怎么开发？ | 商业论证（NPV/IRR）+ 开发计划 |
| PT4 测试验证 | Testing & Validation | 产品和市场假设验证了吗？ | 测试报告 + 试产结果 |
| PT5 商业化上市 | Commercialization | 怎么推向市场？ | GTM 计划 + 上市检查清单 |
| PT6 生命周期管理 | Life Cycle Management | 产品怎么持续演进或退出？ | 生命周期评审 + 组合决策 |

### 项目轨（Project Track / JT）

**主标准：PMP + 一级建造师**  |  **核心命题：正确地做事**  |  **思维模式：范围→进度→成本→质量的平衡**

| 阶段 | PMP 对应 | 一建对应 | 核心问题 | 关键交付物 |
|:---:|---------|---------|---------|-----------|
| JT1 立项启动 | Initiating | 项目前期策划 | 项目做什么？谁参与？ | 项目章程 + 干系人登记册 |
| JT2 计划编制 | Planning（24 过程） | 施工组织设计 + 招投标 | 怎么做？用什么资源？ | 项目管理计划 + 各子计划 |
| JT3 实施交付 | Executing（10 过程） | 施工管理实务 | 按计划做出来 | 可交付成果 + 工作绩效数据 |
| JT4 监控纠偏 | M&C（12 过程） | 进度/成本/质量控制 | 偏了吗？怎么纠？ | 偏差分析 + 变更请求 |
| JT5 收尾验收 | Closing | 竣工验收 + 结算 | 做完了，学到什么？ | 验收报告 + 经验教训 |

### 共用层（Shared Layer）

**两条轨道都需要的通用能力，不属于任何一轨但为两轨共用：**

| 能力 | 产品轨用途 | 项目轨用途 | 标准出处 |
|------|-----------|-----------|---------|
| 需求定义（PRD/Backlog） | 定义产品规格 | 定义项目范围 | PMP.Scope + NPDP.Development |
| 优先级排序 | 功能优先级 | 任务优先级 | PMP.Planning + NPDP.Portfolio |
| 风险管理 | 产品假设风险 | 项目交付风险 | PMP.Risk + NPDP.Tools |
| 干系人管理 | 用户/客户 | 项目相关方 | PMP.Stakeholder |
| 度量与指标 | 产品 KPI | 项目 EVM | PMP.Metrics + NPDP.Metrics |
| 合规审查 | IP/数据合规 | 建设法规/合同 | 一建.法规 + NPDP.IP |
| 沟通管理 | 产品沟通 | 项目沟通 | PMP.Communication |
| 质量管理 | 产品质量 | 工程质量 | PMP.Quality + 一建.质量 |

### 轨道切换规则

**Dispatcher 识别轨道的决策逻辑：**

```
用户输入 → 轨道识别
  ├─ 信号含"产品/用户/市场/商业模式/价值主张" → PT（产品轨）
  ├─ 信号含"项目/进度/施工/合同/招投标/验收" → JT（项目轨）
  ├─ 信号含"需求/优先级/风险/指标/合规" → 共用层
  └─ 信号不明确 → 追问："这个问题更偏产品决策还是项目交付？"
```

**跨轨串联场景：**

| 跨轨任务 | 路径 | 说明 |
|---------|------|------|
| 从产品战略到项目启动 | PT1→PT3 → JT1→JT2 | 产品论证完成后自动触发项目立项 |
| 产品上市 + 项目收尾 | PT5 → JT5 | 产品上市和项目验收同步进行 |
| 合规审查贯穿双轨 | CX-1 同时服务 PT 和 JT | 产品合规（IP/数据）和项目合规（建设法规）分别调用 |

## 三、融合过程：六阶段问题解决生命周期（双轨共用）

三个标准的底层逻辑是一致的：识别问题 → 论证方案 → 计划 → 执行 → 控制 → 收尾。我们将这个共性提炼为六个阶段，每个阶段标注三个标准中对应的过程/知识域。

```
┌─────────────────────────────────────────────────────────────┐
│                                                             │
│   [P1 识别]  →  [P2 论证]  →  [P3 规划]  →  [P4 执行]     │
│                                          ↘                  │
│                                [P5 控制] → [P6 收尾与演进]  │
│                                                             │
│   贯穿层：[CX 专业知识域] ← 任何阶段均可按需调用             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### P1 识别（Frame / 立项识别）

**核心问题：** 要解决什么问题？值不值得做？

| 标准 | 对应过程 | 关键交付物 |
|------|---------|-----------|
| PMP | Initiating 过程组：制定项目章程、识别干系人 | 项目章程、干系人登记册 |
| NPDP | Discovery 阶段 + Strategy | 机会识别、战略一致性评估、概念筛选 |
| 一建 | 项目前期策划 + 法规合规判断 | 立项建议书、合规预评估 |

**本阶段的典型 Skill 场景：**
- 用户来说"我想做一个新产品" → 需要机会识别 + 战略对齐
- 用户来说"我有个项目要做" → 需要立项分析 + 干系人识别
- 用户来说"不知道问题出在哪" → 需要问题诊断 + 需求发现

---

### P2 论证（Justify / 可行性论证）

**核心问题：** 能不能做？值不值得做？选哪个方案？

| 标准 | 对应过程 | 关键交付物 |
|------|---------|-----------|
| PMP | Planning（前端）：范围定义、风险评估、商业论证 | 商业论证、初步范围说明书、风险登记册 |
| NPDP | Concept Evaluation + Business Analysis | 概念评估报告、商业分析（NPV/IRR/回收期）、VOC |
| 一建 | 建设工程经济：投资估算、财务分析、技术方案比选 | 经济评价报告、技术方案比选表 |

**本阶段的典型 Skill 场景：**
- "这个项目投不投？" → 经济评价（NPV/IRR/回收期）
- "选 A 方案还是 B 方案？" → 多方案比选 + 决策矩阵
- "用户到底要什么？" → VOC + Kano + JTBD 分析
- "法规上有没有硬约束？" → 合规审查 + 法规评估

---

### P3 规划（Plan / 方案设计）

**核心问题：** 怎么做？做什么？用什么资源？

| 标准 | 对应过程 | 关键交付物 |
|------|---------|-----------|
| PMP | Planning 过程组（24 个过程）：范围/进度/成本/质量/资源/沟通/风险/采购/干系人管理计划 | 项目管理计划及各子计划 |
| NPDP | Development Planning | 产品开发计划、资源配置、技术评审计划 |
| 一建 | 施工组织设计 + 招投标 + 合同策划 | 施工组织设计、招标文件、合同条款 |

**本阶段的典型 Skill 场景：**
- "帮我写项目计划" → WBS + 进度计划 + 资源计划
- "帮我做招投标" → 招标文件 + 评标标准 + 合同策划
- "功能优先级怎么排？" → 排序框架（RICE/ICE/MoSCoW）
- "风险怎么管？" → 风险识别 + 定性/定量分析 + 应对策略

---

### P4 执行（Execute / 实施交付）

**核心问题：** 按计划做出来，确保交付质量。

| 标准 | 对应过程 | 关键交付物 |
|------|---------|-----------|
| PMP | Executing 过程组（10 个过程）：指导管理项目工作、管理质量、获取资源、实施采购 | 可交付成果、工作绩效数据、变更请求 |
| NPDP | Development + Testing/Validation | 产品原型、测试报告、试产结果 |
| 一建 | 施工管理实务 + 质量管理 + 安全管理 | 施工方案、质量检验记录、安全检查表 |

**本阶段的典型 Skill 场景：**
- "帮我写 PRD / 用户故事" → 需求文档 + 验收标准
- "产品原型怎么测？" → 测试计划 + 测试执行
- "施工方案怎么写？" → 施工组织 + 技术方案
- "文档怎么交付？" → 文档生成 + 格式规范 + QA 审查

### P5 控制（Control / 监控纠偏）

**核心问题：** 做得对不对？偏了怎么纠？

| 标准 | 对应过程 | 关键交付物 |
|------|---------|-----------|
| PMP | Monitoring & Controlling 过程组（12 个过程）：整体变更控制、范围/进度/成本/质量控制、风险监控 | 工作绩效报告、变更日志、预测更新 |
| NPDP | Post-Launch Review + Metrics | 上市后评审、KPI 仪表盘、A/B 测试结果 |
| 一建 | 进度控制 + 成本控制 + 质量控制 + 安全管理 | 进度偏差分析、成本偏差分析、质量整改通知 |

**本阶段的典型 Skill 场景：**
- "实验结果怎么看？" → A/B 测试分析 + 统计显著性判断
- "进度拖了怎么办？" → 挣值分析 + 关键路径调整
- "产品指标怎么设？" → 北极星指标 + 指标树 + 看板设计
- "质量出问题怎么处理？" → 根因分析 + 纠正措施 + 预防措施

### P6 收尾与演进（Close / 收尾复盘）

**核心问题：** 做完了，学到什么？下一步怎么走？

| 标准 | 对应过程 | 关键交付物 |

**本阶段的典型 Skill 场景：**
- "项目做完了怎么总结？" → 复盘引导 + 经验教训提取
- "产品要不要退市？" → 生命周期评估 + 组合决策

## 四、ITTO 映射原则

每个 Skill 必须定义其 ITTO（Input → Tools & Techniques → Output），这是 PMP 的核心模式，也是让 Skill 可落地的关键。

```yaml
# Skill 标准 ITTO 卡片模板
name: skill-name
phase: P1 | P2 | P3 | P4 | P5 | P6        # 主阶段
crosscut: [CX-1, CX-3]                      # 涉及的专业知识域
trigger_signals: ["关键词1", "关键词2"]      # 用户说什么话会触发这个 Skill

input:                                       # 前置条件
  required:
    - field_name: "描述"
      source: "用户直接提供 | 上游 Skill 输出 | 系统自动获取"
  optional:
    - field_name: "描述"

tools_techniques:                            # 处理逻辑
  methodology: "方法论名称（PMP/NPDP/一建出处）"
  steps:
    - "步骤1：..."
    - "步骤2：..."
  branch_conditions:                         # 场景分支（如有）
    - condition: "触发条件"
      what_changes: "处理差异说明"

output:                                      # 交付物
  primary: "主要输出 + 格式"
  secondary: ["附加输出1", "附加输出2"]
  quality_gate: "输出质量校验标准"

boundary:                                    # 边界声明
  does_not: ["明确不做的事"]
  handoff_to: ["下游 Skill 名称"]
```

**ITTO 三规则：**
1. **输入必须可验证**：如果前置条件不满足，Skill 必须明确告知"缺什么"，而不是硬编一个输出
2. **处理必须可追溯**：每个处理步骤必须能说出它用的是哪个标准的哪个方法
3. **输出必须有验收标准**：不能只说"输出报告"，要说清楚报告包含什么、格式是什么、质量标准是什么

## 五、调度逻辑（Dispatch Rules）— 双轨优先

### 5.1 第一级路由：轨道识别

Dispatcher 首先判断用户问题属于哪条轨道：

| 用户信号 | 路由到 | 示例 |
|---------|:---:|------|
| "产品/用户/市场/商业模式/价值主张/竞品" | **PT 产品轨** | "这个产品方向值不值得做？" |
| "项目/进度/施工/合同/招投标/验收/WBS" | **JT 项目轨** | "项目进度拖了怎么办？" |
| "需求/优先级/风险/指标/合规/复盘" | **共用层** | "帮我排优先级" |
| 信号不明确 | **追问** | "这个问题更偏产品决策还是项目交付？" |

### 5.2 第二级路由：阶段识别

确定轨道后，在该轨道内识别阶段：

**产品轨阶段：**

| 用户信号 | 路由到 | 示例 |
|---------|--------|------|
| "有什么机会/用户是谁/市场趋势" | PT1 机会识别 | "帮我做用户画像" |

### 5.3 第三级路由：Skill 选择

```

```

## 八、落地优先级：先打通哪条线

不建议一次性重构所有 139 个 Skill，而是按"用户实际最频繁遇到的问题"分批打通：

### 第一优先级：P3 规划 + P4 执行（日常最高频）

大多数用户的日常需求集中在"帮我规划"和"帮我写/做"。打通这两条线可以覆盖约 60% 的使用场景。

**首批落地的 Skill（约 15 个）：**
- P3：create-prd, backlog-item-generator, sprint-plan, prioritize-workitems, brainstorm-okrs, user-stories
- P4：bidding-assistant, tech-doc-writer, release-notes, system-controller, legal-doc-generator
- CX-1：legal-advisor（合规审查高频需求）

### 第二优先级：P1 识别 + P2 论证（产品创新前端）

产品经理最需要的"前端思考"能力，打通后覆盖约 80% 场景。

**第二批落地的 Skill（约 10 个）：**
- P1：user-profiling, interview-script, customer-journey-map
- P2：swot-analysis, product-solution-evaluator, value-proposition, business-canvas（三个独立画布统一 IO）
- CX-3：market-research 系列

### 第三优先级：P5 控制 + P6 收尾 + CX 全域

补完剩余阶段，实现完整生命周期覆盖。
