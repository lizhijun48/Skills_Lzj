# 外部项目技能提取 Playbook（S-025 详细版）

> 配套 `skill-extraction-sop`(S-025)。本文件是 8 步 SOP 的完整操作手册，含决策矩阵、清单与治理同步模板。
> 经验来源：从 `ai-pm-exploration-toolkit` 提取"洞察抽取/市场研究编排"并落入 PD 体系的一次完整实践。

---

## Step 0 · 范围澄清（先对齐，避免白干）

在动代码前，与用户确认：
- **是否部署原项目**：本任务默认"不部署，只提取知识/方法"。若用户要部署，则不是"提取"而是"集成"，走另一条路。
- **目标子系统**：用户关心哪几个子系统（如合成数据生成器 / 市场研究工具 / 工作流平台）。
- **落点偏好**：提取的东西是"并入现有技能"还是"新建独立技能"（通常两者皆有可能，按子系统定）。

**产出**：一句话范围声明，写进交付说明的"为什么"。

---

## Step 1 · 探索与子系统定位

- 用 Explore 子代理（或并行读）扫描项目结构，避开 `node_modules/`、`.git/`。
- 读 orientation 文档：`README.md` / `CLAUDE.md` / `TECHNICAL_SPECIFICATION.md` / 相关 `*_WORKFLOWS.md`。
- **定位用户关心的子系统**对应的真实文件（full path），区分"文档宣称"和"代码实际"。

**关键原则**：**以代码为准，不以 README 为准**。README 常夸大（如宣称能生成合成访谈稿，代码里只有转写+关键词抽取）。务必 `Read` 核心源文件再下结论。

---

## Step 2 · 可提取性评估（三层判定）

对每个目标子系统，读源码后填下表：

| 层 | 定义 | 提取价值 | 处理 |
|----|------|---------|------|
| **框架层** | 方法论/框架/TAM/SWOT/JTBD 等 | 通常**冗余**（现有体系更严谨） | 不重复提取，仅标注"已有，转 PT-XXX" |
| **执行/编排层** | "怎么把框架跑出来"的方法、prompt、流模式、规则集 | **净增量候选**（现有体系缺） | 提取，工具无关化 |
| **部署胶水** | Docker/n8n/Langflow 配置、CLI 命令、端口、本地路径 | **不可提取**（脱离仓库无意义） | 丢弃或仅作"调用示例"且剥离参数 |

**命名陷阱识别（务必做）**：项目里的词和体系里的词可能同名不同层。例：
- 项目"工作流自动化平台"（用 n8n 搭无代码原型）≠ 体系"workflow-chains"（技能路由编排）。→ 不同层，不是重复，也不增强。
- 项目"合成数据生成器"（Faker 随机 persona）≠ 体系"pd-user-research.Persona"（基于真实访谈）。→ 冲突，禁并入。

**判定结论模板**：
```
子系统 X：
- 实际能力：<读代码得出的真实能力，非名字>
- 所属层：框架 / 执行 / 部署
- 与现有体系：重复 / 冲突 / 互补 / 正交独立
- 净增量：<具体哪块> 或 "无"
```

---

## Step 3 · 与现有技能体系比对

- `grep -rIl` 现有 `skills/` 目录，定位相似技能（按功能词，不只按名字）。
- 读候选技能的 `SKILL.md`，确认其 front matter、触发词、边界声明。
- 判定四类关系：
  - **重复**：现有技能已覆盖 → 不提取。
  - **冲突**：方法论相悖（如随机 persona vs 真实访谈原则）→ 隔离或禁止并入。
  - **互补**：现有有框架、缺执行 → 提取执行层补足（本例市场研究即此）。
  - **正交独立**：完全不同域且外围 → 倾向不建或降权并入。
- 识别 **QG4 触发词冲突**：若新技能触发词与同 Track+Phase 既有技能交集，必须显式划界。

**产出**：每个子系统的"关系判定 + 建议落点（并入哪个技能 / 新建哪个编号 / 放弃）"。

---

## Step 4 · 输出评估表 + 等用户拍板（不擅自落地）

用一张表给用户决策：

| 子系统 | 建议 | 形态 | 提取内容 | 务必避免 | 一句依据 |
|--------|------|------|---------|---------|---------|
| X | 并入 PT-012 / 新建 PT-xxx / 放弃 | 技能+子文件 / 新技能 | <净增量> | <红线> | <判定理由> |

**GOV 决策层边界**：合并/拆分/废弃/新建的**最终决策须用户确认**，Agent 不代替。给出建议后停，等拍板。

---

## Step 5 · 净化（用户同意提取后）

对通过评估的资产做四件事：
1. **工具无关化**：把 `Gemini CLI` / `OpenBB` / `Deep Researcher` 等具体工具泛化为"任意等价 LLM CLI / 财经数据终端 / 多步研究 agent"，prompt 结构保留。
2. **剥离部署依赖**：去掉 Docker 命令、端口、`.local/bin/xxx`、本地绝对路径；只留方法/模板。
3. **红线标注**：
   - 随机/合成数据生成步骤 → 标注"禁止替代真实用户研究"，替换为真实洞察（衔接 PT-012）；
   - 硬编码假数据代码 → 删除，只留"调用示例"骨架。
4. **缺口补全**：原项目缺失的环节顺手补（如本次补全竞品/语音备忘抽取词表，使 6 类场景完整可用）。

---

## Step 6 · 落地（新建 或 并入）

**新建技能**：
- 编号：取所在套件已用最大编号+1（查 `SKILL-ID-REGISTRY.md`）。meta-suite → `S-025` 起。
- 目录：`{suite}/{skill-name}/`，主文档 `SKILL.md` + `references/` 承载细节。
- `SKILL.md` 结构（精简，<150 行）：
  - YAML front matter：`name` / `version` / `description`（前 200 字含核心触发词）/ `governance_id`
  - 核心定位 + 与相邻技能边界
  - **四要素**：功能 / 解决的问题 / 使用时机 / 调用引导（用户早前明确要求）
  - 红线与注意事项
  - 速览表（指向 references/）
  - 调用接口约定（→下游 / ←上游）
  - 参考资料索引表

**并入现有技能**：
- 在 `SKILL.md` 加"能力模块"章节（四要素 + 调用引导），细节放 `references/` 新文件。
- 更新 front matter 描述与触发词、参考资料索引表。

**触发词独立化**：聚焦"从外部项目提取"语义，不与 skill-forge/creator/refactor 的"新建/封装/改造"触发词重叠（QG4）。

---

## Step 7 · 同步 4 张治理全局表（QG13 / §8.1）

**每次增改必做**，不得只改技能本体。

| 全局表 | 路径 | 须同步内容 |
|--------|------|-----------|
| 编号注册表 | `SKILL-ID-REGISTRY.md` | 新增 S-025 行（路径/名/阶段/状态/备注：提取来源）；升级版本号+时间戳 |
| 业务流路由表 | `BUSINESS-FLOW-MAP.md` | 通用工具映射新增一行（触发条件→`skill-extraction-sop`）；升级版本 |
| PT 关系表 | `pd-suite/pd-workflow-chains/SKILL.md` | **仅当**该技能参与 PT 业务链路时登记；meta 技能通常不参与 |
| JT 关系表 | `pm-suite/pm-workflow-chains/SKILL.md` | **仅当**该技能参与 JT 业务链路时登记；meta 技能通常不参与 |

**同步要点**：场景调用不悬空、连接关系显式（→下游/←上游）、QG4 边界划清、版本号时间戳升级。

> **关于 PT/JT 表**：本 SOP 是 S 级 meta 技能，不属于产品/项目交付业务链路，故不强行塞入 PT/JT 关系表（否则是范畴错误）。其衔接关系记录在 SKILL.md 自身 + 注册表备注 + 业务流通用映射中，并在交付说明里透明说明"不强制同步的理由"——这是 §8.2 要求的诚实留痕，非静默跳过。

---

## Step 8 · 交付说明（§8.2 四要素）

完成后**必须**向用户给出：
1. **改了什么**：新增/修改的技能或子能力 + 具体内容（四要素）。
2. **为什么**：治理判断或用户指令。
3. **影响了哪些文件**：全部改动文件的绝对路径（技能文件 + 治理表）。
4. **遗留/待决项**：未决脱节点或需拍板事项，**不静默搁置**。

---

## 判断原则速查清单（ reusable ）

- [ ] 以代码为准，不以 README 为准
- [ ] 拆开命名陷阱（同名不同层）
- [ ] 框架层冗余不重复，只提净增量（执行/编排层）
- [ ] 随机/合成数据红线：禁当真实研究，须标注/隔离
- [ ] 提取前必 grep 现有体系比对（重叠/冲突/互补/正交）
- [ ] QG4 触发词边界在落地时显式划清
- [ ] 净化四件事：工具无关化 / 剥离部署 / 红线标注 / 缺口补全
- [ ] 落地后必同步 4 张治理表 + 给 §8.2 交付说明
- [ ] 合并/废弃/新建最终决策须用户确认
