# skill-extraction-sop · 从外部项目提取可复用技能的 SOP

> **核心定位**：回答"一个外部项目里，哪些东西值得提取成我们技能体系里的技能、怎么提、提完怎么落"。它是 **提取决策 + 落地 SOP**，不是从零创建技能的工具。
> **与 S-022/023/024 的边界（关键，避免 QG4 撞车）**：`skill-forge`(S-024) / `skill-creator-optimized`(S-022) 负责"**写**出一个技能包"；`skill-refactor`(S-023) 负责"**改造**已有技能"。本 SOP 负责它们**之前**的环节——判断外部项目里有什么可提、去重、净化、并把它按治理纪律落进体系；真正锻造技能包时 **handoff 给 skill-forge/creator**。
> ⚠️ 若用户说"帮我新建一个技能 / 把这个流程封装成 Skill" → 直接转 **S-024 / S-022**；若说"这个外部项目里能提取出哪些技能、怎么提" → 用**本 SOP**。

## 能力模块：外部项目技能提取 SOP

### 1. 功能
把"一个含代码/文档/笔记的外部项目"转换为"我们技能体系里的可复用资产"，提供一套可复用的判断与落地流程：
- **可提取性评估**：逐子系统判定实际能力（读源码非 README），区分三层——框架层（通常冗余）/ 执行编排层（净增量候选）/ 部署胶水（不可提取）。
- **现有体系比对**：grep 现有 `skills/` 目录，判定重复 / 冲突 / 互补 / 正交独立，识别 QG4 触发词冲突。
- **净化**：工具无关化（具体工具→"任意等价 X"）、剥离部署依赖（Docker/端口/本地路径）、红线标注（随机合成数据 / 假数据代码）、缺口补全。
- **落地 + 治理同步**：新建或并入现有技能，并强制同步 4 张治理全局表（QG13/§8.1）。

### 2. 解决的问题
- **盲目搬运**：直接把外部项目当技能部署，引入大模型/运行时依赖，重且用不上。
- **只改技能本体、漏改全局表**：导致路由/编号/衔接脱节（正是本体系 §8 要杜绝的）。
- **重复造轮子**：没比对现有体系，提取出和 PT/PM 技能重叠的东西。
- **命名陷阱**：项目里"工作流"和体系里"工作流"同名不同层，误判为重复或重复建。
- **虚假价值**：把随机合成数据当真实用户研究提进来，污染严谨方法论。

### 3. 什么情况下使用
**✅ 使用本 SOP 当：**
- 用户给一个外部项目路径 + "提取 / 看看能提什么 / 哪些能变成技能"；
- 要把某项目的"数据采集方法 / 工具集 / 知识"融入现有技能体系；
- 评估外部项目与现有技能是重复、冲突还是互补。

**❌ 不使用（转其他技能）当：**
- 从零新建一个技能包 → **S-024 skill-forge** / **S-022 skill-creator-optimized**；
- 改造/清理一个**已存在**的技能 → **S-023 skill-refactor**；
- 纯治理盘点/路由（无外部项目源）→ **GOV_SkillGovernance**(CX-8)。

### 4. 红线与注意事项
- **不部署原项目**：本 SOP 只提取知识/方法，不搬运运行时代码、不部署大模型/Docker（用户明确"项目不部署"时尤甚）。
- **随机/合成数据红线**：外部项目的"合成 persona / 假数据代码"**禁止**当真实用户研究提取；若提取，必须标注为"无真实用户时的占位"并强免责，且不得并入严谨的 Persona 方法论技能。
- **框架层冗余不重复**：现有体系已严谨拥有的框架（NPDP/JTBD/KANO 等），外部项目在此层通常更弱，只提其**净增量（执行/编排层）**。
- **命名陷阱必须拆开**：项目里叫"workflow"的东西，和体系里"workflow-chains"可能完全不同层——先拆开再判断，避免范畴错误。
- **治理纪律不可省**：每次增改必须同步 4 张全局表 + 给交付说明（QG13/§8），本 SOP 自身也须遵守。

## 8 步提取工作流速览（详见 references/extraction-playbook.md）

| 步 | 动作 | 关键产出 | 详细 |
|----|------|---------|------|
| 0 | 范围澄清 | 确认"项目不部署、只提知识" | §Step0 |
| 1 | 探索定位 | 项目结构图 + 目标子系统 | §Step1 |
| 2 | 可提取性评估 | 每子系统三层判定（框架/执行/部署） | §Step2 |
| 3 | 现有体系比对 | 重叠/冲突/互补/正交 结论 | §Step3 |
| 4 | 用户决策 | 可提取性评估表 + 依据，等拍板 | §Step4 |
| 5 | 净化 | 工具无关化 + 剥离部署 + 红线 + 补缺 | §Step5 |
| 6 | 落地 | 新建(分配 governance_id) 或 并入现有 | §Step6 |
| 7 | 同步治理表 | 4 张表登记衔接 + 升版本 | §Step7 |
| 8 | 交付说明 | §8.2 四要素（改了什么/为什么/影响文件/遗留） | §Step8 |

> 第 4 步**不擅自落地**——保留/废弃/合并的最终决策须用户确认（GOV 决策层边界）。

## 调用接口约定（供其他 SKILL / 用户调用）

- **能力名**：`skill-extraction-sop`
- **输入**：`{ project_path, target_subsystems[], deploy_ok=false, notes }`
- **输出**：`{ extraction_assessment (per-subsystem 建议+依据), governance_actions (已同步的表), delivery_note (§8.2) }`
- **衔接关系**：
  - → `skill-forge`(S-024) / `skill-creator-optimized`(S-022)：判定"要新建技能包"后，handoff 给它们真正锻造 SKILL.md；
  - → `skill-refactor`(S-023)：若提取涉及改造已有技能；
  - → `GOV_SkillGovernance`(CX-8)：治理纪律（QG13/§8）的权威来源；
  - ← 上游：用户给的外部项目路径 + 提取意图。
